本讲结论

程序只做你写的事，不做你以为的事。调试就是找出两者在哪一步分岔。先用打印和日志看，再上调试器、系统调用追踪和 sanitizer。调试器能设断点、观察点，还能倒着执行。性能分析先测量，再优化。测量靠 time、基准测试、profiler 和火焰图。

代码只做你写的事，不做你想的事 0:00

计算机严格按字面执行，不猜你的心思。你想的和它做的，总会在某一步分岔。调试就是找到这一步。

bash · 本机实测（Python 3.13.5）
$ python -c 'x = [3, 1, 2]; y = x.sort(); print(y, x)'   # 以为 y 是排好的新列表
None [1, 2, 3]   # sort 原地改了 x，返回值是 None

打个比方计算机像一个死抠字面的跑腿。你说“把这摞单子排好给我”，他在原地排好了。递到你手里的，却是一张空收条。

这是讲义开头的“黄金法则”。代码不会做你期望的事，只会做你告诉它的事。计算机几乎什么都能做，但它只认字面。

调试（debugging）处理的是结果不对。性能分析（profiling）处理另一类问题。结果是对的，但太慢或太占内存。

代码看着对，跑了一个例子也对，就以为没问题。练习页的归并排序就是这样。bug 只在下标 i 和 j 不相等时才出现。前两次合并时 i 和 j 都是 0，结果碰巧是对的。所以别只信一个例子，多造几组随机数据去对拍。

跑过头才发现出错？rr 能倒着执行 7:07

rr 先把一次运行完整录下来。回放时既能往前走，也能倒着走。发现值已经坏了，就从这里往回倒。一直倒到它刚被改坏的那一刻。

rr · 写法示意（本机没有 Linux，未实测）
rr record ./corruption        # 录一次完整运行
rr replay                     # 回放，界面就是 gdb
(rr) watch accounts[0].id     # 盯住那个被改坏的字段
(rr) reverse-continue         # 倒着跑，停在最后一次改它的地方

打个比方rr 像行车记录仪。普通调试器只能从现在往前开。rr 能把录像往回拖，拖到撞车前一秒。看清是谁先变的道。

普通调试器只能让程序往前跑：停下，再继续。麻烦在于，你常常跑过了头才发现出错。这时真正的 bug 早就执行过去了。你真正想问的是：“这个数怎么变成 4 而不是 5 的？”（7:45）

记录-回放调试（record-replay debugging）解决的就是这个问题。Linux 上的 rr 把一次运行里所有不确定的东西都录下来。之后可以确定性地重放任意多次，还能倒着执行。它的界面就是 gdb，命令完全一样。

bash · 讲义原文（注释译成中文）
rr record ./my_program     # 录制一次执行
rr replay                  # 回放（打开 gdb 界面）
反向命令（讲义）作用
reverse-continue（rc）倒着运行，直到碰到断点或观察点
reverse-step（rs）倒退一行
reverse-next（rn）倒退一行，跳过函数调用
reverse-finish倒着运行到进入当前函数的地方

视频演示：倒放一次就抓到越界的 strcpy 11:29

账户 0 改名后，id 变成了怪数。rr 倒着执行，直接停在写坏它的 strcpy 上。

  1. gcc -g corruption.c -o corruption。-g 让编译器保留变量名和函数名。还会记下每段机器码对应哪行源码。没有它，调试器只看得到地址（12:38）。
  2. 程序跑完，账户 0 的名字正确改成了 “Alexandria”。id 却变成了一个怪数。
  3. 先 rr record ./corruption，再 rr replay。然后 break 52、continue，停在检测异常的 if 上。此时 p accounts[0].id 已经坏了（16:05）。
  4. 普通 gdb 到这里只能把断点往前挪，再从头重跑。一次次地二分。rr 可以先 watch accounts[0].id，再 reverse-continue。程序倒着执行，直到这个值发生变化（18:25）。
  5. 命中硬件观察点。注意倒放时 Old 和 New 是反的，New value 是更早的值（19:09）。bt 显示改写它的是 C 库的 strcpy，调用者是 update_name（19:51）。
  6. 原因是 name 字段只有 8 字节。“Alexandria” 加上结尾的 \0 有 11 字节。多出的部分写进了紧挨着的 id（21:02）。
rr 的限制（讲义，视频 21:37–22:48）
  • 只支持 Linux。它需要 CPU 的硬件性能计数器。很多虚拟机不提供，比如多数 AWS EC2 实例。也不支持 GPU。macOS 可以看看 Warpspeed。
  • 改了代码就得重新录。旧录像对应的是旧的二进制文件。
  • 用法技巧：第 1 讲有个“跑到失败为止”的循环。把里面的命令换成 rr record。偶发失败一出现，你就有了一份录像。它能反复前进后退。

Heisenbug（9:33）的名字来自测不准原理。你一观察，它就消失。最常见于 print 调试。打印让程序变慢。并发程序里，线程的先后顺序跟着变了。bug 也就不出现了。

调试器同样会改变执行方式。rr 尤其如此，它用确定性调度按固定顺序跑所有线程。某些竞态在它下面可能根本不发生。讲义说，可能要录好几次才能抓到。所以选工具时，不光要看它能做什么。还要看问题在它下面还能不能复现。

strace 把程序找内核办的每件事都列出来 24:55

程序开文件、分内存、建进程、上网，都要找内核。这些请求叫系统调用（system call）。strace 把每一次调用和参数都打印出来。

bash · 写法示意（Linux，本机未实测）
strace -e trace=%file ls -l       # 只看和文件有关的调用
strace -f ./build.sh              # 跟进子进程，不加就漏掉
strace ls 2>&1 | grep openat      # strace 写的是 stderr，先 2>&1 才能 grep

打个比方strace 像银行柜台的流水单。客户在家怎么盘算，你看不见。但他每次来柜台存钱、取钱、查账，都记得清清楚楚。

有时 bug 不在你的代码里。或者你只想知道，一个程序在做什么、卡在哪。它可能还是别人写的。追踪系统调用，就能看到程序在“边界”上做的每件事。

bash · 讲义原文（注释译成中文）
strace ./my_program                  # 追踪全部系统调用
strace -e trace=file ./my_program    # 只看与文件相关的
strace -f ./my_program               # 跟随子进程（程序再启动别的程序时很重要）
strace -p <PID>                      # 附着到正在运行的进程
strace -T ./my_program               # 显示每次调用的耗时
  • 输出太多：开头一大段是在启动进程、加载共享库。这些通常不是你关心的（27:22）。用 -e 过滤。%file 表示所有和文件系统有关的调用。也可以只写一个调用名，比如 statx。man 页的 filtering 一节还有更多类别（34:18）。比如进程、网络和信号。讲师用 2>&1 | less 把全部输出送进分页器慢慢翻。
  • -f 跟随子进程。讲师那台机器上，ls 其实是 Nix 的包装程序。真正干活的 ls 是它启动的子进程。不加 -f，就什么都看不到（30:28）。
  • 参数决定行为：加了 -l，ls 要对每个文件做 statx 和 listxattr。还要去读时区文件。追踪里一眼就能看出，ls -l 比 ls 干的活多（33:10）。
  • -p 附着上去却什么都不打印？说明那个进程卡在纯 CPU 计算里（34:18）。它根本没找内核。
  • macOS 和 BSD 上用 dtruss，它基于 dtrace。想深入学，可以看 Julia Evans 的 strace zine（讲义）。

要统计不要流水账，就把小程序装进内核 34:50

strace 只会逐条打印。eBPF 把一段小程序装进内核，在事件发生处就地计数。bpftrace 是它的高层写法，语法像 awk。

bash · 写法示意（本机没有 Linux，未实测）
# 每次有进程进入 openat 就触发，按进程名计数
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_openat { @[comm] = count(); }'
# 不会逐条刷屏。按 Ctrl-C 时，才打印每个进程打开了几次文件

打个比方strace 像在收银台逐张抄小票。bpftrace 像在收银机里装个计数器。它只记每种商品卖了几件，打烊时报个总数。

想要统计怎么办？比如 read 调用的耗时分布。那就得把一段小程序装进内核。这就是 eBPF（extended Berkeley Packet Filter）。它是跑在 Linux 内核里的沙箱程序。它有内核的视野，表达能力很强。bpftrace 提供了类似 awk 的高层语法（36:06）。

bash · 讲义原文（注释译成中文）
# 打印全系统每一次打开文件（立即输出）
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_openat { printf("%s %s\n", comm, str(args->filename)); }'
# 按名字统计系统调用次数（Ctrl-C 时打印汇总）
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_* { @[probe] = count(); }'
# 只看名叫 bash 的进程
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_* /comm == "bash"/ { @[probe] = count(); }'
# 用 -c 启动一条命令，cpid 就是它的 PID
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_* /pid == cpid/ { @[probe] = count(); }' -c 'ls -la'
片段含义（视频 37:17–41:29）
tracepoint:syscalls:sys_enter_*探针：进入任何系统调用时触发。* 是模式，也可以写具体名字，比如 sys_enter_statx
/条件/过滤。comm 是进程名，pid 是进程号
@[probe] = count()@ 是一个 map。probe 是当前探针名。count() 每调用一次加 1
-c 'ls -la'由 bpftrace 启动这条命令，把它的 PID 放进特殊变量 cpid。命令结束时自动打印结果
  • strace 胜在拿来就能用。想要更低开销，就用 bpftrace。追踪内核函数、做聚合，也用它（讲义）。代价是必须 root。而且它默认监视整个内核，不只是某个进程。视频 39:03 讲师因此碰到一大堆输出。
  • 现成工具：bcc 用 C 写 eBPF 程序，附带很多工具（42:34）。比如 biolatency，它画磁盘请求耗时的直方图。视频里 2 次落在 4–8 μs，1 次落在 2–4 μs。还有 opensnoop，看谁打开了哪个文件。

下面的演示是示意，本机没有 Linux。系统调用在内核里被就地计数，Ctrl-C 时才打印。再看过滤条件和 -c、cpid 怎样缩小范围。

为什么会在这里踩坑

第一次跑 bpftrace，满屏都是别的进程。它默认看的是整个系统，不是你那个程序。要加 /comm == "bash"/ 或 /pid == cpid/ 这类过滤。另外它必须 root，忘了 sudo 就跑不起来。

网络问题看包：tcpdump 抓，Wireshark 拆 43:45

tcpdump 把经过网卡的每个包都打印出来。Wireshark 能看懂 IP 之上的协议。HTTPS 加了密，要靠 mitmproxy 或浏览器开发者工具。

bash · 讲义原文（注释译成中文）
sudo tcpdump -i any port 80             # 抓 80 端口的包
sudo tcpdump -i any -w capture.pcap     # 存成文件，交给 Wireshark 分析

打个比方tcpdump 像邮局门口的监控。每个信封的寄件人、收件人和厚度，它都看得到。信要是 HTTPS 封死的，它就只能看信封。mitmproxy 相当于先拆开抄一份，再封好寄出去。

  • tcpdump 打印经过网卡的每个包。内容有源和目的 IP、端口、TCP 标志、窗口和长度。需要时连包的内容也能打。
  • 视频里讲师用 curl http://neverssl.com 制造流量（44:49）。一个简短的 HTTP 请求和响应，就产生了好几个包。
  • -i 选网卡，讲师的 Wi-Fi 叫 wlp2s0。any 表示所有网卡。
  • Wireshark 能理解 IP 之上的协议（45:57）。比如有插件专门解析 MySQL 流量。还能录下来，离线重放和测试。
  • HTTPS 是加密的，tcpdump 只能看到密文。mitmproxy 冒充服务器做中间人，解密后再记录。
  • 调网页的 HTTPS 请求，往往用浏览器开发者工具最方便。看它的 Network 面板。解密后的请求、响应、头部和耗时都能看到（讲义）。
为什么会在这里踩坑

抓了半天，只看到一堆乱码。因为请求走的是 HTTPS，tcpdump 只能看到密文。调网页请求，先开浏览器开发者工具的 Network 面板。另外 tcpdump 要 sudo。-i 选错了网卡，就什么也抓不到。

内存 bug 不一定崩溃，要靠 sanitizer 揪出来 46:31

越界写、释放后再用这类 bug，往往不会马上崩溃。它们悄悄写坏别处的内存，很久以后才出事。sanitizer 让编译器在每次内存访问前插一道检查。

c · 最小例子（示意）
char *p = malloc(32);
free(p);
p[0] = 'J';     // 写已释放的内存。不开检查，程序通常照常运行
// gcc -fsanitize=address -g uaf.c 重新编译，这一行当场报错

打个比方ASan 像给每块内存配了个门卫。门卫手里有张名单，写着哪些格子能进。free 之后，这块就从名单上划掉。谁再来碰，当场拦下。

缓冲区溢出、use-after-free 和内存泄漏，是最难查的一类 bug。视频里有个 heap overflow 的例子。程序往缓冲区里塞了超长数据，却照常结束（47:51）。看上去什么都没发生。那只是因为被覆盖的那块内存，恰好没人再用。

Sanitizer 是编译器的扩展。它让编译器在程序里插入额外的检查指令。最常用的是 AddressSanitizer（ASan）。它能查出栈、堆和全局缓冲区的溢出。还能查 use-after-free、use-after-return 和内存泄漏。

bash · 讲义原文
gcc -fsanitize=address -g program.c -o program
./program

加上 -fsanitize=address 后，同一个 heap overflow 程序直接崩溃（48:28）。ASan 还给出一份报告。报告里有错误类型和地址，还有出错时的调用链。视频里那条链上是 memcpy。另外还写明这块内存在哪分配，哪些字节被覆盖了。

其他 sanitizer（讲义）检测什么
ThreadSanitizer（TSan，-fsanitize=thread）多线程的数据竞争
MemorySanitizer（MSan，-fsanitize=memory）读未初始化的内存
UndefinedBehaviorSanitizer（UBSan，-fsanitize=undefined）未定义行为，比如整数溢出

sanitizer 要重新编译，但跑得足够快。可以放进 CI 和日常开发（49:46）。Java、Python 这类有运行时的语言，很多检查由运行时完成。这些检查有时默认关着，因为太贵。ASan 在这些语言里用不上。但它们的 unsafe 操作，同样可能出这类问题。

本机实测：MinGW 没有 ASan 运行时，但编译器能提前警告

讲义调试练习 3 的 uaf.c，本机不加检查直接运行。结果确实“看起来正常”。加 -fsanitize=address 就链接失败，因为 MinGW-w64 的 gcc 缺 libasan。不过 gcc 的 -Wall 在编译期就发现了问题：

$ gcc uaf.c -o uaf && ./uaf
Hello, world!
Jello, world!
$ gcc -fsanitize=address -g uaf.c -o uaf_asan

$ gcc -Wall -g uaf.c -o uaf

编译期警告只能抓住编译器“看得出”的情况。ASan 在运行期检查每一次访问，能抓住复杂得多的场景。完整对照见练习页调试 3。

程序没崩，输出也对，就以为没有内存 bug。use-after-free 那一下写入，通常会“成功”。上面实测就打印出了 Jello。可它也许已经悄悄改坏了别处的数据。写 C 和 C++，平时就开着 -Wall，测试时再开 ASan。

不能重编译就用 Valgrind，代价是慢 50:50

Valgrind 不改你的程序。它自己假装成 CPU，一条条解释执行。所以能检查每一次内存访问，但慢得多。

Valgrind 是一个可扩展的程序解释器。它逐条执行你程序的指令，在每条指令前后做额外检查。不用重新编译，就能查每一次内存访问。它能指出哪条指令写了不该写的内存。还能指出这块内存是哪条指令分配的。

bash · 讲义原文
valgrind --leak-check=full ./my_program

适用场景有这几种（讲义）。没有源码，或者没法重新编译，比如第三方库。或者你需要 sanitizer 没有的检查。Valgrind 也是强大的 profiler，见第 13 节。

LLM 擅长解释报错和定位，不擅长修 52:07

看不懂的报错和几十层的调用栈，可以交给 LLM 翻成人话。它给的修法，一定要自己用调试工具验证。

borrow.rs 的核心三行（注释是笔记加的。完整实测见练习页调试 5）
let first = &scores[0];            // 不可变借用，一直活到最后一行
scores.push(100);                  // 要可变借用，和上一行冲突，报 E0502
println!("first = {}", first);     // 问 LLM 时，整段代码和完整报错一起贴

打个比方LLM 像见过无数病例的老护士。你一说症状，她马上能猜出几种可能。但开不开刀，还得拍片子确认。

讲师与讲义的建议
  • 解释难懂的报错（52:44）。C++ 模板错误和 Rust 借用检查器的报错，往往很晦涩。别人多半遇到过几乎一样的报错。可地址、程序名略有不同，很难搜到。LLM 很擅长把它翻成人话，还能给出绕过办法。
  • 跨语言、跨抽象层（53:18）。比如 Python 程序链接了 Rust 库，Rust 又调用了 C 库。讲师的经验是，LLM 会自己写小的复现程序。它从 Python 一路追到 Rust，再追到 C。最后指出“C 代码这里看起来不对”。它不太擅长修这种 bug，但很擅长找。
  • 由症状猜原因：比如“程序能跑，但内存多用了 10 倍”。LLM 能列出可能的原因，以及该查什么（讲义）。
  • 读长长的调用栈（54:27）。崩溃栈动不动几十上百层。在陌生代码库里，重点尤其难找。

局限（讲义）：它可能编出听着合理、实际错误的解释。也可能给出掩盖 bug 而不是修复 bug 的改法。一定要用真正的调试工具验证。它是理解代码的补充，不是替代。

讲义提示：调试符号

想得到有意义的调用栈，就要带调试符号。二进制文件和它链接的库都要带。也就是加 -g，通常是 DWARF 格式。编译时再加 -fno-omit-frame-pointer 保留帧指针，profiler 的调用栈会更可靠。否则调用栈里可能只有内存地址，或者残缺不全。C++、Rust 这类原生程序尤其要注意。

练习页调试 5 在本机生成了两条真实的难懂报错。一条是 Rust E0502，一条是 26 行的 C++ 模板错误。页面还给了向 LLM 提问的模板和核对方法。

为什么会在这里踩坑

LLM 给的改法，常常只是让报错消失。比如 Rust 里到处加 clone()，C++ 里强制类型转换。编译是过了，程序的意思却变了。所以改完要重新编译、重新跑测试。再对照编译器自己的说明，比如 rustc --explain E0502。

优化之前先测量，别凭感觉找热点 54:27

算法课教大 O，却不教怎么找程序里的热点。凭感觉优化，很容易改错地方。先用工具测出时间花在哪，再动手。

bash · 写法示意
time ./slow                                     # 第一步：总共花了多久，CPU 忙还是在等
python -m cProfile -s tottime slow.py | head    # 第二步：时间花在哪个函数上
# 最后才改代码。改完再测一遍，确认真的变快了

打个比方看病先拍片，再开刀。不拍片就动刀，切掉的多半不是病灶。

代码功能对了还不够，吃光 CPU 或内存也不行。“过早优化是万恶之源”（讲义）。先用 profiler 和监控工具，弄清时间和资源花在哪。再集中优化那一部分。讲师说，性能分析和调试密切相关。弄明白代码在做什么，通常也就明白它表现如何。

real 远大于 user 加 sys，说明程序在等 55:00

time 报三个数。real 是墙上的钟走了多久。user 和 sys 是 CPU 真正干活的时间。差出来的那部分，程序在等网络、磁盘或别的东西。

最简单的办法就是计时。time 几乎每个 shell 都有，放在任何命令前面就行：

bash · 讲义原文
$ time curl https://missing.csail.mit.edu &> /dev/null
real	0m0.272s
user	0m0.079s
sys	    0m0.028s
含义上例
real墙钟时间：从开始到结束，包括等待0.272 s
userCPU 执行用户代码的时间0.079 s
sysCPU 在内核里替这个程序干活的时间0.028 s

CPU 一共只用了 107 ms，剩下 165 ms 在等网络。反过来，多核程序的 user 可以大于 real（56:10）。10 个 CPU 各忙 1 秒，real 是 1 秒，CPU 时间却是 10 秒。另外，同一条命令多跑几次，耗时会变（56:46）。视频里是 124 ms、138 ms 这样跳。所以只跑一次 time 来比较两个程序，并不可靠。

bash · 本机实测（Git Bash）
$ time bash -c 'i=0; while [ $i -lt 200000 ]; do i=$((i+1)); done'
real	0m3.130s
user	0m2.406s
sys	0m0.296s
$ time sleep 1
real	0m1.248s
user	0m0.015s
sys	0m0.046s
为什么会在这里踩坑：time 看不到原生程序的 CPU

对 MSYS 自己的程序，比如 bash 和 sleep，Git Bash 的 time 是准的。原生 Windows 程序就不行了，比如 python 和 gcc 编出的 exe。它们的 user 和 sys 几乎总是 0.015 s：

bash · 本机实测
$ time python -c 'sum(range(3 * 10**7))'
real	0m0.735s
user	0m0.015s
sys	0m0.031s
$ python -c 'import time; t = time.process_time(); sum(range(3 * 10**7)); print("cpu seen by python itself:", round(time.process_time() - t, 2), "s")'
cpu seen by python itself: 0.47 s

在这台机器上只信 real。CPU 时间请在程序内部测，或者换 Linux。

只跑一次不算数：多跑、预热、看波动 57:17

同一条命令每次耗时都不一样。基准测试要预热，要跑很多次，再看均值和标准差。比较两个程序时，倍数也要带上误差。

bash · 本机实测（Git Bash，TIMEFORMAT=%R 只打印 real）
$ TIMEFORMAT=%R; for k in 1 2 3; do time ls -R /usr/share > /dev/null; done
1.483   # 第一次最慢，多半是文件还没进磁盘缓存
0.261
0.181   # 同一条命令，后两次快了好几倍

打个比方量体重别只称一次。刚吃完饭和早上空腹，差一两斤很正常。多称几次取平均，再看看上下浮动多大。

hyperfine 把每条命令跑很多次。它统计均值和标准差。最后给出“快几倍、误差多少”的结论：

bash · 讲义原文
$ hyperfine --warmup 3 'fd -e jpg' 'find . -iname "*.jpg"'

  Time (mean ± σ):      51.4 ms ±   2.9 ms    [User: 121.0 ms, System: 160.5 ms]
  Range (min … max):    44.2 ms …  60.1 ms    56 runs

Benchmark #2: find . -iname "*.jpg"
  Time (mean ± σ):      1.126 s ±  0.101 s    [User: 141.1 ms, System: 956.1 ms]
  Range (min … max):    0.975 s …  1.287 s    10 runs

Summary
  'fd -e jpg' ran
   21.89 ± 2.33 times faster than 'find . -iname "*.jpg"'

  • 视频里的现场结果正好相反（57:54）。find 比 fd 快了约 40 倍。讲师是在一个几乎空的目录里测的。那不是 fd 优化的场景。可见基准测试的结论，和测试条件绑在一起。
  • 网页开发：浏览器开发者工具自带很好的 profiler。见 Firefox Profiler 和 Chrome DevTools 的文档（讲义）。

本机没有 hyperfine。练习页性能 3 写了个不到 50 行的 Python 脚本。它按同样的方法，比较了 grep -r 和 git grep。还手推了“± 0.60”是怎么来的：

为什么会在这里踩坑

改完代码跑一次 time，快了 20%，就宣布优化成功。可同一条命令连跑三次，上面实测就差了好几倍。至少多跑几次，看均值和波动。两组数据的波动范围要是重叠，这 20% 可能只是噪声。

程序慢，先看是哪种资源被吃满了 58:33

先看大盘，再看细节。CPU 是全满，还是只满一个核？内存够不够？磁盘和网络在不在排队？

bash · 写法示意（Linux）
htop                       # 每个核一根条，别只看总数
free -h                    # 总内存和已用内存
ss -tlnp | grep :8080      # 谁占着 8080 端口
lsof /var/log/app.log      # 谁开着这个文件

打个比方程序慢像高速堵车。先看是堵在收费站，还是堵在匝道。收费站是 CPU，匝道是磁盘和网络。找对地方，才知道该修哪儿。

程序慢，先看它是不是资源受限。是用满了所有核，还是只用了一个核？还是磁盘太慢？

htop每个核的利用率、内存、负载和进程列表。F6 排序，t 树状显示，H 显示或隐藏线程。小写 h 是帮助，这条按 htop 手册写（补充）。还有 I/O 等标签页
btop比 htop 监控的东西多得多，可以配置

负载（load average）是什么（视频 59:06）

htop 右上角有三个数。它们是过去一段时间里，平均“需要多少个 CPU 核”。三个数对应越来越长的时间窗口。讲师建议你自己查一下确切含义。补充：Linux 上通常是 1、5、15 分钟的指数平均。等待磁盘 I/O 的进程也算在内，见 man proc 的 loadavg 一节。

为什么会在这里踩坑

看到某个进程 CPU 占用 100%，就以为它用满了机器。其实它可能只占满了一个核，其余的核都闲着。htop 里要看每个核的条，不能只看总数。反过来，CPU 很闲程序却很慢，就该去看磁盘和网络。

perf 采样找热点，火焰图一眼看出时间去哪 1:01:21

采样型 profiler 每隔约 1 毫秒拍一下调用栈。被拍到次数多的函数，就是热点。火焰图把这些栈画出来，越宽越热。

bash · 写法示意（Linux，本机未实测）
gcc -g -O2 slow.c -o slow -lm    # -g 留下函数名，不然报告里全是地址
perf record -g ./slow            # 采样，-g 连调用栈一起记
perf report                      # Self 只算函数自身，Children 连带它调用的

打个比方采样像老师隔几分钟抬头扫一眼教室。扫一百次，有八十次看到小明在玩手机。那他大部分时间都在玩。追踪型 profiler 像给每个人都装了计时器。数字准，但人人都被拖慢。

真要让程序变快，就得知道程序内部哪里最热。CPU profiler 有两类（讲义）：

追踪型（tracing）

记录程序的每一次函数调用。数字精确，但开销大。例子有 Valgrind 的 callgrind、Python 的 cProfile。

采样型（sampling）

定期暂停程序，记下调用栈，常见是每毫秒一次。开销小，结果是统计近似。生产环境一般用它。例子有 perf、py-spy。

perf 是 Linux 的标准 profiler。不用重新编译，就能分析任何程序。perf stat 给出总览：

bash · 讲义原文
$ perf stat ./slow_program

         3,210.45 msec task-clock                #    0.998 CPUs utilized
               12      context-switches          #    3.738 /sec
                0      cpu-migrations            #    0.000 /sec

视频里，讲师对讲义的 slow.c 采样（1:02:31）。命令是 perf record -g ./slow，再 perf report。Children 列算的是这个函数，加上它调用的所有函数。所以 _start 是 100%。Self 列只算函数自身，cos 43.6%，sin 43.2%。在 report 里按 h 看帮助。还能把热点标到汇编和源码行上（1:03:40）。

火焰图：越宽越耗时，横轴不是时间顺序 1:04:48

火焰图的纵轴是调用层级。底部是程序入口，越往上调用越深。横轴宽度正比于花在那里的时间。

一大堆数字，人很难读。火焰图（flame graph）把它变成了图。讲师用的是 flamegraph 的 Rust 移植版 inferno。在浏览器里打开 SVG，还能点击放大（1:05:25）。

bash · 讲义原文
perf record -g ./my_program
perf script | stackcollapse-perf.pl | flamegraph.pl > flamegraph.svg
讲义推荐

交互式查看用 Speedscope。系统级分析用 Perfetto。各语言也有专用工具。Python 有 cProfile 和 py-spy，Go 有 go tool pprof。Rust 有 cargo-flamegraph，其实对任何编译型程序都能用。

采样会漏，要精确计数就用 callgrind 1:06:35

采样只看得到被拍到的瞬间。频率调高更准，但暂停越多，程序被拖得越慢。要精确数据，就用 Valgrind 的 callgrind（讲师）。

它解释执行每一条指令，所以能精确计数，但很慢。

bash · 讲义原文（注释译成中文）
valgrind --tool=callgrind ./my_program
callgrind_annotate callgrind.out.<pid>     # 文本报告
kcachegrind callgrind.out.<pid>           # 图形界面

callgrind 给出精确的调用次数，还有谁调用了谁。加 --cache-sim=yes 还能模拟缓存行为（讲义）。

本机实测：没有 perf，用 Python 版对照两类 profiler

slow.c 在本机编译运行，用了约 11–18 秒。几次运行差异较大。perf 跑不了，于是把它翻成 Python 版 slow.py。再分别用追踪型的 cProfile 和自己写的 40 行采样器分析：

$ python -m cProfile -s tottime slow.py | head -12

cProfile 让程序慢了 2.6 倍，从 0.40 s 变成 1.05 s。换来的是精确的调用次数。采样器几乎不拖慢程序。但它只看得到 Python 帧，分不出 sin 和 cos。详见练习页性能 2。

下面的演示分两幕。第 1 幕画出采样、合并计数、画火焰图的过程。数字按视频里的 perf report 折算。第 2 幕是上面这组本机实测的对照。

为什么会在这里踩坑

火焰图里某个块很宽，就以为它被调用了很多次。宽度只说明它占的时间多。可能是调用多，也可能是单次就很慢。要精确的次数，得用 callgrind 或 cProfile 这类追踪型工具。另外，没带 -g 或省掉了帧指针，调用栈就会残缺。火焰图上只剩一堆地址。

内存只涨不跌，就用内存 profiler 看谁在涨 1:06:35

内存 profiler 记录堆内存随时间的变化。泄漏和过度分配，都能从曲线里看出来。

mem.py · 本机实测（补充，非视频内容。注释是后加的）
import tracemalloc
tracemalloc.start()                          # 从这里开始给内存记账
a = [0] * 1_000_000                          # 一百万个元素的列表
cur, peak = tracemalloc.get_traced_memory()  # 当前用量和峰值，单位是字节
print(cur // 1024, "KiB")                    # 本机输出 7812 KiB，每个元素存一个 8 字节指针

打个比方内存 profiler 像记账本。每笔开销都记下是哪一行花的。月底一对比，就知道钱从哪儿漏出去了。

视频只顺带提了一句（1:07:12）。Valgrind 有多种“工具模式”。比如检查内存用得对不对，或者统计指令次数。讲义补充了专门的内存 profiler：

bash · 讲义原文
valgrind --tool=massif ./my_program
ms_print massif.out.<pid>

Massif 记录堆内存随时间的使用情况。它能帮你发现内存泄漏和过度分配。Python 可以用 memory-profiler 逐行查看内存用量。

补充（非视频内容）：Python 标准库的 tracemalloc

不装第三方包也行。tracemalloc.start() 之后，用 tracemalloc.take_snapshot().statistics('lineno') 按源码行统计当前分配的内存。两次快照相减，还能看出哪一行在涨。见官方文档。上面的最小例子用的就是它。

为什么会在这里踩坑（补充，非视频内容）

内存涨了，不一定是泄漏。缓存、预分配、列表扩容，都会让内存先涨一截。要看的是曲线。跑得越久涨得越多，而且从不回落，才像泄漏。只看某一刻的总量，很容易冤枉好代码。

性能数据要画成图，表格看不出规律 1:07:12

性能分析不只是找哪里慢。还要看耗时怎样随输入变化。几千行的数字表看不出规律，一张图就看出来了。

bash · 写法示意
echo "$(date +%s),$ms" >> latency.csv   # 打日志时就写成“时间戳,数值”
gnuplot -e "set datafile separator ','; plot 'latency.csv' using 1:2 with lines"   # 一行出图

打个比方体检报告上一排数字，很难看出趋势。把十年的体重画成一条线，哪年突然胖了，一眼就看到。

讲师举了个例子。比如一个像 grep 的搜索程序。你想知道它的耗时怎样随输入变化。变量有输入大小、模式长度和模式复杂度。一张大表格记满了输入多大、模式多长、用了多少微秒。这种表没什么用，要画出来（1:07:55）。

bash · 讲义原文（注释译成中文）
# 画一个 “时间戳,数值” 的 CSV
gnuplot -e "set datafile separator ','; plot 'latency.csv' using 1:2 with lines"
  • 让数据好画（讲义）。打印或记日志时，就用 CSV 或 JSON 这种整洁格式。比如 1705012345,42.5。这比一句话好处理得多。
  • gnuplot 为 shell 而生。它和 bpftrace 一样，用 -e 传一段小程序。适合快速出图（1:08:33）。
  • matplotlib 和 ggplot2 适合反复切分、变换数据，验证猜想。讲师最喜欢 ggplot2 的 facet，也就是分面（1:09:47）。它按某一列把数据拆成一组并排的小图。再用颜色、行列编码更多维度，一次看清五维数据。
讲义里的例子
  • 画出请求延迟随时间的曲线。百分位数看不出的周期性变慢，曲线上一目了然。比如垃圾回收、定时任务、流量模式。
  • 往一个不断增长的数据结构里插元素，画出耗时。底层数组容量翻倍时，会出现特征尖峰。
  • 按维度分面，比如请求类型、用户群、服务器。常常发现“全系统问题”其实只出在某一类上。
为什么会在这里踩坑

只看平均延迟，一切正常。可每隔一分钟就有一次尖峰，平均值把它抹平了。用户偏偏就撞上了那一下。所以别只盯一个汇总数，把原始数据按时间画出来看看。

以后要分析的数，现在就记进日志 1:11:35

讲师的结束语把首尾连了起来。以后想分析的数据，现在就用结构化的形式记进日志。真需要时，直接解析、画图。

python · 写法示意
log.info(json.dumps({"event": "search",
                     "input_bytes": n,        # 输入多大
                     "pattern_len": len(p),   # 模式多长
                     "us": elapsed}))         # 用了多少微秒。以后直接拿去画图

打个比方像搬家前就给每个箱子贴好标签。现在多花一分钟，以后找东西就不用把箱子全拆开。

讲师说，你要是知道以后会做性能分析，就别等。早点把相关的数记进日志。比如输入多大、函数用了多久、内部的图有多大。尽量用结构化的形式。等到真需要时，信息已经在日志里了。直接解析、画图，就能看出潜在问题。比如“扩展性悬崖”。

为什么会在这里踩坑

日志只写一句话，比如 “search took a while”。出了性能问题想回头分析。这才发现没记输入大小，也没记耗时。只能补上日志，再等问题重现一次。

一页带走：本讲结论都在这几行里 1:12:48

把本讲浓缩成几行命令。每行的注释就是结论和考点。

bash · 本讲速查（注释即考点）
logging.basicConfig(level=logging.INFO)   # 日志按级别过滤。配置放在最前面，不然会被忽略
b merge, len(left) == 2                   # pdb 条件断点用逗号，gdb 用 if
# 为什么要条件断点：前两次合并 i 等于 j，bug 不显现
watch students[1].id                      # 观察点：值一变就停，回答“谁改了它”
rr record ./prog; rr replay               # 录一次，随便倒着放。只支持 Linux
(rr) reverse-continue                     # 倒放命中观察点时，New value 才是更早的值
strace -f ./prog 2>&1 | less              # -f 跟子进程。追踪写在 stderr，要先 2>&1
gcc -fsanitize=address -g prog.c          # ASan：运行时抓越界和 use-after-free
time ./prog                               # real 2.0 s，user 0.1 s：在等，加 CPU 没用
strace -T ./prog                          # 接着查它在等什么：看哪个系统调用耗时长
hyperfine --warmup 3 'a' 'b'              # 快 1.8 ± 0.6 倍：误差太大，别急着下结论
perf record -g ./prog; perf report        # 采样找热点。Self 算自身，Children 连带子调用
# 火焰图的宽度是时间占比，不是调用次数。要次数就用 callgrind 或 cProfile
  • print 调试仍然最常用。修好 bug 后，把 print 改成带级别的日志留下。结构化日志方便事后提取和画图。
  • 调试器能设断点，断点可以带条件。还能单步、看变量、看调用栈、设观察点。gdb 和 lldb 通用，pdb 这类是语言专用。
  • rr 录一次就能确定性回放，还能倒着执行。配合观察点，直接找到谁改了它。它只支持 Linux，还要小心 Heisenbug。
  • strace 看程序和内核的边界。要统计用 bpftrace，查网络用 tcpdump、Wireshark 和 mitmproxy。
  • 内存 bug 用 sanitizer，要重新编译但够快。Valgrind 不用重新编译，但很慢。
  • 性能先测量。time 分清 real、user、sys。基准测试多跑几次，看均值和 σ。perf 加火焰图找热点，callgrind 求精确。最后把数据画出来。
