本讲结论

Git 仓库里只有两样东西。一是对象：blob、tree 和 commit。它们按内容的 SHA-1 命名，写进去就不再改。二是引用：分支和 HEAD 这些能移动的名字。每条 git 命令，都只是在添加对象、移动引用。想清楚它对提交图做了什么，命令就不再是咒语。

Git 存的是快照，还能自动帮你找 bug 0:00

版本控制系统把目录在每个时刻的样子存成快照。每个快照都是整个目录，外加谁做的、为什么做。

bash · 写法示意
git log --oneline -3         # 最近 3 个快照，一行一个
git blame main.py            # 每一行最后是谁、哪次提交改的
git bisect start HEAD v1.0   # 先说好坏：HEAD 是坏的，v1.0 是好的
git bisect run ./test.sh     # 自动二分：脚本失败就算坏，几步就揪出元凶

打个比方版本控制像游戏存档。每次存档存的是整个世界，不是比上次多走几步。想回到哪一档，直接读档。

一个人用

能看旧版本，能记下为什么这么改。还能在并行的分支上开发。比如功能 1 写到一半，先切去修 bug。两边的改动互不干扰（1:07）。

多人协作

能看别人改了什么，能解决并行开发的冲突。没有版本控制，就只能来回发 zip 包。很快就乱成一团（1:40）。

讲义还列了几个问题，现代 VCS 都能轻松回答。这个模块是谁写的？这一行是谁、什么时候、为什么改的？过去 1000 个版本里，某个单元测试是从哪次开始挂的？

最后一个问题，Git 能自动二分查找来回答（2:52）。你写一个测试，有 bug 就失败。Git 会帮你定位引入 bug 的那次提交。演示见第 19 节。Git 是当今事实上的标准。

为什么会在这里踩坑

很多人把 Git 当成网盘，只会 add、commit、push 三板斧。出了问题不知道 Git 存了什么，就只能删库重来。其实每个快照都完整存着。提交过的东西，多半找得回来。

命令只能死记，数据模型可以理解 3:24

Git 的命令行界面很乱，硬背只能当咒语。但底层数据模型很简单。理解了它，命令自然就通了。

bash · 写法示意
# 自顶向下：背咒语，出错了只能删库重来
git pull; git add .; git commit -m "fix"; git push
# 自底向上：每条命令都问一句，它对提交图做了什么
git commit     # 新增一个 commit 对象，再把当前分支挪过去
git branch x   # 不新增任何对象，只是多了一个名字

打个比方背命令像背地铁换乘口诀，线路一改就懵。看懂线路图，怎么换乘自己就能推出来。

讲义引了 xkcd 1597。漫画里说，Git 用优美的分布式图论树模型跟踪协作。怎么用？没人知道，背下几条命令就行。出了错，就把工作存到别处，删掉项目，重新下一份。讲师问现场谁这么干过，不少人举手，包括他自己。

原因是 Git 的命令行是一个有漏洞的抽象（leaky abstraction）。从命令学起，就只能把命令当咒语背。可 Git 底层的设计很漂亮。丑陋的界面只能死记，漂亮的设计可以理解。所以这一讲先讲数据模型，再讲命令。每条命令都对应回数据模型（4:28）。

为什么会在这里踩坑

平时用 Git 出错，多半是不知道命令改了哪里。比如以为 git branch -d 删了提交，其实只删了名字。先想数据模型，这类误会就少了。

文件是 blob，目录是 tree，快照是顶层 tree 5:46

Git 只用两种东西描述目录。文件叫 blob，就是一串字节。目录叫 tree，把名字映射到 blob 或别的 tree。

bash · 本机实测（练习页 ex01-b 与 ex01-a，节选）
$ git cat-file -p HEAD:foo    # 子目录 foo 也是一个 tree，里面记着 bar.txt
100644 blob 3b18e512dba79e4c8300dd08aeb37f8e728b8dad	bar.txt
$ git cat-file -t 4448adbf    # baz.txt 的内容是一个 blob
blob

打个比方tree 像一本书的目录页，只写“哪个标题在哪一页”。blob 是那一页的正文。目录页本身不装正文，只记页码。

快照就是被跟踪的那个顶层 tree。目录可以一层套一层，所以 tree 也能嵌套。

为什么会在这里踩坑（补充，非视频内容）

blob 里只有内容，没有文件名。名字记在上一层的 tree 里。所以 Git 并不记录“改名”这个动作。改名之后，对新名字 git log，历史会停在改名那次。加上 --follow，Git 才会按内容相似度往前追。

历史是一张图：每个提交记着自己的 parent 8:05

Git 的历史不是一条线，而是一张有向无环图。每个提交记着一组 parent。合并出来的提交有两个 parent。

bash · 本机实测（练习页 ex01-e，节选）
$ git cat-file -p HEAD | head -4   # HEAD 是一次合并提交，所以有两行 parent
tree b6fe6fe890c2f61255f8c330c28aa2dfd93c302e
parent 352b132d8e0501612e1848b6836d29f15d3b341f
parent c560925a653e009456e6427c402986e7ef0b1998
author Ada Example <ada@example.com> 1768557600 +0000

打个比方提交图像家谱。每个人只记自己的父母是谁。合并提交就是有两个父母的孩子。往上一直追，就是整条血统。

快照之间怎么连？最简单的是一条线：版本 1、2、3 排成一列。Git 不这么做。每个快照记着它的一组 parent，也就是之前的快照。说“一组”，是因为合并时会有两条线汇到一起。Git 把这种快照叫做 commit（提交）。

讲义原文（箭头指向 parent，意思是“在它之前”）
o <-- o <-- o <-- o <---- o
            ^            /
             \          v
              --- o <-- o

第三个提交之后，历史分成了两支。比如两个功能在并行开发。最后两支被合并成一个新提交，就是加粗的那个。它同时包含两边的改动，有两个 parent（9:49）。上面实测里那两行 parent，说的就是这件事。

提交是不可变的（视频 10:27）

现实中没法回到过去改历史，Git 也一样。历史只能追加，不能修改。错误照样能纠正。所谓“修改历史”，其实是新建一批提交。再把引用（见第 7 节）指到新的那批上。

为什么会在这里踩坑

git log 默认把这张图拉平成一列显示。分叉和合并都看不出来，容易以为历史是一条线。想看图的形状，加上 --graph。

commit 就是 parent、作者、说明加一个 tree 12:13

整个数据模型几行类型定义就能写完。blob 是字节数组，tree 是名字到对象的映射。commit 是一个结构体。

bash · 本机实测（练习页 ex01-c）
$ git cat-file -p HEAD   # 一个真实的 commit 对象，对照下面的伪代码看
tree 12330f8cfe317d61bbf9690538896975910e22f2
parent a9254971ec6ef8d6423964549097af7233cda0ac
author Ada Example <ada@example.com> 1768557600 +0000
committer Ada Example <ada@example.com> 1768557600 +0000

exclaim

打个比方commit 像一张快递单。单上写着寄件人、备注和上一单的单号。箱子里装着整个目录，也就是 tree。

讲义原文（注释译成中文）
// 文件就是一堆字节
type blob = array<byte>

// 目录：名字 → 文件或目录
type tree = map<string, tree | blob>

// 提交：父提交、元数据、顶层 tree
type commit = struct {
    parents: array<commit>
    author: string
    message: string
    snapshot: tree
}

对照实测看。第一行 tree 就是伪代码里的 snapshot。parent 对应 parents，最后一行是 message。真实的 commit 比伪代码多一行 committer。第一个提交没有 parent 行，见练习页 ex01-b。

讲师强调了几个词（13:29）。blob 和 tree 是这个递归结构里的元素。“快照”不完全是 Git 的标准术语。它指被跟踪目录对应的顶层 tree。commit 是历史图里的节点。它也是递归的，因为它会引用别的 commit。

为什么会在这里踩坑

伪代码里 parents 是 commit 本身，好像提交里装着父提交。真实存储里只放父提交的哈希，见下一节。所以父提交一变，子提交的哈希就得跟着重算。

对象按内容的 SHA-1 命名，引用别人只记哈希 15:28

blob、tree、commit 统称对象。Git 用对象内容的 SHA-1 当键，存进对象库。这叫内容寻址：内容一样，ID 就一样。

bash · 本机实测（Git 2.55，哈希和讲义原文相同）
$ git cat-file -p HEAD^{tree}   # tree 里不装子对象，只记它们的哈希
100644 blob 4448adbf7ecd394f42ae135bbeed9676e894af85	baz.txt
040000 tree c68d233a33c5c06e0340e4c224f0afca87c8ce87	foo
$ git cat-file -p 4448adbf      # 拿哈希前缀就能取回内容
git is wonderful
$ printf 'blob 17\0git is wonderful\n' | sha1sum   # 手算一遍，结果一样
4448adbf7ecd394f42ae135bbeed9676e894af85 *-

打个比方内容寻址像按指纹建档。同一个人永远是同一个指纹。档案柜按指纹编号，不按名字。别的档案提到他，只写指纹号。

讲义用几行伪代码写出了对象库：

讲义原文
type object = blob | tree | commit
objects = map<string, object>

def store(object):
    id = sha1(object)
    objects[id] = object

def load(id):
    return objects[id]

关键细节是，对象引用别的对象时，并不装着它们。它只记下它们的哈希。可以把哈希当成指针（17:26）。讲义那个目录的顶层 tree，打开就是上面那样。本机按同样内容造了一个仓库，哈希和讲义一字不差。

最后一条命令说明了哈希到底算的是什么。先是类型和长度，再是一个 \0，最后才是内容。

学生提问：SHA-1 是什么？（视频 21:52）

哈希函数把任意长的字节，确定地变成固定长度的输出。SHA-1 输出 160 位，写成 40 个十六进制字符。结果看着像随机数。两个不同的输入，几乎不可能撞出同一个结果。

讲师用“随机预言机”打比方。想象全世界共用一本登记簿。有人第一次查某个输入，就给它分配一个随机值。以后谁再查，都得到同一个值。

另一个提问是，哈希为什么写成字符串。其实在磁盘上它是字节数组。写成十六进制，只是为了讲解方便（23:35）。

补充（非视频内容）：SHA-1 已经不安全了吗

2017 年已经有人造出了 SHA-1 碰撞。Git 从 2.13 起，换用能检测已知碰撞攻击的 SHA-1 实现。从 2.29 起，又实验性地支持 SHA-256 仓库，命令是 git init --object-format=sha256。内容寻址的思想不变。详见 Git 文档 hash-function-transition。

为什么会在这里踩坑

两个人在不同电脑上提交同一份文件。blob 哈希一样，commit 哈希却不一样。因为 commit 里还有作者、时间和 parent。任何一项不同，哈希就变。练习页把身份和时间都固定了，哈希才能复现。

下面的演示分两幕。第 1 幕从字节开始，算出一个 blob 的 ID。第 2 幕看 tree 和 commit 怎么用哈希互相指。再看改一个字节时，哪些对象会变，哪些被共享。

引用是给哈希起的名字，而且可以改 24:08

40 位的哈希记不住，所以 Git 给它起名字，叫引用。对象写进去就不变。引用却随时能改成指向别的提交。

bash · 本机实测（练习页 ex01-b，节选）
$ cat .git/HEAD .git/refs/heads/master   # 引用就是小文本文件
ref: refs/heads/master
a9254971ec6ef8d6423964549097af7233cda0ac
# HEAD 里写着“我跟着 master”，master 里写着一个提交哈希

打个比方对象像图书馆里的书，上架后再也不改。引用像书架上的“新书推荐”标签。标签随时能挪到另一本书上。

比如 master 通常指向主开发线上最新的提交。讲义把引用也写成了伪代码：

讲义原文
references = map<string, string>

def update_reference(name, id):
    references[name] = id

def read_reference(name):
    return references[name]

def load_reference(name_or_id):
    if name_or_id in references:
        return load(references[name_or_id])
    else:
        return load(name_or_id)

历史为什么必须不可变？讲师是这么解释的（24:08）。后面的提交靠内容的哈希指向前面的提交。改了中间某个提交，它的哈希就变了。后面所有指向它的东西都对不上。所以对象库只能追加，可变的部分全放在引用里。开发新功能时，你新建提交指向旧提交。再把 master 挪到新提交上。

为什么会在这里踩坑

rebase 或 amend 之后，提交哈希全变了。如果已经 push 过，同事手里还是旧哈希。两边的历史就分叉了。所以已经分享出去的历史，别改写。

提交了密钥先作废它，撤销提交用 revert 26:30

“改写历史”并不是真的改。Git 是照着你要的改动，重建那个提交。它之后的提交也全部重建。

bash · 本机实测（补充，身份和时间按练习页固定）
$ git revert --no-edit HEAD   # 不碰旧提交，追加一个反向改动
[anish 5fe8159] Revert "add hotel"
 Date: Fri Jan 16 10:00:00 2026 +0000
 1 file changed, 1 deletion(-)
$ git log --oneline           # 旧提交还在，只是多了一个
5fe8159 Revert "add hotel"
856e17c add hotel
13341bc initial commit

打个比方revert 像在账本末尾记一笔冲账。前面记错的那笔不涂改，只是后面再记一笔抵消它。

  • 已经分享出去了：先去对应服务作废这个 key。再生成一个新的。作废之后，它留在历史里也没关系（27:05）。
  • 还没分享：可以用 git rebase 这类命令改写历史（27:39）。它不是真的修改，而是重建那个提交和之后所有提交。练习 3 练的就是这个。
  • 只想撤销某次提交的效果：用 git revert。它算出那次的改动，在最新处追加一个反向的新提交。历史一点不改（28:15）。
  • 合并时 Git 怎么知道怎么合：靠一套启发式规则。两边改的是不同文件，就自动合并。同一文件里离得远的两处，也能自动合并。改的是同一处，比如同一个函数，Git 就放弃。它报合并冲突（merge conflict），在文件里留下冲突标记。由你来判断怎么改（29:23、31:05）。git mergetool 能帮忙，详见第 12 节。
为什么会在这里踩坑

密钥推上去以后，很多人第一反应是改写历史。可别人的克隆和 fork 里可能早有了。所以第一步永远是作废密钥，改写历史只是第二步。撤销已分享的提交，用 revert 最安全。

HEAD 记着你在哪，仓库就是对象加引用 31:42

新建提交时，Git 得知道 parent 是谁。所以它用一个特殊引用 HEAD，记着“你现在在哪”。

讲义例子（注释是笔记加的）
git checkout master; git reset --hard 5d83f9e
# 前一半：HEAD 附着到 master 上
# 后一半：master 挪到 5d83f9e，工作区也跟着变过去
# 合起来：丢掉未提交的修改，让 master 指向 5d83f9e

打个比方仓库像一本只能往后续写的书。对象是写好的页，引用是贴在页边的便利贴。HEAD 是你手里的书签，标着你正在读哪一页。

HEAD 可以粗略理解成“你现在正在看的那个东西”。于是可以给 Git 仓库下定义了：仓库就是对象加引用。磁盘上 Git 存的就这两样。

所有 git 命令，都是在提交图上做两件事。一是添加对象，二是添加或移动引用（讲义）。反过来，你想对提交图做某种改动。多半有一条命令能做到。比如“丢掉未提交的修改，让 master 指向 5d83f9e”。这就是上面那两条命令。

学生提问：GitHub 是什么？（视频 32:59）

很多人以为 HEAD 就是“最新的提交”。其实它只是“你现在在哪”。切到旧提交时，HEAD 就指着旧提交，见第 15 节。

git add 拷的是此刻的内容，之后再改不算 34:46

暂存区决定下一次提交里有什么。git add 把文件此刻的内容放进暂存区。git commit 再把暂存区做成提交。

bash · 本机实测（练习页 ex01-d，节选）
$ echo hotel >> nato.txt; git status --short   # 右列 M：工作区改了，还没暂存

$ git add nato.txt; git status --short         # 左列 M：改动进了暂存区
M  nato.txt
$ echo india >> nato.txt; git status --short   # 暂存后又改：两列都是 M
MM nato.txt

打个比方git add 像把作业复印一份交到讲台上。之后你在原稿上接着改，讲台上那份不会变。commit 收走的是讲台上那份。

有的 VCS 只有一个“拍快照”命令。它把目录当前的样子整个存下来。Git 不这样，因为我们想要干净的快照。暂存区不属于数据模型。它是“怎么做出一个提交”的操作界面。

  • 你写了两个独立的功能，想拆成两次提交。每次只含一个功能。
  • 你修了一个 bug，又到处加了调试用的 print。你只想提交修复，丢掉 print（讲义）。

Git 的办法是暂存区（staging area，也叫 index）。你用它挑出下一次提交要包含的修改。

命令（讲义）作用

git commit -a 只暂存已跟踪文件的修改。新建的文件不会被带上，得先 git add。很多人以为 -a 是“全部”。提交完才发现，新文件没进去。

分支只是一个指向提交的指针 45:00

分支是一种特殊的引用。HEAD 附着在它上面时，每次提交它都跟着往前挪。别的分支原地不动。

bash · 本机实测（补充，身份和时间按练习页固定）
$ git branch anish                 # 建分支不新增任何对象
$ cat .git/refs/heads/anish        # 分支就是一个文件，里面只有一个哈希
13341bc1a326fe29015968de880508bce2fa2b8b
$ wc -c < .git/refs/heads/anish    # 40 个十六进制字符，加一个换行
41
$ git switch -q anish; echo hotel >> nato.txt; git commit -q -am "add hotel"
$ git log --all --oneline --decorate   # 只有 anish 前进了，master 留在原地
856e17c (HEAD -> anish) add hotel
13341bc (master) initial commit

打个比方分支像一枚书签。你拿着哪枚书签往后写，它就跟着挪到新的一页。别的书签留在原处。

git status 说 On branch master，意思是 HEAD 附着在 master 上（45:00）。git commit 一条命令做了两件事。先在图里加一个节点，再把 master 挪过去。

  • 分支不是“一串提交”：直觉上分支像一整条血统。但在 Git 里，它只是一个指向提交的指针。想挪到哪就挪到哪。血统由提交里的 parent 记着（46:42）。
  • master 不会自动指向最新提交。只有你所在的分支，才会随提交前进。git branch anish 在当前位置建新分支，git switch anish 切过去。再提交，前进的是 anish，master 留在原地（48:03）。
  • switch 也改工作区：切回 master 后，nato.txt 变回 master 那个快照的内容。刚加的 hotel 不见了（49:20）。
  • git log 默认只显示从当前分支走得到的历史。加 --all，才显示从所有分支走得到的（49:55）。
bash · 本机实测（练习页 ex01-e，复刻视频的操作）

合并生成有两个 parent 的提交，改了同一处才冲突 50:28

两个提交谁也不是谁的祖先，历史就分叉了。git merge 新建一个合并提交，把两边的改动合在一起。

打个比方合并像两个人各改了同一份文档的不同段落。一个改开头，一个改结尾，拼起来就行。两人改了同一句话，就得有人拍板。

切回 master，运行 git merge anish。Git 新建一个合并提交，会打开编辑器让你写说明。它提示 Auto-merging nato.txt。一边在开头加了 alpha，一边在末尾加了 hotel，中间相同。差异合并算法自动合在一起，没有冲突（51:10）。

删错分支别慌，reflog 记着引用去过哪 54:09

引用是会变的，所以 Git 记下了每个引用的历史，叫 reflog。分支挪错了、删错了，都能从这里找回原来的位置。

bash · 本机实测（补充，身份和时间按练习页固定）
$ git branch -D anish        # 没合并的分支，用 -D 强删
Deleted branch anish (was 856e17c).
$ git reflog -3              # HEAD@{1} 就是被删分支最后指的提交
13341bc HEAD@{0}: checkout: moving from anish to master
856e17c HEAD@{1}: commit: add hotel
13341bc HEAD@{2}: checkout: moving from master to anish
$ git branch anish 856e17c   # 照着哈希重建，分支回来了
$ git log --all --oneline --decorate
856e17c (anish) add hotel
13341bc (HEAD -> master) initial commit

打个比方reflog 像浏览器的历史记录。书签删了，历史记录里还有你去过的网址。照着网址再建一个书签就行。不过历史记录也会定期清理。

学生问，删了分支还能找回来吗？讲师说这是相当高级的内容。操作得当，就永远用不上。Git 还维护了一些额外状态。其中就有引用的历史，命令是 git reflog。引用是可变的，所以记下它曾经指向哪里很有用。

Git 怎么决定留哪些对象？从任何引用出发能走到的提交，都算“活着”。哪个引用都走不到的，就成了孤儿对象。Git 会自动对它们做垃圾回收。所以刚删的分支，提交还在对象库里，reflog 也找得到。一年后才后悔，可能就没了（54:40）。

学生提问：新建分支时怎么指定它指向哪里？（视频 55:50）

不带参数时，它指向当前位置，也就是 HEAD。也可以给一个引用或哈希。git branch old <哈希> 就在那个提交上，建了一个叫 old 的分支。上面找回 anish 用的就是这招。

为什么会在这里踩坑（补充，非视频内容）

reflog 只存在你本地的仓库里，push 不会带上它。换台电脑，就没有这份记录了。reflog 条目也会过期。过期后再 gc，孤儿对象就真的没了。所以别把它当备份。

main 放稳定代码，每个功能开一个分支 56:34

常见做法是让 main 放最新的稳定代码。开发功能时开一个功能分支，改完再合回 main。

bash · 写法示意
git switch -c fix-login      # 从 main 开一个功能分支
git commit -am "fix login"   # 在分支上随便提交，main 不受影响
git switch main              # 改完回到 main
git merge fix-login          # 合回来，再删掉分支名

打个比方main 像正式出版的书。功能分支像你的草稿本。草稿写好了，再誊进正式版。

这个分支以前默认叫 master。现在 GitHub 默认叫 main。更复杂的工作流也有。比如网站的生产版本在 main，预发布的测试版在 staging。功能和修复分支先合进 staging 测试。没问题了，再合进 main（57:08）。

名字只是约定，叫 anish 也行。讲义列了几种流行的工作流，比如 git-flow，也有对它的批评。

补充：本机 Git 的默认分支名（本机实测）

本机是 Git 2.55。没配 init.defaultBranch 时，它仍用 master。但 git init 会打印一句提示：This default branch name will change to "main" in Git 3.0。提示里还教你用 git config --global init.defaultBranch <name> 来设定。练习页的实验都显式设成了 master，和讲义一致。

为什么会在这里踩坑

一直在 main 上直接改。改到一半来了紧急 bug，半成品就和修复混在一起了。养成习惯，一件事开一个分支。

切到旧提交会游离 HEAD，这时的提交没人跟 57:45

git checkout 一个提交哈希，HEAD 就直接指着提交。它不附着在任何分支上。这时提交，没有分支跟着前进。

bash · 本机实测（练习页 ex01-f，节选）
$ git checkout -q HEAD~1; git status | head -1   # 切到上一个提交
HEAD detached at 6f7b00b
$ echo zulu >> nato.txt && git commit -q -am "orphan"; git switch master
Warning: you are leaving 1 commit behind, not connected to
any of your branches:

  d6fefb2 orphan
$ git branch rescue HEAD@{1}   # 趁 reflog 还在，给它起个名字

打个比方游离 HEAD 像在旧版本上写散页。写的东西没装订进任何一本册子。你一走开，散页就没人管，迟早被清理。

想把工作区变回某个旧状态，有两种办法。一是 git switch old，切到指向旧提交的分支。二是直接 git checkout <提交哈希>，哈希写出足够唯一的前缀就行。

第二种情况下，git log 里那个全大写的 HEAD 直接指着提交。git status 会说你处于 detached HEAD（游离 HEAD）状态。这时没有活动分支（58:54）。

游离状态下也能提交，但没有分支跟着前进。切回 main 时，Git 会警告你。说你留下了 1 个提交，没连到任何分支上。这个提交暂时还在对象库里。可没有分支指向它，也没有分支指向它的后代。它最终会被回收（59:59）。补救办法见 1:08:58 的问答：用它的哈希建一个分支。

为什么会在这里踩坑

为了看旧代码，checkout 了一个哈希。顺手改了几行，还提交了。切回 main 时 Git 警告了，很多人没看就关了。那几个提交就成了孤儿。补救是趁 reflog 还在，用 git branch 给它起个名字。上面实测的 rescue 就是这么救的。

remote 只是另一个仓库，fetch 取数据不动本地分支 59:25

Git 是分布式的。你手里就是一份完整的仓库。它可以连任意多个别的仓库，叫 remote。push 送出对象和引用，fetch 取回来但不改你的本地分支。

bash · 本机实测（练习页 ex01-h：用本地裸仓库代替 GitHub）
$ git status -sb | head -1                    # bob 刚 push 过，alice 这边却显示一致
## master...origin/master
$ git fetch -q && git status -sb | head -1    # fetch 之后，才知道落后 1 个
## master...origin/master [behind 1]
$ git pull -q --ff-only && git log --oneline  # pull 才真正挪动本地 master
fdf7920 bob: second
4d59c41 alice: first

打个比方origin/master 像你上次看天气预报时记下的数。天变了，你不重新看预报，记下的数就不会变。fetch 是重新看一眼。pull 是看完再照着换衣服。

GitHub 上的仓库并不特殊。在上面建一个空仓库。这相当于别人做了一次 git init（1:00:34）。

命令（讲义）作用
git remote列出 remote
git remote add <名字> <url>添加 remote，惯例叫 origin
git push <remote> <本地分支>:<远程分支>把对象送到远程，再更新远程的引用
git branch --set-upstream-to=<remote>/<远程分支>让本地分支对应一个远程分支。git push -u 也会设置

视频里的流程在 1:01:43 到 1:04:40：

  1. 在 GitHub 上建一个空仓库。
  2. git remote add origin …。认证细节见 GitHub 文档。
  3. git push -u origin main。远程没有 main，就新建它。-u 让本地 main 跟踪 origin/main。以后直接 git push 就行。

学生提问：push 只发送那一个提交吗？（视频 1:05:46）

bash · 本机实测（补充，接第 7 节 revert 的例子）

$ git diff HEAD~2 --stat   # 和两步前比：什么都不输出
$ git rev-parse HEAD^{tree} HEAD~2^{tree}   # 原因：两个快照的 tree 哈希一样
b32d974f6ffb790006046a5147487d17bc41ba1d

  • git diff HEAD~ 和上一个提交比。也可以比两个名字，或只看一个文件（1:07:32）。
  • git log -p 给每个提交附上改动。可以一路往下翻（1:07:32）。
  • Git 面向用户的高层命令叫 porcelain，意思是“瓷器”。它们都建在这一讲的数据模型之上。两小时讲不完它们。但基础懂了，进阶内容很好学（1:08:07）。
补充（非视频内容）：那磁盘不会爆吗

逻辑上存快照，不等于物理上每次复制整个目录。没变的文件是同一个 blob，直接共享。第 6 节演示第 2 幕里，改一个文件只新增 4 个对象。

另外，git gc 会把对象打包成 packfile。包里会对相似的对象做增量压缩。但这只是存储优化，数据模型仍然是快照。

有人以为 revert 会把那次提交从历史里删掉。其实它追加了一个新提交。新快照恰好和两步前一样。上面 git diff HEAD~2 为空，就是这个原因。

撤销有四招，分享过的历史只用 revert 1:08:07

每种撤销都能对应回数据模型。要么新建提交再挪引用。要么拿一处的内容，覆盖另一处。

bash · 本机实测（补充，身份和时间按练习页固定，节选）
$ git log --oneline -1                      # amend 之前
13341bc initial commit
$ git commit -q --amend -m "first commit"   # 新建一个提交顶替它
$ git log --oneline -1                      # 哈希变了，旧的还在 reflog 里
5ad3af1 first commit
$ echo india >> nato.txt; git add nato.txt; git status --short
M  nato.txt
$ git reset -q nato.txt; git status --short   # 移出暂存区，工作区的改动还在
 M nato.txt

打个比方amend 像重新打印最后一页，把旧的那页换掉。revert 像在本子末尾写一行“作废上一条”。前者换掉了一页，后者只往后加。

撤销（讲义）作用对数据模型做了什么（补充）

$ git bisect start HEAD HEAD~15     # 先说好坏：HEAD 坏，HEAD~15 好
Bisecting: 7 revisions left to test after this (roughly 3 steps)
[6b417f4f142162f71857d8ac44f1a9729ca015e4] v8: feature 8
$ git bisect run bash test_add.sh   # 自动跑测试：退出码 0 算好，1 算坏
running 'bash' 'test_add.sh'
# ……中间又测了 3 次，这里省略
78824cac241795729e846fa53e1abbb36f5eef32 is the first 'bad' commit

为什么会在这里踩坑

测试脚本的退出码要守规矩。0 表示好，125 表示跳过。1 到 127 里的其他值都算坏。脚本因为缺环境而失败，bisect 也会当成坏。结果就指错了提交。

开头提到的“自动二分查找”，就是 git bisect。下面的演示在 16 个提交的历史上，真跑了 git bisect run：

一页带走：仓库就是对象加引用 1:08:58

把本讲浓缩成几行命令。每行的注释就是结论和考点。

bash · 本讲速查（注释即考点）
git cat-file -p HEAD     # commit 里只有 tree、parent、作者和说明，不存 diff
git hash-object f.txt    # 内容一样，blob 哈希就一样，和文件名无关
git commit               # 两台电脑提交同一份文件：blob 相同，commit 不同（时间和作者不同）
git status --short       # MM：只有左边那个 M 会进这次提交
git branch -d anish      # 只删名字，已合并的提交还能从 master 走到
git merge sweet          # 两边改了同一行才冲突，合并提交有两个 parent
git rebase master        # 重放出新提交：parent 变了，后面每个哈希都跟着变
git checkout 6f7b00b     # 游离 HEAD：这时的提交没有分支跟着
git reflog               # 引用去过哪都记着，删错分支从这里找回
git fetch                # 只更新 origin/master，本地分支不动
git revert HEAD          # 已分享的历史别改写，追加一个反向提交
  • blob 是文件，tree 是目录，commit 是快照加 parent 加元数据。
  • 三者都是对象，按内容的 SHA-1 寻址，互相用哈希指向。
  • 对象不可变，只能追加。引用是可变的名字，比如分支和 HEAD。仓库就是对象加引用。
  • 暂存区决定下一次提交里有什么。
  • 提交时，只有 HEAD 附着的分支前进。merge 生成有两个 parent 的提交。
  • 游离 HEAD 下的提交没有分支跟着。reflog 记着引用的历史，走不到的对象最终被回收。
  • remote 就是另一个仓库。push 送出，fetch 取回不动本地，pull 等于 fetch 加 merge。
  • 改写历史就是新建提交再挪引用。已分享的历史别改写，用 revert。
