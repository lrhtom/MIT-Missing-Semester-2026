本讲结论

工程师有一半时间在和人打交道。注释、README 和提交信息，都是写给未来读者的。它们要记为什么，不只记“是什么”。提 issue、提 PR、做评审、向人提问，都要尊重对方的时间。用了 AI，就要说出来。

这一讲不写代码，也不上白板。讲的是怎么和人协作。一类是写给后来者看的文字。一类是和别人一来一回的交流。

打个比方代码像一台机器，沟通像它的说明书。机器再好，说明书没人看得懂，就没人敢接手修。

他估计，做个好工程师，大约 50% 靠写好代码和系统。另外 50% 靠和人沟通（1:16）。

注释写代码里看不出的“为什么” 1:54

单向沟通是写给以后某个工程师看的。最主要的载体是代码注释。注释该写的，是读代码看不出来的东西。

python · 最小例子（示意）
CHUNK_SIZE = 1464   # 坏：把代码念了一遍，读者早就知道

# 好：交代这个数从哪来
# 1492 (PPPoE MTU) - 20 (IPv4 头) - 8 (UDP 头) = 1464
CHUNK_SIZE = 1464

打个比方注释像菜谱旁边的批注。“放两勺盐”菜谱上已经写了。值钱的批注是“别换成酱油，会发苦”。

单向沟通没有对话。读者可能很久以后才读到，那时你不在场。这个读者也可能是半年后的你自己（2:27）。

讲师见过最多的注释，是解释代码做了什么。这也是最没用的。代码就在那儿，读一遍就知道（2:58）。值得写进注释的，是代码里不容易看出来的东西。讲义列了七类，几乎总是值得写：

类型写什么反例 → 正例（讲义的例子）
TODO标出没做完的地方。写清缺什么，为什么推迟TODO: optimize → TODO: this O(n²) loop is fine for n<100, but will need indexing if we scale
引用代码来自论文、别处的代码或某份文档时，贴上链接。用永久链接，并注明和原文的差异视频 3:29 的例子。排序函数里有串怪代码。配上出处，读者就懂了
正确性论证不简单的代码为什么能算对。代码给出步骤，注释解释步骤为什么成立讲义没给例子
来之不易的教训花了 30 分钟以上才调通，修法又不直观的地方“过去的你没意识到需要它，未来的读者也不会”
常量的来历魔法数字是随便选的？测出来的？还是正确性要求的？“为什么是 1492？为什么是 16 位？”哪怕写“随意选的”也有信息量
承重的选择正确性依赖一个看着不起眼的实现细节“必须是 BTreeSet，因为下面依赖迭代顺序”
“为什么不”故意不用显而易见的做法时，写明原因。不然有人会“修”回去，然后弄坏视频 5:08：明明是个 map，却没用标准库的 HashMap

讲师最喜欢“为什么不”这类注释（4:32）。比如你花了两小时，才发现标准库的 map 在这里不行。于是换了别的结构。你不写下来，就会有个聪明的后来者把它改回标准库。然后把你踩过的坑再踩一遍（5:42）。

chunker.py 节选（练习 2 的示例仓库，中文注释是笔记加的）
# 1492 (PPPoE MTU) - 20 (IPv4 header) - 8 (UDP header).
# Ethernet allows 1500, but on PPPoE (DSL) links 1472-byte chunks got fragmented.
CHUNK_SIZE = 1464          # 上面两行英文注释：常量的来历

def retransmit(pending: list[bytes], send) -> None:
    # A list, not a set: packets must be resent in their original send order.
    for packet in pending[:MAX_IN_FLIGHT]:      # 上面那行：承重的选择，也是 why-not
        send(packet)

真实项目里的好注释长什么样？练习 1 在本机装的 CPython 标准库源码里真跑了 grep。每一类都找到了实例。

比如 heapq.py 里有一段 why-not 注释。它说，我们本可以提前跳出循环。但这不是好主意，尽管很多书都这么写。random.py 里还有一句“原论文漏掉了对 log(v) 的调用”。这就是在注明和参考文献的差异。

也可以记在 issue 跟踪器里。但 TODO 写在代码旁边更好找。用第 1 讲的 grep 一搜就有（3:29）。

README 按漏斗写，先说是什么，最后才说怎么装 5:42

README 通常是别人接触你项目的第一站。它要像漏斗。顶上让人几秒内判断“是不是我要的”。往下再一层层加深。

markdown · 最小例子（示意）
# mytool                       <!-- 第 1 问：这是什么，一句话说完 -->
Turn a CSV into a chart.       <!-- 第 2 问：凭什么值得你关心 -->
    mytool plot data.csv       <!-- 第 3 问：先给用法，让人看到效果 -->
    pip install mytool         <!-- 第 4 问：决定要用了，再看怎么装 -->

打个比方README 像商店橱窗。路人先看招牌和样品，觉得有意思才进门。你不能让他在门口先填会员表。

README 后来成了什么都往里放的大杂烩。有的又长又没用，有的很短却正好够用（6:15）。讲师建议按顺序回答四个问题：

  • 顺序很重要：很多项目一上来就给安装步骤（7:24）。可读者还没决定要不要用。讲义说要先展示用法。人们想先看到能得到什么，再花力气安装。
  • 保持简洁：README 是拿来快速翻的参考。其他内容放到别的文件里。
  • CONTRIBUTING.md（8:00）：写怎么报 bug、怎么提 PR、怎么测试。还有项目里不常见的约定。README 写给用户，CONTRIBUTING 写给协作者。

提交信息记“为什么”，改了什么 diff 里都有 8:34

提交信息很容易只写“改了什么”。可改了什么，看 diff 就知道。读者想知道的是为什么改、为什么这样改。

bash · 最小例子（示意）
git commit -m "fix"            # 坏：blame 追到这里，线索就断了
git commit -m "Use 1464-byte chunks so packets fit PPPoE links"   # 好：标题带着原因
git blame -L 5,5 chunker.py    # 第 5 行最后是哪次提交改的
git log -S'1464' --oneline     # 1464 这个数是哪次提交加进来的

打个比方提交信息像病历。化验单上的数字谁都能看，那就是 diff。医生写的“为什么开这个药”，换个医生才接得上手。

第 5 讲讲了 Git 的命令。这里讲 Git 卫生，也就是和别人协作时怎么用好它。提交信息连起来，就是代码库的变迁史。它记的是代码为什么变成这样（9:09）。

git blame 文件 给每一行标出最后改它的提交。你可以去看那次提交的信息，再一路往前追。但这类工具有个前提。提交信息得写清为什么（9:43）。

正文要回答四个问题 9:43

标题一行说清改了什么。正文回答下面四个问题。没有的项可以省。

什么问题逼你改？

为什么非改不可。

考虑过哪些别的办法？

为什么没用别的办法。修 off-by-one 这种没有备选的，可以省略（10:14）。

有什么取舍和影响？

优化常常是常见情况变快，少数情况变慢。运行更快但编译更慢，也值得写。C、Rust 这类有单独构建步骤的语言就常这样（10:49）。

有什么出人意料的地方？

看 diff 看不出的后果。评审者可能正好不同意这个取舍（11:25）。

Their PPPoE links have an MTU of 1492 bytes, so every 1500-byte IP

Solution: size chunks for the smaller MTU (1492 - 20 - 8 = 1464) and

赶时间时，大家都爱写 fix 和 update。当时觉得自己记得住。可 blame 追过来的，往往是几个月后的你。那时 diff 只告诉你 64 改成了 16。为什么改，没人知道。

一次提交只做一件事，用 git add -p 拆开 14:50

一周没提交，最后 git add . 一把梭。提交里就混满了不相关的改动。git add -p 按块逐个问你，能把它们拆成几个独立的提交。

bash · 最小例子（示意）
git add -p                   # 逐块问你：这块要不要放进下一次提交
  y                          # 要：这块是新功能
  n                          # 不要：这块只是格式化，留到下一次
git commit -m 'Add mode()'   # 这次提交只讲一件事

打个比方git add -p 像收拾行李时一件件过手。这件放进今天的箱子，那件留到明天。最后每个箱子只装一类东西。

最典型的是顺手跑了格式化器。diff 很大，大部分只是格式变化。只有少数是语义变化（15:26）。

逻辑上独立的部分，应该拆成不同的提交。git add -p 是 patch 模式。它把 diff 切成块（hunk），逐块问你。这块要不要放进下一次提交？答 y 或 n 就行。

补充（非视频内容）

这里用 printf 'n\ny\n' | 代替手敲 n 和 y，只是为了能自动真跑。平时直接在终端里回答就行。输出里的提示没换行，是因为输入来自管道，不是终端。

  • 拆开的提交可以分成多个 PR（16:45）。开源项目收到混着无关改动的大 diff，会让你回去重整。拆开后，维护者能先合并没争议的部分。有争议的慢慢谈。你的改动反而进得更快。

写太多等于没写，读者过了临界点就不读了 17:53

认真写注释、提交信息和 README 之后，有个危险。钟摆会摆过头，写得太多。

提交信息 · 最小例子（示意）

# 刚好：标题说 what，正文只补 diff 里看不到的 why
Limit in-flight packets to 16 to match the gateway buffer

打个比方文字像菜的分量。一碟刚好吃完。端上一大盆，客人看一眼就饱了，一口都不想动。

读者的反应大致是这样。没有文字，就没得读。文字不多，会读完。超过某个临界点，就一个字都不读了。或者只读第一段（18:27）。

讲师建议

写之前先问自己：如果我是读者，会读吗？用 LLM 写东西时尤其要注意。它很擅长生成大量文字。你通常得明确要求“简洁的摘要，不要长篇大论”。讲义的说法是，只解释“为什么”。“怎么做”相信读者自己想得出。

为什么会在这里踩坑

用 LLM 写 PR 描述最容易写长。它会把每个文件改了什么都复述一遍。维护者翻两屏还没看到重点，干脆不看了。真正要紧的那句 why，反而埋在了中间。

bisect 二分找到坏提交，信息写得烂照样白找 19:05

git bisect 在好版本和坏版本之间二分查找。几步就能找出引入 bug 的提交。可那个提交要是没写为什么，你还得从头调试。

bash · 最小例子（示意）
git bisect start HEAD v1.0     # 告诉它：HEAD 是坏的，v1.0 是好的
git bisect run sh test.sh      # 测试脚本退出码 0 算好，非 0 算坏
git bisect reset               # 找完了，回到原来的分支
# 16 个提交最多测 4 次。可找到的提交只写着 update，还是白找

打个比方bisect 像查水管哪段漏水。从中间截断看一眼，漏的那半再从中间截。16 段水管查 4 次就够。可找到那段后，图纸上没写它为什么这么接。你还是不知道怎么修。

你升级了某个软件，发现一个以前没有的 bug。告诉 bisect 哪个版本好、哪个版本坏。它就检出中间的提交让你测。你回答好或坏，范围减半，直到只剩一个（19:40）。

打个比方维护者像小诊所里唯一的医生，门口排着几百个病人。你进门就说清症状、病史和用药，他几分钟就能开方。你只说“我不舒服”，他得一样样问。

为什么要“高信噪比”

一半是尊重对方的时间，一半是为了自己。格式糟糕的 issue 或 PR，维护者可能直接关掉。也可能不理，或者放一年再说。大家都知道，“以后有空”永远不会来（22:13）。

提 PR 前先读规矩、看许可证，一个 PR 只做一件事 31:36

PR 就是带着几个提交去问维护者：能不能并进你的项目？所以先照项目的规矩来，再把为什么写清楚。

bash · 最小例子（示意）
cat CONTRIBUTING.md          # 先读规矩：怎么测试，提交信息怎么写
cat LICENSE                  # 合并后，你的代码按这个许可证发布
git switch -c fix-title      # 一个分支只做一件事
git request-pull main ../fork.git fix-title   # 生成一封“带附件的邮件”

打个比方提 PR 像往别人家里送一件家具。先问清他家门多宽，东西归谁，这就是 CONTRIBUTING 和许可证。一次只送一件，再附张纸条，说明为什么适合他家。

视频 29:27 有学生问“PR 是什么”。讲师说，别人有一个仓库。你带着一个或一组 git 提交去问他。能不能把这个并进你的项目？

  1. 读 CONTRIBUTING.md，照着做。讲义建议从小处开始。修个错别字、改改文档，就是熟悉项目流程的好起点。这样不用一边学流程，一边在内容上来回拉扯。
  2. 看许可证（32:10）。改动合并后，会按项目的许可证发布，比如 GPL。copyleft 许可证要求衍生作品也开源。你如果是公司员工，还要看公司的规定。上班时间写的代码，不一定能贡献出去（32:46）。讲义推荐 choosealicense.com。
  3. 隔离改动：一个 PR 只放你真想被接受的改动。每个 PR 都能单独评审。有时几处看似无关的改动，得一起才能实现一个功能。那就放进同一个 PR，但要保持提交整洁。再告诉评审者“请逐个提交地看”。维护者很感激这种评审指引（33:24）。
  4. 写清为什么（34:29）。PR 描述像一封邮件，附件是你的 git 提交。要说明项目为什么该接受这个功能、修复或文档改动。主动指出需要特别留意的地方。看 CONTRIBUTING.md 的要求，可能还要写取舍和测试方法。
合并 PR，维护者就接下了长期责任（35:01）

你加了一千行，维护者就要永远维护这一千行。你却可以拿到功能就走。所以他们不光要考虑想不想要这个功能。还要考虑这种实现自己能不能长期扛。会不会和以后的功能冲突。

好意的改动也可能被拒。可能是方向不合，也可能是加了不想要的复杂度。还可能是需求没说清。讲义说，证明它值得维护成本，是贡献者的责任。

第一次提 PR，很多人把格式、改名和新功能一起塞进去。维护者没法只收其中一部分，只好让你拆开重来。还有人不看许可证，就贡献了公司不让外传的代码。

另起炉灶的 fork 很贵，只能当最后手段 35:43

PR 被拒后，你可以把项目复制一份。作为独立项目长期维护。但这很昂贵，需要很好的理由。

最小例子（示意）
# PR 被拒了，fork 之前先问自己两个问题
# 1. 我要的和原项目的目标范围，本质上不同吗？
# 2. 我愿意一个人长期维护、同步上游、处理 issue 吗？
# 两个都是“是”，才 fork，并注明原项目。只是“我的功能没进”，就别 fork

打个比方fork 像和合伙人闹翻后自己另开一家店。招牌、进货、账本都得自己扛。原来那家的改进，你这边也用不上。

先分清两个“fork”（补充）

GitHub 上提 PR 的常规流程里，也有一步叫 fork。它在你的账号下复制一份仓库，改完再向原仓库提 PR。那只是工作副本。讲师这里说的 fork 是另一回事。它是把项目复制一份，换个名字。然后作为独立项目长期维护。

维护者可能会说“超出范围”或“太多了”。也可能说“我不想要这个功能”。这时你可以另起炉灶（36:14）。但这很昂贵。两个项目各有一个维护者，代码却大量重叠。维护者的时间被分摊了。一边的改进，另一边享受不到。

所以它被视为最后手段，需要很好的理由（36:51）。讲义也建议优先贡献给上游。确实要 fork，而且许可证允许，就注明原项目。

问答：有人会主动申请当某部分的维护者吗？（37:59）

看项目规模。Linux 内核有很多子系统，各有维护者。带来一整个新子系统的人，几乎默认要负责维护它。小项目就少见了。2000 行的项目里，说“我来维护这 50 行”没有意义。改动会扩散到整个代码库，多个维护者还有协调成本。

不过，持续贡献正是成为维护者的路。维护者往往就是贡献最多的人。某天原维护者可能会问你，愿不愿意接手（39:43）。

为什么会在这里踩坑

PR 被拒的那一刻，最容易冲动 fork。可几个月后，上游又修了一堆 bug。你得一个个手动合过来。合不动了，你的 fork 就成了没人维护的旧版本。

AI 写的 PR 可以交，但你得答得上为什么 40:18

LLM 生成的 PR 大多没用，因为提交者没当好过滤器。用 AI 可以，前提是你理解每处改动，并为它负责。

最小例子（示意）
# 维护者在 PR 下面问：为什么用 removesuffix，不用 rsplit？
# 答不上来：说明改动不是你做的，PR 多半会被关
# 答得上来：AI 只是帮你打字，你仍然为它负责

打个比方AI 像一个手很快的实习生。他写的东西可以交上去，但签字的是你。客户问起来你答不上，丢的是你的信用。

现在开源项目里有大量 LLM 生成的 PR。少数有用，多数没用。提交者只说一句“实现这个功能，提交并开 PR”。结果往往不够精简，夹带无关改动，why 也写得不好。

维护者问“为什么这样改”，提交者答不上来。因为改动不是他做的（40:51）。所以维护者普遍怀疑 AI 写的 PR。

讲师与讲义的态度

不是说不能用 LLM。它在实现改动、写提交信息、写 PR 描述上都很有用。它甚至能帮你处理评审意见。但你必须参与其中。你得理解为什么要改，为什么这样改。

如果你只是描述了 bug，按下回车，再把结果贴进 PR。那维护者自己也能做。他们没做，多半是有原因的（41:27 到 42:02）。

讲义说，用 AI 找问题、写修复都可以。前提是你仍然做足功课，把它打磨成值得合并的贡献。别把这份活转嫁给本就超负荷的维护者。

为什么会在这里踩坑

让 AI 改一个 bug，它可能顺手改了别处。你没细看就提交，diff 里就混进一堆无关改动。维护者一问“这几行为什么改”，你也答不上来。

评审针对代码不针对人，还要给能动手的建议 42:42

评审是关于代码的一场异步对话。好意见针对代码，能直接动手改。它用提问的口气，讲清原因，还分清哪些必须改。

评审意见 · 最小例子（讲义的例子，注释是笔记加的）
You wrote confusing code.            # 坏：评判的是人
Don't use globals here.              # 坏：只说不要，对方不知道怎么改
Can you replace these globals with a config dataclass,
so that tests can run in parallel?   # 好：提问、给替代方案、讲原因
nit: maybe call this retry_timeout_s # nit 开头：可改可不改（这一条是示意）

打个比方评审像两个厨师试同一锅汤。说“你不会做饭”没用。说“盐是不是少了？客人口味偏重”，对方马上就能改。

评审常被想象成“新人提 PR，前辈挑错，直到 PR 变好”。但那不是评审的本意。评审只是一场关于代码的异步对话。有人提出改动，另一个人思考它。两人像头脑风暴一样，讨论好在哪、不好在哪。

正因为有“前辈挑错”的心态，评审的话常像在评判人。要记住，评审针对的是代码（43:17 到 43:51）。看它在这个项目里、为这个目的、在此时是否合理。

你被要求评审的时间，会比想象中早得多。哪怕只是大学的小组项目，也至少应该互相评审。评审还是最快的学习方式之一。你能看到别人的做法，学到模式和惯用法。看到别人犯的错，以后自己就不犯。

新鲜的眼光还能发现老手忽略的问题。讲义还说，你的疑问往往暴露出一些假设。它们该写成文档，或者该简化掉。

  • 为什么别留太多：对方会累，会拖延。还分不清哪条最要紧。改了一处，别处的意见可能就失效了。留一百条，可能只有五十条值得处理。同一种命名问题，在第一处说一次就够了。比如“本仓库用这种命名，请全局统一”（48:00）。
  • 为什么要夸：想象结对编程时，对方一开口就说你错了。评审也一样。一句肯定不用对方做任何事，点一下 resolve 就行。但它让评审更平衡，对方也更愿意照你的意见改。在开源项目里，这还决定他们会不会再来。见视频 46:47 和 50:50。
AI 评审不能代替人（51:21）

现在很多人用 AI 做评审，效果可以很好。但它做的基本是“零上下文”评审，只看描述和 diff。评审里真正要紧的意见，往往不在 diff 里。这个改动适不适合整个代码库和产品方向？有没有破坏向后兼容，而项目还没准备发破坏性版本？这些 AI 不知道。

所以 AI 满意，不代表维护者满意（52:30）。讲义说，AI 适合做第一轮，不能代替用心的人工评审。

学生追问，给它更多上下文行不行？讲师认为在一定程度上可以，但会碰到边界。比如你可以给它讲破坏性变更。它能用英语复述一遍。可它不一定懂这个项目的破坏性变更策略。他不认为给够上下文，就能得到完美评审（53:06）。

评审别人时，很容易一口气留几十条“这里不对”。写的人觉得自己很认真。收到的人只觉得被否定，还分不清哪条最要紧。结果改得更慢，下次也不想找你评审了。

先说你懂多少，再问具体的是非题 54:14

问好问题，能让对方一下子找到你的知识缺口。先做功课，说出你的理解，问具体的是非题。没听懂就接着追问。

提问 · 最小例子（讲义的例子，注释是笔记加的）
How do SQL joins work?
# 太泛：对方只能从头讲起，多半讲到你不关心的地方
Does a LEFT JOIN include rows where the right table has no match?
# 具体的是非题：对方一个字就能答，还能顺手纠正你的误解

打个比方提问像看病。你说“我哪里都不舒服”，医生只能从头查。你说“右膝上楼时疼，没摔过”。医生马上就知道往哪查。

工程师不写代码的时间里，很大一部分在提问或回答。对象有导师、老师、助教，还有做完了实验的同学。讲师最希望大家先学会问好问题，这是第一阶段。回答好问题是第二阶段（54:47）。

讲义推荐了 Julia Evans 的两篇文章。一篇是 How to ask good questions，另一篇是 How to get useful answers to your questions。

  • 说出理解（55:22）。对方就知道哪些不用重复，能直接找到你的知识缺口。
  • 是非题：有点反直觉。可一串是非题能很快确认，你哪里对、哪里错。这样也不会扯得太远。问题要具体。“SQL join 怎么工作？”太泛。“LEFT JOIN 会包含右表没有匹配的行吗？”就能回答（讲义例子）。
  • 承认不懂（55:58）。装懂只会让对方没法判断你的水平。反过来，被问到不会的，就说“我不知道”。讲义说，后面还可以接一句。比如“但我觉得……”，或者“我可以去查”。
  • 别接受不完整的答案（56:36）。很多人没听懂，说声“好的谢谢”就走了。那等于没学到。要问到懂为止，或者问到明显待太久了。
  • 先做功课（57:17）：同事之间随口一问没关系。但什么都没查就问，对方会有点烦。
对 LLM 同样适用（57:58）

告诉它你知道什么，问具体的问题。别因为它给了答案就停下，用是非题接着追问。在 Stack Overflow 或论坛上也这样问。后来搜到这个帖子的人也会受益，这叫水涨船高。

用了 AI 就说出来，还要说清用在哪部分 58:33

AI 用得越来越多，相关规范却还没定型。讲师给了几条底线。用了就披露，并说清用在哪。守团队的规矩，考试面试别偷用。

PR 描述 · 最小例子（示意）
Tests in test_report.py were generated by an LLM and reviewed by me.
The fix in report.py is hand-written.
# 说清哪部分用了 AI，审查者才知道该细看哪里
# 只写一句“用了 AI”不够，对方不知道该细看哪部分

打个比方披露 AI 像论文里写清分工。谁做了实验，谁写了初稿，都写明白。审稿人才知道该在哪里多看两眼。

AI 在软件工程乃至整个社会里，用得越来越多。第 7 讲讲了战术层面的事。这里讲“软”的部分：

  • 用了就披露（59:05）：这不是羞耻的事。目的是设定预期，让作品得到合适程度的审查。有些代码你没细读、没完全弄懂。别人得知道，要多看几眼（59:43）。讲师自己就在用 LLM 写一个大项目，毫不避讳。但交付时他会说明：“这些代码我没全读过，是个起点。”
  • 说清用在哪部分（1:00:17）。只说“全是 vibe coding 出来的”，信息太少。换个说法就清楚了。“备份工具是我写的，前端样式用 LLM 做。”又比如“测试是 LLM 生成的，实现是我写的”。这种区分对审查者很有用。讲义也坦白，它的部分内容用了 LLM。包括校对、头脑风暴，以及代码片段和练习的初稿。
  • 遵守团队和项目的规范（1:00:53）。有些规定出于法律原因。比如健康、金融数据不能离开公司。智能体却可能把它们传到云端（1:01:56）。那里你管不了。有些规定只是尊重项目开发者的意愿。公开说明你的用法，能避免代价高昂的错误。
  • 学习时要有意取舍（1:01:56 到 1:02:33）。用 AI，你会学得少一些。有时这没关系，但应该是有意的选择。讲义说，学习时让 AI 替你快速拿答案，恰恰适得其反。你学到的多半是提示词技巧，不是任务本身。
  • 考试与面试（1:03:07）。这些场合本来就是评估你的能力。少数公司允许面试时用 AI，前提是让他们看你怎么用。拿不准就问。明确禁止外部工具时，就别用。讲义说，偷偷用“一定会反噬你”。

一页带走：写给人看的东西，都要写清为什么 1:04:18

把本讲浓缩成几行。每行的注释就是结论和考点。

本讲速查（注释即考点）
CHUNK_SIZE = 1464  # 1492-20-8     # 注释写代码里看不出的 why。只复述代码的注释最没用
git commit -m "fix"                 # 坏：blame 追到这里就断了。复杂改动按 P、S、I 三段写
"给这个 diff 写提交信息"            # LLM 只看得到 what。在同一会话里让它提交，或让它缺什么就问你
git add -p                          # 一次提交只做一件事，格式化和新功能分开提交
git log -S'1464' --oneline          # 查某个字符串是哪次提交加进来的
git bisect run sh test.sh           # 16 个提交最多测 4 次。信息写得烂，找到了也帮助不大
"analytics.csv".rstrip(".csv")      # 最小复现：用户远多于维护者，缩减的活由你来干
Can you replace these globals ...?  # 好评审：针对代码、用提问、给替代方案、讲原因
nit: ...                            # nit 开头表示不阻塞，作者先处理必须改的
Tests were generated by an LLM.     # 披露要说清用在哪部分，再守住团队和考试的规矩
  • 注释、README 和提交信息，是写给未来读者的单向沟通。要记 why。what 读代码、看 diff 就知道，why 会随时间流失。
  • 值得写的注释有七类。带上下文的 TODO、引用、正确性论证、教训。还有常量来历、承重选择和 why-not。
  • README 按漏斗写：是什么，为什么关心，怎么用，怎么装。CONTRIBUTING.md 写给协作者。
  • 复杂提交按 Problem、Solution、Implications 写。用 git add -p 拆成逻辑独立的提交。git blame、log -S 和 bisect 好不好用，全看提交信息。
  • 维护者远少于用户。bug 报告写清环境、期望和实际、步骤、试过什么。最好附上最小复现。先搜重复，不发 +1，礼貌跟进，漏洞私下报。
  • PR 先读 CONTRIBUTING，看许可证，只做一件事，写清为什么。被拒时，fork 是最后手段。用 AI 可以，但你得理解它，并为它负责。
  • 评审要针对代码、能动手、用提问、讲原因。分清阻塞和 nit，肯定优点，别留太多。AI 评审只能做第一轮。
  • 提问前先做功课。说出理解，问具体的是非题，承认不懂，追问到懂。用了 AI 就披露，并遵守规则。
