本讲结论

代码要在别人的机器上跑起来，得说清两件事。一是交出去的东西是什么，叫构件（artifact）。二是它对周围环境做了哪些假设。依赖、环境、版本和锁文件，都在回答这两个问题。容器、配置、编排和发布也一样。

你的代码隐含地依赖着一整套东西。有语言运行时、第三方库和操作系统的特性。甚至还有硬件。做 Python 库、命令行工具或 Web 服务，依赖各不相同。部署步骤也不一样。

dependencies = ["typer>=0.9"]

[build-system]
requires = ["setuptools>=61.0"]
build-backend = "setuptools.build_meta"
greeting.py（讲义原文）
import typer


def greet(name: str) -> None:
    print(f"Hello, {name}!")


def cli() -> None:
    typer.run(greet)


if __name__ == "__main__":
    cli()

[project.scripts]安装时额外生成一个 greet 命令。它调用 greeting 模块里的 cli 函数
[build-system]用什么构建系统产出构件

库写宽范围，应用把版本全钉死 25:21

库要和用户的其他依赖装在一起，约束越宽越好装。应用是最终产品，钉死版本才能人人一样。

toml · 写法示意
# 库的 pyproject.toml：给用户留余地
dependencies = ["requests>=2.0,<3"]   # 只卡主版本
# 应用的依赖：全部钉死
dependencies = ["requests==2.32.3"]    # 只能是这一个，测过的就是它

打个比方库像通用插头，要尽量适配各种插座。应用像定制家具，尺寸按你家量好，一厘米都不改。

版本写死，大家装到的都一样，不会出问题。只写范围，就是希望它和这些版本都兼容。怎么选，要看你在做什么：

库（library）写宽范围

库会被别的代码导入，和用户的其他依赖装在一起。约束写得太死，用户就容易冲突，装不上。视频里看了 requests 的依赖（25:54）。3 个都是宽范围，基本只卡主版本。

应用和服务（application）全部钉死

应用是最终消费者。它通过界面或 API 提供功能，不被别人 import。钉死精确版本，才能保证每个用户的体验可复现。ripgrep 的依赖没有一个范围（26:36）。全是测过的确切版本。

钉住（pinning）一个库，就是写确切版本，不写范围。比如写 requests==2.32.3，不写 requests>=2.0。

为什么会在这里踩坑

把应用的习惯带到库里，最容易出事。假设你的库钉死了 numpy 1.x 的某个版本。用户项目里，别的包却要 numpy 2。两个约束没有交集，用户就装不上你的库。这就是第 4 节的依赖地狱。

锁文件把整棵依赖树的版本和哈希都记下来 27:24

语言包管理器管不到的，交给 Nix 这类工具 29:58

pip 只管 Python 包。编译器、CUDA、OpenSSL 这类系统级依赖，得用管得更广的工具。

bash · 写法示意
pip install cupy-cuda12x      # pip 只管 Python 这一层
nvcc --version                # CUDA 工具包得先在系统里装好，pip 管不着
nix-shell -p python312 gcc    # Nix：连编译器和系统库一起钉死

打个比方pip 像小区物业，只管楼里的事，水厂和电网它管不了。Nix 像连水电一起承包的开发商。从地基到灯泡，全记在账上。

只要离开编程语言自己的环境，就得用管得更广的工具。讲师举了个例子。你以为 Python 3.12 就是 3.12。可构建 Python 要用 C 编译器，编译器的版本也会不同。Nix 这类包管理器能管操作系统里的所有包。它用可复现的方式，管住每一处可变的地方。甚至有个操作系统 NixOS 就基于这个理念。它用版本控制的配置文件，管理整台电脑（讲义）。代价是拿灵活性换来了复杂度。

讲义推荐 · Nix / Bazel

Nix 和 Bazel 提供密闭（hermetic）构建。编译器、系统库，连构建环境本身都钉死。而且按内容寻址。这样无论何时何地构建，结果都逐位相同。越来越多项目还用 nix flakes，按项目管理系统级的库和程序。

CuPy 离不开 CUDA，这种依赖写不进 pip 30:40

CuPy 是调用 NVIDIA CUDA 指令的 Python 包装层。它的安装说明不是一句 pip install。而是先装好兼容的 CUDA 工具包。这种依赖根本写不进 Python 的打包信息。看它发布的 wheel，不光分操作系统和 CPU 架构。还要按 CUDA 运行时版本和 Python 版本分别编译。你得自己挑对文件（31:54）。还有 GPU 驱动、特定版本的编译器、OpenSSL 这类共享库。它们至今常常要在系统层面安装。

升级有风险，不升级也有风险（讲义）

新版本会有意无意地带来破坏。旧版本又会随时间暴露安全漏洞。这对矛盾永远存在。讲义的建议有两条。一是用持续集成（第 9 讲）拿新版本依赖跑测试。二是用 Dependabot 这类自动化工具发现依赖的新版本。即便这样，开发和生产环境的差异，仍会让升级出问题。所以要有回滚（rollback）预案。撤销升级，重新部署已知良好的版本。

为什么会在这里踩坑

pip 装 CuPy 显示成功，一跑起来却报 CUDA 相关的错。pip 的成功只说明 Python 这一层装好了。系统层的 CUDA 和驱动，它根本不检查。遇到这类报错，先查系统依赖，别反复重装 Python 包。

容器共享宿主内核，所以比虚拟机轻 33:02

虚拟机连操作系统一起交付，开销大。容器复用宿主的内核，只隔离应用这一层，轻得多。

bash · 写法示意（Linux 宿主，本机没有 Docker）

docker run --rm python:3.12 uname -r     # 容器里看到的是同一个内核：内核是共享的

打个比方虚拟机像在你家院子里再盖一栋小房子，水电全套自带。容器像在你家隔出一个房间。墙是自己的，水电总闸还是你家那个。

CUDA 这类依赖，最好别让用户自己凑。那就把用户需要的一切都随构件交付。这几乎就是交付整台电脑。

虚拟机（VM）

电脑里运行电脑。它模拟整台计算机，自带一套独立的操作系统。隔离得很彻底。Windows 里能跑 Linux，反过来也行。给别人一个虚拟机镜像，所有依赖都在里面。缺点是开销大。跑一个应用，得带一整套操作系统（33:39）。

容器（container）

应用大多只关心用户态的依赖，不需要改操作系统本身。所以容器复用宿主操作系统的核心，也就是共享内核。它只隔离应用这一层。应用连同依赖、库和文件系统，打成一个包。比 VM 轻，启动更快，运行也更高效（34:24）。

只有部分操作系统原生支持容器，比如 Linux 和 BSD。在 Windows 或 Mac 上跑容器，其实是先跑一个 Linux 虚拟机。容器跑在这台虚拟机里面。好在生产环境部署的应用基本都是 Linux，问题不大。

Dockerfile 每条指令是一层，改哪层就从哪层重建 38:15

镜像是把整个文件系统当构件交付。Dockerfile 一条指令生成一层，Docker 会缓存每一层。

Dockerfile · 最小例子（示意）

为什么会在这里踩坑

把拷源码的 COPY 写在装依赖前面，是最常见的坑。源码一改，COPY 这层就变了。它后面的装依赖层全部重建，每次都要重新下载。下一节的改进版调整了顺序。

好的 Dockerfile：镜像小、层少、版本锁死 41:25

改进版换了 slim 基础镜像，还合并了 RUN。它清掉了包管理器缓存，先装锁定的依赖再拷源码。

Dockerfile · 最小例子（示意）
FROM python:3.12-slim                  # slim 版，不带一堆用不上的东西
RUN apt-get update && apt-get install -y gcc && \
    rm -rf /var/lib/apt/lists/*        # 一条 RUN 一层：装完马上清缓存
COPY pyproject.toml uv.lock ./         # 先只拷依赖清单
RUN uv sync --locked                   # 清单不变，这层就命中缓存

打个比方搬家装车，大件先上，零碎最后放。依赖清单很少变，是大件。源码天天改，是零碎。顺序对了，每次只用重装最后那几箱。

讲义指出了第一版的问题。它用了完整版的 Python 镜像，没用 slim 版。多条分开的 RUN 产生了多余的层。没锁版本。也没清理包管理器缓存，把没用的文件也打了进去。常见的错误还有两个。一是用 root 身份运行容器。二是不小心把密钥打进镜像层。改进版是这样的：

Dockerfile（讲义原文 · 改进版）

    rm -rf /var/lib/apt/lists/*

COPY . .
RUN uv sync --locked --no-dev

  • 合并 RUN，加 --no-install-recommends，再删掉 apt 的列表缓存。讲师说，最终产品不会再装别的东西（42:00）。
  • 视频里比了两版镜像的体积。第一版接近 2 GB，优化版大约半个 GB（42:43）。

讲义：Docker 的三个局限
  • 镜像通常和平台绑定。linux/amd64 的镜像放到 linux/arm64 上，比如 Apple Silicon，只能慢速模拟运行。
  • 容器需要 Linux 内核。macOS 和 Windows 上的 Docker 其实跑着一个 Linux 虚拟机，有额外开销。
  • 容器共享宿主内核，隔离比虚拟机弱。在多租户环境里，这是安全隐患。

多服务应用的部署解决了。还剩一个问题：谁来启动它们？总不能指望机器每次重启后，有人 SSH 上去敲 docker compose up。生产环境希望服务开机自启，失败时重启。Linux 上最流行的是 systemd。在 /etc/systemd/system 下写一个声明式的单元文件，就能注册新服务。

/etc/systemd/system/myapp.service（讲义原文）
[Unit]
Description=My Application
Requires=docker.service
After=docker.service

[Service]
Type=oneshot
RemainAfterExit=yes
WorkingDirectory=/opt/myapp
ExecStart=/usr/bin/docker compose up -d
ExecStop=/usr/bin/docker compose down

[Install]
WantedBy=multi-user.target
行含义（据视频 52:51 的 TL;DR）
Requires / After=docker.service依赖 Docker。必须等 Docker 服务起来后再启动
WorkingDirectory进入这个目录执行命令
ExecStart=… up -d启动。-d（detach）让它在后台运行，不卡住命令行
ExecStop=… down有人要停止服务时执行
WantedBy=multi-user.target开机进入多用户模式时启动。讲义说，这保证系统启动时就运行

之后就用 systemctl start myapp、systemctl status myapp 和 systemctl stop myapp 管理。视频里 start 之后，看似什么都没发生。status 显示 compose up 已经执行了。现在这组服务归操作系统管，机器重启后会自动启动。再访问网页，显示已访问 4 次（53:44）。

$ uv publish --publish-url https://test.pypi.org/legacy/
Publishing greeting-0.1.0.tar.gz
Publishing greeting-0.1.0-py3-none-any.whl
$ uv pip install --index-url https://test.pypi.org/simple/ greeting

TestPyPI 是一个独立的练习用注册表。专门用来测发布流程，不会污染真正的 PyPI。视频里 greeting 这个名字已经被人占了。讲师改用 missing-semester 包演示。上传前，他把版本号比上次测试升了一个 patch（58:07）。本机没有 TestPyPI 账号，只跑了不上传的 --dry-run，见练习 5 的 ex05-a：

bash · 本机实测
$ uv publish --dry-run --trusted-publishing never --publish-url https://test.pypi.org/legacy/ dist/*
Checking 2 files against https://test.pypi.org/legacy/
Checking greeting-0.1.0-py3-none-any.whl (1.5KiB)
Uploading greeting-0.1.0-py3-none-any.whl (1.5KiB)
Checking greeting-0.1.0.tar.gz (1.0KiB)
Uploading greeting-0.1.0.tar.gz (1.0KiB)

dry-run 下会打印 Uploading，但不会真的上传。见 uv help publish 对 --dry-run 的说明。

  • 信任：用户怎么确认，下载的包真的来自你，没被篡改？注册表用校验和验证完整性。有的生态还支持包签名（讲义）。它用密码学证明作者身份。
  • 各语言的注册表：Rust 有 crates.io，JavaScript 有 npm，Ruby 有 RubyGems。容器镜像有 Docker Hub。私有或内部的包，组织会自建仓库。比如私有 PyPI 和私有镜像仓库。也可以用云厂商的托管服务。
  • Docker 镜像：只能推到你有权限的注册表（59:23）。讲师只能推以自己用户名开头的镜像。所以先按这个规则重新打标签，再 docker push。之前推过的层会被跳过。之后谁都能从 Docker Hub 拉下这个镜像。里面是完整的文件系统。
  • 问答：怎么和同学共享镜像？用镜像仓库（container registry）（1:01:47）。Docker Hub 不是唯一的，GitHub 也有。只要双方都能访问同一个仓库，就能 push 和 pull。读取私有内容要认证，证明你是你，而且你有权限。

把 Web 服务部署到互联网，还需要更多基础设施。要注册域名，配置 DNS 指向服务器。通常还要 nginx 这样的反向代理，处理 HTTPS 和路由流量。文档、静态网站这类简单场景，用 GitHub Pages 就够了。它直接从仓库免费托管（讲义，练习 6）。

为什么会在这里踩坑

同一个版本号不能重复上传。传错了想覆盖 0.1.0，注册表会拒绝。只能把版本升到 0.1.1 再传。讲师现场也是先升了 patch 才上传的。

一页带走：构件加上它对环境的假设 1:00:20

把本讲浓缩成几行命令。每行的注释就是结论和考点。

bash · 本讲速查（注释即考点）
source venv/bin/activate          # 激活就是把 venv/bin 插到 PATH 最前面
bash venv/bin/activate            # 白跑：子进程改完 PATH 就退出了，必须 source
uv pip install .                  # 按 pyproject.toml 把包装进当前环境
uv build                          # 产出 sdist 和 wheel，wheel 就是带元数据的 zip
"1.10.0" > "1.9.0"                # 当字符串比是 False，版本号要按整数逐段比
^0.2.3                            # 等于 >=0.2.3,<0.3.0，不允许升到 0.3.0
pandas~=2.1.0                     # 等于 >=2.1.0,<2.2.0，不允许 2.2.0
dependencies = ["typer>=0.9"]     # 库写范围给用户留余地，应用靠锁文件钉死
uv lock && uv sync --locked       # 不同时间解析结果不同，锁文件记下确切版本和哈希
COPY pyproject.toml uv.lock ./    # 依赖层放前面，改一行源码，这层照样命中缓存
docker run python:3.12 uname -r   # 容器共享宿主内核，所以轻。代价是隔离更弱
redis://cache:6379                # 容器里连别的服务用服务名，localhost 是自己
systemctl enable myapp            # WantedBy 要 enable 才会开机自启（补充）
  • 交付代码，就是定义构件，再说清它对环境的假设。
  • 安装器查索引、选构件、递归解析依赖，再下载安装。约束的交集为空，就是依赖地狱。用每个项目一个环境来隔离。
  • 虚拟环境只是一个目录。激活就是把它的 bin 或 Scripts 插到 PATH 最前面，必须 source。
  • pyproject.toml 描述项目。uv build 产出 sdist 和 wheel。wheel 是带元数据的 zip，文件名里的标签说明适用平台。
  • SemVer 里，PATCH 修 bug，MINOR 加功能，MAJOR 破坏兼容。版本号按整数逐段比。库写范围，应用钉死。
  • 锁文件记着整棵树的确切版本和哈希。uv sync 照着装，结果可复现。
  • VM 交付整个操作系统。容器共享内核，只隔离应用层。Dockerfile 每条指令一层，层可以缓存。
  • Compose 声明多个服务和它们的依赖顺序。配置在运行时注入，密钥不进版本控制。systemd 负责开机自启。
  • 发布到 PyPI 或 TestPyPI、GitHub、镜像仓库。用校验和与签名建立信任。
