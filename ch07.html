本讲结论

编码智能体由两部分组成。一是语言模型，它按上下文给出续写的概率。二是 harness。它在循环里调用模型，替模型读写文件、跑命令。然后把结果喂回给模型。懂了这一点，就懂了三件事。一是为什么要审批工具调用。二是为什么要管理上下文。三是为什么它会犯错。

编码智能体会自己调用工具。它读文件、改代码、跑检查，最后向你报告。你要做的，是下指令和审批。

打个比方像请了个装修师傅。他自己量尺寸、买材料、动手干。你只在他拆墙之前点个头。

第 3 讲讲了 AI 自动补全和行内对话（inline chat）。这一讲讲更强的形态：编码智能体（coding agent）。讲义的定义是这样的。它是一个对话式 AI 模型，能使用工具。工具包括读写文件、网页搜索和执行 shell 命令。它可以嵌在 IDE 里，也可以是独立的命令行或图形程序。它的自主程度很高。

dl.py（讲义原文）
from urllib.request import urlopen

def download_contents(url: str) -> str:
    with urlopen(url) as response:
        return response.read().decode('utf-8')

def extract(content: str) -> list[str]:
    import re
    pattern = r'\[.*?\]\((.*?)\)'
    return re.findall(pattern, content)

print(extract(download_contents("https://raw.githubusercontent.com/missing-semester/missing-semester/refs/heads/master/_2026/development-environment.md")))

它记得前面的对话，走偏了随时打断 8:36

智能体保留之前的对话，可以接着下指令。看它走偏了，就按 Ctrl+C 打断，补一句话纠正。

最小例子（示意）
> 把类型注解删掉               # 多轮：接着上一轮说，它知道指的是哪个文件

打个比方像带一个实习生，这是讲义给的心智模型。脏活累活他干，但需要你指路。偶尔做错了，你得纠正。

看它走偏了还不打断，最费事。等它跑完再说“别这样”，已经晚了。走错的那些步骤都留在上下文里，会接着干扰它。早打断，早纠正。

语言模型只是条件概率分布，推理就是抽样 12:33

LLM 拿到提示 x，算出各种续写 y 的概率。用它的时候，就是按概率抽一个续写出来。

python · 最小例子（示意，sample 是假想函数）
history = ["User: 1+1 等于几？"]
reply = sample(llm, history)        # 按概率抽一个续写，多半是 "2"
history += [reply, "User: 把 1 都换成 2 呢？"]
reply = sample(llm, history)        # 整段历史再发一遍，它才“记得”上文

打个比方像手机输入法的联想词。它只管猜下一个词最可能是什么，然后挑一个。它“记得”上文，只因为每次都重发了整段记录。

讲师说要讲到“刚好够用”的抽象层次。不教你自己实现，但让你明白三件事。它擅长什么，局限在哪，harness 为什么有那些功能。编码智能体大致分两部分。底层是语言模型，外面包着一层 agent harness。

LLM 是什么

把 LLM 看成一个条件概率分布 πθ(y | x)。x 是提示字符串，y 是续写字符串。使用它就是从分布里抽样：ŷ ~ πθ(· | x)。讲师说，“这就是 AI 语言模型的全部”。大量工作，都花在让这个分布有用上（13:08）。

上下文窗口

LLM 有一个固定的上下文窗口（context window）。输入串和输出串的长度都有上限（14:17）。后面讲的“上下文管理”，全都源于这一点。

那聊天应用怎么支持追问？讲师在黑板上举了个例子。用户问“1 + 1 等于几”，模型答“2”。用户再问“把 1 都换成 2 呢？”。单看这一句，没法回答。

办法是给每条消息加上轮次标记（turn marker）。每次都把整段对话历史当成新的输入 x（15:33）。然后再推理一次。讲义的说法也一样。每来一条新的用户提示，就推理一次。提示串就是完整的历史。

下面的演示分两幕。第一幕看一次推理怎么抽样。第二幕看多轮对话怎么拼接历史。

为什么会在这里踩坑

以为模型有记忆，是最常见的误解。它“记得”上一轮，只因为应用把历史又发了一遍。所以对话越长，每次推理的输入越长。最后会撞上上下文窗口。同一个问题问两次，答案也可能不同。因为每次都是抽样。

harness 在循环里调模型、跑工具、喂回结果 17:18

模型除了输出文字，还能输出“调用工具”的请求。harness 真的去执行，把结果追加进上下文，再推理一次。直到模型输出给用户的文字。

python · 最小例子（示意，简化自练习页的 mini_harness.py）
while True:
    out = llm(ctx)                 # 把整个上下文发给模型，推理一次
    if out.is_text: break          # 模型输出了文字：循环结束，控制权交还用户
    ctx += [out, run_tool(out)]    # 是工具调用：在你的机器上真的执行，结果追加回去

打个比方模型像只会写纸条的军师，自己不出门。harness 是跑腿的。军师写“去查一下 dl.py”，跑腿的去查，把结果塞回来。军师再写下一张，直到写出“汇报完毕”。

再加一个想法：对模型的输出做特殊解释。模型除了给用户写文字，还能输出“调用工具”的请求。它被训练得会输出这种请求。比如“运行 mypy dl.py”（17:59）。包在模型外面的那层代码，叫 agent harness，也叫 scaffolding。它做两件事（19:44）：

  • 在循环里调用 LLM，拿到输出。
  • 如果输出是工具调用，就在你的机器上真的执行。工具输出会作为新的输入追加进去，再推理一次。比如 mypy 打印的“error line 1, expected int…”。直到模型输出给用户的文字，控制权才回到用户。
  • 写文件的工具：在 Claude Code 里，模型可以给出一个 diff。diff 就是一段文字，由 harness 解释并应用到文件上（25:06）。
  • 问：harness 和模型之间有标准接口吗？不算完全标准化，但互通性不错。比如开源的 opencode，能配合不同家的模型（22:08）。Anthropic 和 OpenAI 的都行。
  • 问：模型是随机的，harness 是确定的，它们怎么配合？靠抽样。harness 每次调用模型，都是抽一个输出，再据此行动。模型并不像人那样聪明。有时它会调用你机器上没有的命令。有时会写出错误的代码。但实践中效果相当不错（22:49）。

上下文越满模型越差，换任务就清空 45:58

上下文塞得越多，模型越容易分心。做不相关的事，就清空。走错了路就回退，把最近几步从历史里弹出去。

最小例子（示意）
/clear    # 清空上下文，开始新任务（Claude Code 的命令，补充）
# 回退：把消息从历史末尾弹出去，假装没发生过
# 比追加一句“别这么做了”更省上下文

打个比方上下文像一张草稿纸。写满了，新东西就挤不下。没写满，乱涂的地方多了也看花眼。换题就换张新纸，写错了就擦掉。

回到“模型有固定的上下文窗口”。比如它只支持 10 万个 token 的输入。实践中，即使没超出窗口，输入太多也会让任务变难。上下文被“污染”了。管好输入，模型通常表现更好（46:35）。

讲义的总结是这样的。让智能体拿到需要的信息，但避免不必要的内容。不然会撑爆窗口，或者降低表现。harness 会自动提供并管理一部分上下文。但大量控制权在用户手里。

  • 清空：最基本的控制。聊天时，消息只会越积越多。编码智能体还会把每次工具调用和输出都加进去。做一件和之前无关的事，就杀掉重启。或者用命令清空上下文（47:11）。
  • 回退：你让它做了某事，又改主意了。可以打断它，再追加一条指令。但它已经做的那些都还在上下文里，没用还添乱。多数 harness 有回退命令。它把消息从历史末尾“弹出去”（47:46）。就当没发生过。

一个会话从早用到晚，什么都往里塞。模型就越来越糊涂。前面无关的文件、失败的尝试，都在分散它的注意力。换任务就清空，这是最该养成的习惯。

对话太长就压缩成摘要，查新库读 llms.txt 48:31

对话太长时，harness 用 LLM 把历史前缀总结成摘要。摘要替换掉原来的历史。模型不知道新库，就把 llms.txt 这种纯文本文档放进上下文。

最小例子（示意）

# 同一件事没做完：压缩，接着干。换不相关的事：直接清空

压缩（compaction）。窗口有限，怎么支持无限长的对话？对话很长时，聊天工具和编码智能体会调用 LLM。可以自动触发，也可以手动触发。它把历史前缀总结成摘要，再用摘要替换原来的历史。Claude Code 里可以手动用 /compact，还能看到摘要长什么样。讲师建议你自己试试。来回聊几轮，让它调几次工具。再压缩，看看摘要（49:02）。

更像艺术而非科学。还在做同一件事，就继续，LLM 写的摘要通常相当不错。要做不相关的事，就清空上下文。别留一堆没用的东西，哪怕只是摘要。

子任务交给子智能体，只把结论收回来 55:28

主智能体把一件子任务交给子智能体。子智能体用全新的上下文去干，干完只交回结果。主智能体的上下文不会被细节撑满。

# 主智能体：只收到一句“检查通过”，或者一份问题清单

打个比方像经理派实习生去查资料。实习生翻了一下午文档，回来只交一页总结。经理的桌面一直是干净的。

既然有一个智能体，为什么不能有多个？部分原因还是上下文管理。主智能体发现一个子任务时，不在自己的上下文里做。它启动另一个智能体，只把子任务作为提示交给它。子智能体做完，把控制权和结果交回来。这样主智能体的上下文不会被细节污染。子智能体也只拿到它需要的信息（讲义）。

讲义：用 LLM 来写这些提示

技能、子智能体这些高级功能，都要写提示词。可以先让 LLM 帮你起草。有些智能体甚至内置了这个功能。

为什么会在这里踩坑

子智能体看不到主对话的历史。派活时只说“检查一下”，它不知道查什么。查哪些文件、按什么标准，都要写进提示。另外，它的 description 要写清什么时候用。主智能体只看得到描述，靠它决定要不要委派。

AI 不是魔法：看着对的代码也要审 58:26

它只是一个概率模型。给定一堆输入 token，它给出下一个 token 的条件概率。它不像人那样聪明，会犯错，而且错得很像对的。

python · 最小例子（示意，补充）
def mean(xs: list[float]) -> float:
    return sum(xs) / len(xs)   # 看着没毛病，测试也许都过了
mean([])                       # 空列表：ZeroDivisionError
# 审 AI 写的代码，专挑边界情况看：空输入、None、超大值

打个比方AI 像一个口才很好的新同事。说得头头是道，偶尔也会一本正经地胡说。你指出来，他还可能坚持自己是对的。

工具很强，但 AI 不是魔法，会犯错（58:58）。

  • 审查输出：检查正确性和安全漏洞。讲师多次遇到这种代码。乍看合理，实则有细微错误，找 bug 花了很久。
  • 验证可能比写更难。关键代码，讲师常常干脆自己写，不用 AI（59:30）。
  • 跑偏与“煤气灯”：它会钻进兔子洞。有时它明明错了，你指出来，它还坚持自己是对的。这会让你很困惑。
  • 调试死循环：改代码，跑测试，失败。再改，再失败。代码越改越糟，得盯着点。
  • 别把它当拐杖（讲义）：警惕过度依赖和一知半解。还有一大类编程任务，AI 仍然做不了。计算思维依然有价值（1:00:02）。讲师说，“离计算机科学家过时还远着呢”。
为什么会在这里踩坑

智能体说“全部测试通过”，不等于真通过了。它可能没跑测试，也可能改了测试。练习页有个补充实验。命令被拒绝执行，假模型照样说“能通过编译”。真实模型也可能这样。所以要看原始输出，自己跑一遍验收。
