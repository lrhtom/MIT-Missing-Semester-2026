本讲结论

写代码时，大部分时间在跳转、阅读和小改。Vim 把编辑器界面做成一门能组合的语言。命令就是动词加计数加名词。IDE 靠语言服务器看懂代码的语义。AI 工具有三种形态：补全、行内对话和编码智能体。

开发环境分两派：终端拼装和图形 IDE 0:34

开发环境就是写软件用的一套工具。核心是文本编辑。再配上高亮、类型检查、格式化和补全。

bash · 最小例子（示意）
# 终端派：几个命令行工具拼成一套环境

打个比方终端派像自己攒电脑，每个零件都挑最顺手的。IDE 派像买品牌整机，插上电就能用。

讲师先展示了自己的两套环境。

终端工作流

讲师用 tmux 分出几个窗格。左边 Vim 打开讲义，右下角是 shell，右上角跑着 docker。这套环境由几样东西拼成。终端复用器用 tmux，编辑器用 Vim，shell 用 Zsh。再加上各语言的命令行工具。比如 Python 的 linter 兼格式化器 Ruff，还有类型检查器 Mypy。它很轻量。有的机器没有图形界面，也装不了软件。SSH 上去以后，它可能是唯一选择。

集成开发环境 IDE

IDE 是 Integrated Development Environment 的缩写，比如 VS Code。编辑、lint、自动格式化，全在一个程序里。图形 IDE 更容易上手。AI 功能通常也集成得更好，比如 AI 自动补全开箱即用。课上不少人举手说听过 Cursor。它是 VS Code 的一个分支（fork）。

学生问，终端里的编辑器算不算 IDE（1:47）。讲师说，Emacs 和 Vim 本质上是文本编辑器。装上一堆插件，它们也能表现得像 IDE。不过一般人说 IDE，指的是图形 IDE。

讲义建议

两种都要基本熟悉，至少精通一种。还没有偏好的 IDE，就从 VS Code 开始。

平时只用图形 IDE 的人，SSH 到服务器上常常傻眼。那里没有图形界面，往往也不让装软件。所以终端编辑器至少要会打开、修改、保存和退出。

写代码是跳来跳去地小改，Vim 专为此设计 3:51

写代码很少从头写到尾。大多是跳到一处，读一小段，改一行。Vim 的按键就是为这种节奏设计的。

vim · 最小例子（示意）
j      # 下移一行
10j    # 下移 10 行：数字加动作，这就是组合
f(     # 在本行往右找 (
%      # 跳到和它配对的括号
ci(    # 删掉括号里的内容，直接开始输入

打个比方Vim 的按键像乐高积木。学会几块基本的，就能拼出成百上千种动作。不用一个个死背。

比如用 Word 写文章，通常是从头写到尾，或者从头读到尾。写代码不一样。你在文件之间跳来跳去，读一小段。在这里加个函数，再跳到上面改一行 bug。讲师问，谁能从头到尾一口气写完一个程序？没有人举手（4:41）。Vim 就是为这种“导航加小改”优化的。

  • 手不离键盘：在键盘和鼠标之间来回切换很慢。这是 Vim 和前身 vi 的作者观察到的。所以 Vim 避免用鼠标，连方向键都尽量不用。方向键离主键位太远了。
  • 界面是编程语言：按键就是命令，名字都有助记含义。命令之间还能组合。讲师开场演示了几下（6:56）。j 下移一行，10j 下移 10 行。f 找字符，% 跳到配对的括号。ci( 删掉括号里的内容，并开始输入。
  • 效果：熟练以后，编辑速度能跟上思考速度。就像一个“脑机接口”。
不用 Vim 也能用 Vim 的思想

很多软件支持“Vim 模式”。VS Code 有 VSCodeVim 插件，Zsh 内建了 Vim 模拟。bash 也支持，写法是 set -o vi，练习 1 实测过。连 Claude Code 都有 Vim 编辑模式。

所以 2026 版课程不再专讲 Vim 这个软件（11:34）。怎么用 :wq 退出不再是重点，在 VS Code 里点 X 就行。重点是各处通用的核心思想和按键。

为什么会在这里踩坑

手在键盘和鼠标之间来回挪，每次都要重新找光标。一次只慢一点，可写代码时这个动作极其频繁。Vim 的设计，就是把这一步省掉。

同一个键，在不同模式下干不同的事 8:05

Vim 是模态编辑器（modal editor）。按键先看当前在哪个模式，再决定干什么。

vim · 最小例子（示意，文本是 the quick fox）
x          # Normal 模式：删掉光标下的字符
ix<Esc>    # i 进 Insert，这时 x 就是打一个字母 x
vex        # v 进 Visual，e 选到词尾，x 删掉整个选区
:q!        # 有没保存的修改时 :q 会被拒，加 ! 强制退出

打个比方模式像汽车的挡位。同样踩一脚油门，D 挡往前走，R 挡往后退。踩之前先看挂的是哪个挡。

Command-line运行命令，比如 :q 退出:

拿字母 x 举例。在 Insert 模式下，它插入一个字面的 x。在 Normal 模式下，它删掉光标下的字符。在 Visual 模式下，它删掉选中的部分。

移动命令是名词，指代一段文字 13:28

移动命令也叫名词。它指代从光标到落点的那段文字。单独按是挪光标。前面加个动词，就是对这段文字动手。

vim · 最小例子（示意）

d$     # 加上 d：从光标删到行尾

打个比方移动命令像指路的话，比如“下一个词”“行尾”。单独说，是让你走过去。前面加个“删”，就是把这一段路拆掉。

编辑命令是动词，作用在名词上 18:05

以前用鼠标做的事，现在用键盘上的编辑命令做。它们叫动词，后面跟一个移动，就作用在那段文字上。

vim · 最小例子（示意）
dw     # 删到下一个词首，连词后的空格一起删
cw     # 改这个词：删掉它，再进 Insert 模式
d$     # 从光标删到行尾
x      # 删一个字符，等于 dl
u      # 撤销，Ctrl+r 重做

打个比方动词加名词，就像说“删掉这个词”“改到行尾”。句式是固定的。换个名词，就是一条新命令。

动词和名词能自由组合，这正是 Vim 像编程语言的地方。

命令（讲义）作用
i进入 Insert 模式。但删改文字，应该用比退格键更强的东西
o / O在下方或上方开一个新行，并进入 Insert
d{移动}删除。dw 删一个词，d$ 删到行尾，d0 删到行首。讲师还演示了 dj，删掉本行和下一行
c{移动}修改。cw 改一个词。相当于 d{移动} 再按 i
x / sx 删一个字符，等于 dl。s 替换一个字符，等于 cl
Visual + d / c选中后删除或修改
u / Ctrl+r撤销、重做
y / p复制（yank）、粘贴。d 这类命令也会把删掉的内容存起来
~ / J翻转字符大小写。把下一行接到本行末尾

数字让动作重复，i 和 a 决定带不带外壳 19:18

动作前面加数字，就重复那么多次。名词前面加 i，指括号里面。加 a，连括号一起算。

vim · 最小例子（示意）
3w     # 前进 3 个词
7dw    # 删掉 7 个词，是一条命令，一次 u 就能撤销
ci(    # change inside ()：只改括号里面
da'    # delete around ''：连引号一起删
5u     # 计数几乎哪都能加：撤销 5 次

打个比方i 像只倒掉杯子里的水，杯子留着。a 像连杯子一起扔掉。

计数（count）让一个动作重复多次。3w 前进 3 个词，5j 下移 5 行，7dw 删掉 7 个词。讲师补充，几乎任何命令都能带计数。比如 5u 撤销 5 次（19:51）。

修饰符（modifier）改变名词的含义。i 表示 inner，也就是里面。a 表示 around，也就是连同外壳。

实战：用 Vim 修好有 3 个 bug 的 FizzBuzz 24:13

修 bug 的节奏是固定的。在 Normal 模式里跳到位置，进 Insert 改一点，马上回来。

练习 2 的 lecture.keys 拆成三行（注释是笔记加的）
Goif __name__ == "__main__": main()<Esc>   # bug 1：main 从没被调用
/range<CR>wwi1, <Esc>ea + 1<Esc>           # bug 2：应该从 1 数到 limit
:6<CR>ci"buzz<Esc>                         # bug 3：5 的倍数也打印成了 fizz

打个比方修 bug 像外科手术。先精准找到病灶，切一刀就收手。Normal 模式负责定位，Insert 模式只管那一刀。

FizzBuzz 是“确认你会写代码”的经典题。打印 1 到 n。3 的倍数打印 fizz，5 的倍数打印 buzz。同时是 3 和 5 的倍数，打印 fizzbuzz。讲义给了一个有 3 个 bug 的版本：

讲义原文：坏掉的 FizzBuzz
def fizz_buzz(limit):
    for i in range(limit):
        if i % 3 == 0:
            print("fizz", end="")
        if i % 5 == 0:
            print("fizz", end="")
        if i % 3 and i % 5:
            print(i, end="")
        print()

def main():
    fizz_buzz(20)
bug按键（讲义）本机 Vim 回放后的光标
main 从没被调用。讲师先运行了一次，什么都没输出G 到最后一行，o 开新行。输入 if __name__ == "__main__": main()，再按 EscL12 → L13
从 0 开始，不是从 1/range<CR> 搜索。ww 前进两个词。也可以写 2w，小计数时人们常直接连按。i 输入 1,，Esc。e 跳到下个词尾。a 追加 + 1，EscL2 C14 → C20 → C22 → C27 → C31
5 的倍数打印了 fizz:6<CR> 到第 6 行。ci" 把引号里的内容改成 buzz，EscL6 C13 → C23
  • 讲师指出，a 和 l 加 i 效果一样，但少按一个键。他说这“省了 50% 的输入”（26:45）。这些重叠的专用按键，用一阵就成了肌肉记忆。
  • 工作节奏：平时待在 Normal 模式到处移动。要改的时候进 Insert 改一点，马上回到 Normal。
  • 讲师的 Vim 开了 Python 支持，o 之后自动缩进了，他按了退格。本机回放用的 Vim 不加载任何配置，没有自动缩进。最后 :w 保存。

$ python fizz.py | tr '\n' ' '

为什么会在这里踩坑

第 2 个 bug 最容易只修一半。把 range(limit) 改成 range(1, limit) 还不够。range 不含右端点，最后一个数会丢。要写成 range(1, limit + 1)，才会数到 limit 本身。

bash · 本机实测
$ python -c "print(list(range(5)))"          # 从 0 开始，到 4 为止
[0, 1, 2, 3, 4]
$ python -c "print(list(range(1, 5)))"       # 只改起点，5 还是没有
[1, 2, 3, 4]
$ python -c "print(list(range(1, 5 + 1)))"   # 讲义的修法：右端点加 1
[1, 2, 3, 4, 5]

IDE 靠语言服务器看懂代码，LSP 把 M×N 变成 M+N 28:56

IDE 不会为每种语言各写一套支持。它和各语言的语言服务器之间，说一种通用协议，叫 LSP。

LSP · 最小例子（示意，练习 3 有完整的真实会话）
编辑器 → 服务器：textDocument/completion   # 在 r. 后面，能补全什么
服务器 → 编辑器：Area, H, W                 # 服务器推断出 r 是 Rect，列出它的成员
编辑器 → 服务器：textDocument/definition   # Println 定义在哪
服务器 → 编辑器：publishDiagnostics         # 发现错误时，服务器主动推送，不用你问

打个比方LSP 像电源插座的国家标准。电器厂只管做标准插头，装修队只管装标准插座。M 种电器配 N 种房子，不用做 M×N 种转接头。

补全、跳转这些功能，都要对代码有语义层面的理解。这套协议叫语言服务器协议，英文是 Language Server Protocol。IDE 实现协议的一端，语言服务器实现另一端。两边就能互通。讲师的说法是，把 M×N 问题变成 M+N 问题（30:06）。

比如 VS Code 的 Python 扩展依赖 Pylance，Go 扩展依赖官方的 gopls。

语言服务器带来的功能（讲义）讲师在 VS Code 里的演示
代码补全：输入 object. 后看到字段和方法在一个对象后敲点号，列出所有字段和方法（31:15）
行内文档：悬停或补全时显示文档字段有 docstring 时会直接显示
跳转到定义右键选 Go to Definition，跳到结构体定义。不然只能全局搜索，到处翻
查找引用：跳转定义反过来“我定义的这个结构体，都在哪里用了？”
帮你管 import：整理、删掉没用的、标出缺的用了 fmt 却没导入，出现红色波浪线。保存时自动加上 import（33:05）
代码质量：格式化、类型检查、lint，边写边查错调用不存在的方法，立刻提示“该类型没有这个方法”。不用等编译或跑测试，第 9 讲细讲

为什么会在这里踩坑

没有语言服务器，跳转定义只能按文本全局搜索。同名的函数、字段一多，就跳到别处去了。这时别急着怪 IDE。先看语言服务器装没装、配没配好。

配置语言服务器（讲义）

有的语言，装好扩展和语言服务器就能用。有的还要告诉 IDE 你的环境，才能发挥全部作用。比如在 VS Code 里，要先指定 Python 环境。这样语言服务器才看得到你装的包。环境在第 6 讲细讲。

不同的语言服务器还有各自的设置。比如项目不用类型注解。那就可以在 VS Code 的 Python 支持里，关掉静态类型检查。讲师建议，用到哪种语言，就把它的支持配好。不会就搜 “how to set up Go support for VS Code”。

为什么会在这里踩坑

装了 Python 扩展，import numpy 还是一条红线。多半是 IDE 选错了 Python 环境。语言服务器看不到你装的包。先在 VS Code 里选对解释器，再看红线还在不在。

AI 写代码有三种形态，能改的范围一个比一个大 33:54

补全只能往光标后面续写。行内对话能改选中的代码。编码智能体能跨文件、分多步干活。

最小例子（示意）
def extract_links(md: str) -> list[str]:   # 补全：写到这里，它接着往下写函数体
# 行内对话：选中几行，Ctrl+I，输入“不要用第三方库”
# 编码智能体：在对话框里说需求，它自己翻文件、改多处

打个比方补全像帮你接话的同桌，只能接你的下半句。行内对话像改作文的老师，只改你圈出来的那段。智能体像坐在旁边的搭档。它能自己翻整个项目，也能和你商量。

讲师说这是最难准备的一部分，因为不确定大家的背景。他现场问，谁用过专门写代码的 AI 工具？ChatGPT 这类独立聊天不算。只有约 20% 的人举手，于是重点讲基础。

2021 年中，GitHub Copilot 推出，用的是 OpenAI 的 Codex 模型。从那以后，大语言模型在软件工程里被广泛采用。目前主要有三种形态：

形态你怎么用能改哪里
自动补全 autocomplete边打字边出现灰色建议，按 Tab 接受。可以用注释“引导”它只能在光标之后续写

拿补全去干需要改别处的活，它只会在光标后面硬写。下一节的 import re 被塞进函数中间，就是这么来的。动手前先想清楚改动范围，再挑形态。

补全只看上下文，名字起清楚它才补得对 35:25

AI 补全只在光标处往后续写。它补的是最可能的写法。所以函数名和注释，决定了它补出什么。

python · 最小例子（示意，签名取自讲义）
def extract(contents: str) -> list[str]:
    # 名字太含糊：模型只会把内容按行切开
    # 加一行英文注释，说明要提取 Markdown 链接，它就补对了
def extract_links(contents: str) -> list[str]:
    # 更好：名字自己说清楚，用不着临时注释

打个比方补全像一个听半句话就抢答的同学。你只说“提取”，他不知道提取什么。说成“提取链接”，他就答对了。

补全的形式和传统补全一样，在光标处给出续写建议。可以开着它被动地用。也可以用代码注释来提示（prompt）它。讲师用 VS Code 加 GitHub Copilot 演示。他强调不推荐具体产品，Cursor 里效果一样。演示任务是写一个脚本。它下载本讲讲义，再提取里面所有的链接。

讲义原文：只写了函数签名
import requests

def download_contents(url: str) -> str:

模型补全了函数体。讲师还用快捷键在几个候选之间切换（37:09）：

讲义原文：模型的补全
    response = requests.get(url)
    return response.text

接着写一个名字含糊的函数 def extract(contents: str) -> list[str]:。模型只能按最可能的方式补，结果是把内容按行切开。这对“提取链接”毫无用处。加一行注释 # extract all Markdown links from the content，补全就对了。下面是讲义原文：

讲义原文：注释引导后的补全
    import re
    pattern = r'\[.*?\]\((.*?)\)'
    return re.findall(pattern, content)
  • 只能补光标之后：import re 被塞进了函数中间。按惯例，它应该在模块顶部。这是补全形态固有的局限（40:35）。
  • 更好的做法：函数名起得有描述性，比如 extract_links，再写个 docstring。模型同样能一次补对，docstring 对以后读代码的人也有用。只为引导 AI 写的临时注释，事后删掉（41:45）。
  • 务必检查：模型只是在大量数据上训练出来的概率模型。它没有人那样的智能。接受补全前，要看它是否真做了你想要的。有时得改一改，或者自己重写（37:45）。
讲义原文：把脚本补完
print(extract(download_contents("https://raw.githubusercontent.com/missing-semester/missing-semester/refs/heads/master/_2026/development-environment.md")))

按 Tab 太顺手，最容易漏看。补出来的代码有时看着对，其实有问题。本节的 import re 被塞进了函数中间，就是一例。接受之前一定要读一遍。

行内对话能改已有代码，但通常只改选区 42:25

选中一段代码，用自然语言下指令，模型就改这一段。编辑器用 diff 显示改动，你审完再决定留不留。

最小例子（示意）
Vj                               # Vim 键位：按行选中，j 往下扩
Ctrl+I                           # 唤起行内对话，Mac 上是 Cmd+I
use built-in libraries instead   # 讲义里的指令：别用第三方库
# 红色是要删的行，绿色是新增的行，审完再接受

打个比方行内对话像在文档上圈一段，旁边批注“改成这样”。批注只管圈里的字，圈外的一个不动。

行内对话（inline chat）也是用自然语言让模型写代码。和补全不同，它能改已有的代码。接着上面的例子，假设不想依赖第三方库 requests。讲师在 VS Code 里用 Vim 键位 V 加 j，选中那三行。再按 Ctrl/Cmd+I 唤起行内对话，输入“不要用第三方库”。讲义里写的是 use built-in libraries instead。

讲义原文：模型的提议
from urllib.request import urlopen

def download_contents(url: str) -> str:
    with urlopen(url) as response:
        return response.read().decode('utf-8')

编辑器用 diff 显示改动。红色是删除，绿色是新增。你审完再选择保留（43:38）。

学生提问：改动要用到选区外的代码呢？（视频 44:14）

要看具体实现。讲师现场试了一下。他把光标放在函数里，让它把 import 移到外面。在这个实现里，它只改选区内的内容，没做成有用的事。别的编辑器的行内对话，可能允许改其他地方。这个领域很新，变化很快。

为什么会在这里踩坑

想让它“把 import 移到文件顶部”，可能做不成。有些实现只改选区里的内容，文件顶部不在选区里。这种跨位置的改动，交给编码智能体。

AI 工具基本都要联网，要真隐私只能本地跑 45:25

主流模型太大，只能跑在云端。你的代码和提示词都会发过去。想完全不上传，就得在本地跑模型。

三种选择（示意）
# 云端模型：代码和提示词发到服务商的 GPU 上算，能力最强
# 打开隐私选项：服务商承诺不保留数据，但你只能选择信任
# 本地模型：数据不出电脑，代价是能力差一截、很耗电

打个比方云端模型像去餐馆吃饭，菜好，但后厨你看不见。本地模型像在家做饭，放心，就是手艺差点。

  • 要联网吗？基本都要。这些工具用的模型非常大，有的上万亿参数。要大量显存和高级 GPU 才跑得动。也有能在笔记本上跑的本地小模型。但能力差一截，而且很耗电（46:02）。
  • 能不让代码上传到云端吗？讲师说“可以，但有星号”。有些工具能在设置里打开额外的隐私选项。提供方承诺不保留你的代码和提示词。但你是在信任他们这么做，常见的技术保障手段还很少。真要隐私，只能在本地跑模型（47:08）。
  • 在 Python 以外、没那么灵活的语言里，效果差吗？讲师的经验是“还行”。有些补全模型还会预测光标下一步要去哪。比如它发现你需要 import re。它会先建议光标跳到顶部写 import。写完再跳回来补函数体（48:32）。
  • 在合适的抽象层次上工作：简单的事让 AI 直接搞定。任务超出它的能力，它会写出看着对、其实有 bug 的代码。或者彻底糊涂（49:10）。工具每隔几个月就进步一截。三个月前做不到的事，现在可能轻松完成。所以要一直用，不断试探它的边界。这样你对它擅长什么的直觉，才不会过时。
讲师的提醒（视频 50:52）

这些 LLM 不像人那样有智能。它们是“概率性的下一个 token 预测器”。有时说得合理也正确，有时乍看合理，却完全错误。所以用它们，和把任务交给一位员工不一样。讲师说，希望员工别像这些模型那样，试图对你 gaslight。

为什么会在这里踩坑

AI 写的代码有时看着合理，其实是错的。任务越超出它的能力，越容易这样。别像信任同事那样直接合并，每一行都要自己审。

要 AI 解释、反问、说把握，得用编码智能体 50:19

补全和行内对话只管写代码。想让 AI 先问你问题、解释思路，得用编码智能体。它是对话式的。

对话示意
你：先别写代码。问我几个问题，弄清需求再动手。       # 补全和行内对话做不到这一步
智能体：链接要去重吗？相对路径要不要转成绝对路径？   # 对话式工具可以反过来问你

打个比方补全和行内对话像自动铅笔，你写到哪它补到哪。智能体像一个能聊天的搭档，可以先商量，再动笔。

学生问：能不能让 AI 解释它为什么这么写？能不能先问我问题，再说说它有多确定？讲师说，补全和行内对话做不到，编码智能体可以。它们是对话式工具。讲师说，它“大致相当于接入了你代码库的 ChatGPT”。你可以让它先问你问题，也可以随时问它。

之前有学生问侧边栏的 “Build with agent” 聊天框（40:02）。它和写注释有什么区别？答案也在这里。补全只在光标后补一小段。改文件别处的事，要交给对话或智能体。

补充（非视频内容）：扩展本质上是什么

以 Vim 为例，扩展就是一些脚本。它们放在约定的目录里，启动时会被执行。Vim 8 起自带包机制，~/.vim/pack/*/start/*/plugin/*.vim 会自动加载。练习 4 在沙箱里写了一个 7 行的插件。实测加载前 :Hello 报错，返回 1。加载后正常工作。

VS Code 扩展是装在扩展目录里的 JavaScript 包。由扩展主机进程负责加载。

为什么会在这里踩坑（补充，非视频内容）

扩展能读你的代码，也能运行程序。来路不明的扩展，和第 2 讲的 curl | bash 一样危险。装之前看看发布者、安装量和更新时间。一次只装一个，确认真在用再留下。

# LSP：编辑器实现一次客户端（M），语言实现一次服务器（N），M×N 变 M+N
# AI 补全只能续写光标之后，所以 import re 被塞进了函数中间
# 隐私：设置里的“不保留数据”靠信任，真隐私只能本地跑模型
  • 写代码主要是跳转、阅读和小改。Vim 为此优化，核心思想在各种软件的 Vim 模式里通用。
  • 模态编辑：Normal 是大本营。i、R、v、V、Ctrl+v、: 进入其他模式，Esc 回来。
  • 编辑语言：动词 d c y，计数 3 5 7，名词 w e $ %，修饰符 i a。7dw、ci(、da' 都是这么拼出来的。
  • 语言服务器协议把 M×N 变成 M+N。功能有补全、悬停文档、跳转定义和查找引用。还能整理 import，边写边查错。
  • AI 有三种形态。补全只续写光标之后，行内对话改选区。编码智能体能对话、走多步，第 7 讲细讲。不管哪种，结果都要审。
  • 主流模型在云端。要真正的隐私，只能在本地跑模型。
