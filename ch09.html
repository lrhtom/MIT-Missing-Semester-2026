本讲结论

代码好不好，别靠人盯，交给工具链自动把关。格式化器统一写法，linter 找反模式。测试加覆盖率验证行为。pre-commit 钩子在本地拦，CI 在服务器上拦。命令运行器把长命令变短。正则表达式是贯穿这些工具的小语言。编辑器的搜索替换也靠它。

检查交给工具链，在多个关口各跑一遍 0:00

本讲讲一条质量流水线。同一套检查，在编辑器、提交前和服务器上各跑一遍。

bash · 最小例子（示意）
ruff format --check src   # 格式化器：只报告写法问题，不改文件
ruff check src            # linter：不运行代码，找反模式
python -m pytest          # 测试：真跑代码，看结果对不对
git commit                # 钩子：提交前自动把上面几步跑一遍

打个比方像机场安检。值机、安检口、登机口各查一次。离飞机越近，越没法绕过去。

本讲先讲格式化器、linter 和测试。再讲 pre-commit 钩子、持续集成和命令运行器。最后讲正则表达式。

很多工具只认一门语言。它们得懂这门语言的语义（0:37）。但概念是通用的，每门语言都找得到对应的工具。比如 Python 的 Ruff 能格式化，也能 lint。Prettier 则能跨好几门语言。

讲师全程用一个叫 Minilib 的 Python 小库演示。它只有一个文件，用 Hatch 管理（1:08、3:35）。里面是些没啥用、正好拿来演示的函数，比如 fizzbuzz 和 left_pad。

视频没有完整展示源码。所以笔记照视频的描述，重建了一份 Minilib。它放在本讲练习页的 minilib/ 目录里。视频提到的格式问题、lint 问题和两个 bug，都故意留着。本页的“本机实测”大多跑在它上面。

检查只在自己电脑上跑，换个人就忘了。你今天记得跑格式化，同事明天直接提交。所以检查要写进钩子和 CI，让机器替人记着。

格式化器只改写法，不改程序的意思 1:08

格式化器只动表面写法：引号、空格、import 顺序、行长。改完以后，程序的语法树和原来一模一样。

python · 最小例子（取自下面的实测 diff）
def hypot(a,b):                  # 格式化前：逗号后、* 两边都没空格
    return sqrt(a*a + b*b)
def hypot(a, b):                 # 格式化后：只补了空格
    return sqrt(a * a + b * b)   # 语法树没变，程序的意思也没变

打个比方格式化器像报社的排版员。他只调字距和换行，一个字都不改。所以稿子交给他，你不用再校对一遍。

格式化器英文叫 auto-formatter。有了它，人不用再操心这些细节。脑力可以花在更难的问题上。更大的好处是整个团队的代码风格统一（讲义）。

  • 两种模式（2:25）。检查模式加 --check，只报告，退出码非 0，适合放进 CI。修复模式直接改写文件。
  • 可配置的程度不同。Prettier 能配很多选项，配置文件要提交进仓库。Black 和 gofmt 几乎不让你配。这是为了躲开“自行车棚效应”。引号用单的还是双的，不值得花时间争（2:59）。
  • 编辑器集成：可以设成保存时自动格式化。讲师没演示这一步。
  • 代码得先能被解析，格式化器才能干活（4:07）。

linter 不运行代码，靠读代码找反模式 7:06

linter 做静态分析。它不运行代码，光读代码就能找出反模式。它比格式化器深一层，看的是语义（7:41）。

python · 最小例子（节选自重建的 Minilib）
import subprocess                         # I001：os 应该排在 subprocess 前面
import os                                 # F401：导入了没用，能安全地自动删掉

def divide(a, b):
    if b == 0:
        raise ValueError("divide by zero")   # EM101：字符串直接写进异常，要人工改

打个比方linter 像带你的老同事扫一眼代码。他不用跑程序，光看就知道哪里迟早出事。

  • 规则：每个 linter 带一组规则和预设，可以按项目配置。Ruff 大约有 800 条规则（15:56）。
  • 误报：有些规则会误报。所以都能按文件或按行关掉，Python 里写 # noqa: 规则编号。
  • 文档：好的 linter 会讲清每条规则。查什么，为什么不好，该怎么写。讲义举的例子是 SIM102，也就是可以合并的嵌套 if。
  • 自动修复：有些问题能自动修。讲师强调要分清两种（8:48）。安全修复保证不改变语义。不安全修复要加 --unsafe-fixes，讲师打趣说“如果你觉得刺激”。很难写出安全变换的问题，只能由人来改。

semgrep 在语法树上匹配，正则换个写法就漏 16:29

grep 一个字符一个字符地比，代码换个写法就找不到。semgrep 先把代码解析成语法树，再按结构匹配。

python · 最小例子（取自练习 4 的样本）
subprocess.Popen(cmd, shell=True)    # 1 号：grep 和 semgrep 都能找到
subprocess.Popen(
    cmd,
    shell=True,
)                                    # 3 号：拆成多行，grep 一次只看一行，漏了
P(cmd, shell=True)                   # 5 号：Popen 的别名，字符级搜索认不出
# subprocess.Popen(cmd, shell=True)  # 8 号：只是注释，grep 第一版却报了

打个比方grep 像按字形查字典。同一个词换行写，它就不认识了。semgrep 像懂语法的语文老师。句子怎么断行、换什么代称，主谓宾它都认得。

通用 linter 的规则适合起步。可项目常有自己的规矩。比如“别用 pickle，有安全隐患”，又比如“别用 exec”。semgrep 全名是 semantic grep，用起来像 grep。不同在于，它先把代码解析成语法树，在树上匹配。它支持多种语言。

讲师先用正则搜 subprocess.check_output(.*, shell=True。他用的工具是 ag，一个 grep 的替代品。一开始能找到。可代码稍微一改，正则就匹配不上了。比如多加一个关键字参数，或者把调用拆成多行。他只能不停地补正则，像打地鼠（17:37 到 18:44）。换成 semgrep 是这样写：

讲义原文
$ semgrep -l python -e "subprocess.Popen(..., shell=True, ...)"

模式里的 ... 表示任意参数。讲师演示了一下。拆成多行、多了参数，semgrep 都找得到（19:18）。

练习 4 在本机沙箱里装了 semgrep 1.182.1。它拿 9 种写法逐个测了一遍，结果画在下面的演示里。

为什么会在这里踩坑

拿 grep 做代码规范检查，会两头出错。调用拆成多行，它就漏报。注释和字符串里出现这串字，它又误报。练习 4 实测过 6 处真调用。grep 最多找到 3 处，semgrep 找到 5 处。semgrep 也有盲区。shell=True 藏进字典再用 **kw 传进去，它就看不出来。

测试就是再写一段代码，去检查原来的代码 20:30

测试是一段会自己跑的代码。它调用被测函数，结果不符合预期就报错。代码一直在改，测试就一直跑。它确认你没弄坏东西（21:09）。

tests/test_fizzbuzz.py（内容同视频，注释是笔记加的）
from minilib import fizzbuzz            # 忘了这行，报的是 NameError，不是断言失败


def test_fizzbuzz_3():                  # 名字以 test_ 开头，pytest 才会找到它
    assert fizzbuzz(3) == "fizz"


def test_fizzbuzz_30():
    assert fizzbuzz(30) == "fizzbuzz"   # 30 同时是 3 和 5 的倍数

打个比方测试像给代码配一把尺子。每次改完，拿尺子量一遍。长短不对，马上就知道。

测试是让人相信“代码是对的”的标准手段。这是个很深的话题，这里只讲高层概念。

概念含义
单元测试 unit test测单个函数。比如 fizzbuzz 该返回什么，left_pad 该返回什么
集成测试 integration test测模块之间、服务之间怎么配合
功能测试 functional test端到端地测，看软件是否满足用户需求
测试驱动开发 TDD先把规格写成测试，哪怕只是一部分。再写实现，最后跑测试确认实现达标（21:41）
回归测试 regression test修完 bug 就写一个测试，保证它以后不会悄悄回来（讲义）
性质测试 property-based test见本讲第 7 节
mock用假的实现替代数据库、Web API 这类外部依赖。出自讲义，视频问答也讲了（1:11:42）。见本讲第 16 节

在 pytest 里，测试就是普通函数。它放在约定的位置，名字以 test_ 开头。它不带参数、不返回值，里面写 assert。pytest 会自己找到并运行它们（24:04）。

测试怎么组织，要看语言和框架。做自己的项目时，查一下这门语言用什么测试框架就行。

测试一红，先别急着改被测代码。看清报的是什么错。AssertionError 说明被测代码结果不对。NameError 这类别的异常，多半是测试自己写错了。

更隐蔽的坑是函数名没以 test_ 开头。pytest 根本不会跑它。本机实测：

覆盖率只看哪行跑过，不管结果对不对 26:17

跑测试时，覆盖率工具记下哪些代码行被执行过。它只看测到了哪里，不看测得对不对。

手推 · 最小例子（数字来自下面的实测和视频）
# Cover = (Stmts - Miss) / Stmts，也就是跑到的语句占多少
(22 - 11) / 22    # 本机 TOTAL：50%
(18 - 9) / 18     # 视频：utils.py 有 18 条语句，漏了 9 条，也是 50%

打个比方覆盖率像检查学生有没有把课本每一页都翻过。翻过不代表看懂了。

测试写得好不好，程序很难回答。写测试要创造力，是一门越练越好的手艺。不过有工具帮忙，就是代码覆盖率（26:51）。工具能逐行显示覆盖情况。Codecov 这类服务还能跟踪覆盖率的历史变化（讲义）。

Missing 列怎么读

这一列是没执行到的行号。10-15 是 fizzbuzz 的后几支。注意第 13 行 return "fizzbuzz"。明明测了 fizzbuzz(30)，它还是没跑到。说明这行永远走不到，bug 就在这里。

HTML 报告

coverage html 生成网页报告。它用颜色逐行标出哪些执行过。看一眼就知道下一步该测什么（27:23）。讲师说，这也是评估开源项目质量的好指标（29:08）。

问答：能用 AI 提高覆盖率吗？（29:41）

完全可以，这也是本讲的练习之一。先搭一个闭环。让 AI 智能体能自己跑测试，自己生成覆盖率报告。XML 格式更紧凑，更适合给 LLM 看。然后告诉它：把覆盖率提到 100%。

智能体写测试相当不错。但覆盖率不是完美指标，AI 写的测试也不完美。讲师见过一个前端项目，覆盖率 100%。可那些测试几乎没用（31:05）。所以要审查它的输出。必要时多给点指引，比如“去测功能”。讲义也说，别过度追求覆盖率，专心写高质量的测试。

为什么会在这里踩坑

把覆盖率当 KPI，就会有人写不带 assert 的测试。每行都跑过，覆盖率 100%，bug 一个没抓到。练习 2 实测过这种测试，left_pad 的截断 bug 一直都在。

下面的演示逐条语句算覆盖率。最后看一个真实例子：覆盖率 100%，bug 还在。

性质测试不写具体答案，只写结果该守的规律 31:38

普通测试写的是“这个输入得到这个输出”。性质测试只写函数该满足的性质。输入由测试库成批生成。

python · 视频里的两条性质（按视频描述整理，示意）
@given(st.text(max_size=20), st.integers(0, 50))   # 字符串最长 20，整数取 0 到 50
def test_left_pad_1(s, i):
    assert len(left_pad(s, i)) >= i      # 性质 1：结果长度至少为 i

@given(st.text(max_size=20), st.integers(0, 50))
def test_left_pad_2(s, i):
    assert s in left_pad(s, i)           # 性质 2：原字符串要完整留在结果里

打个比方像验收一台榨汁机。你不必算出每个橙子该出多少汁。只查两条：汁不比橙子多，杯里没有橙子皮。然后扔一千个随机橙子进去试。

left_pad 的规格是给字符串左边补空格。补完的长度至少为 i。讲师写了一个“巧妙”的实现，里面藏着 bug。他借这个例子介绍性质测试，英文是 property-based testing。上面两条性质，整理自视频 34:36 到 36:13。

它更接近形式化规格，但通常只是部分规格（32:14）。这种方法由 Haskell 的 QuickCheck 发明并推广。Python 里对应的库是 Hypothesis。

  • Hypothesis 不做数学证明。它随机生成输入，看性质成不成立。人要给一点提示。比如字符串最长 20，整数取 0 到 50（35:43）。
  • 讲师故意写了几个错误实现，第一条性质照样成立。可见性质只是部分规格（37:23）。
  • 现场还踩了个坑：忘了写 assert。表达式算出 True 或 False，转手就被丢掉。测试永远“通过”（38:19）。
  • 第二条性质找到了具体反例：s = '00'，i = 1（39:26）。拿着它就能去调试。
补充（非视频内容）：不装 Hypothesis 也能体会它的思路

本机没装 Hypothesis。练习不要求，按规范也不额外安装。笔记用 30 行标准库代码，模仿它的两件事。一是随机生成输入，二是把反例“缩小”到最简。在重建的 left_pad 上真跑，源码在下面演示的代码面板里：

pre-commit 钩子不通过，git 就拒绝提交 39:58

每次提交前，git 先跑一遍钩子。任何一个钩子返回非 0，这次提交就不会生成。

bash · 最小例子（示意）
pre-commit install              # 每个克隆做一次，写入 .git/hooks/pre-commit
git commit -m 'Add double()'    # 先跑钩子：格式不对，这次提交被拒
ruff format src && git add -A   # 修好格式，重新暂存
git commit -m 'Add double()'    # 钩子全过，提交才生成
git commit --no-verify          # 应急时跳过钩子，所以服务器上还要 CI

打个比方钩子像小区门口的门禁。刷不过卡就进不了门。可门边还有个侧门，叫 --no-verify。

Git 的钩子（hook）会在某些操作前后，运行你指定的脚本。pre-commit 钩子在每次提交之前运行。

pre-commit 框架让配置更省事。在 .pre-commit-config.yaml 里列出要跑的检查。每个开发者只需执行一次 pre-commit install（40:32）。

minilib/.pre-commit-config.yaml（练习 1，注释是笔记加的）
repos:
  - repo: local                    # 钩子就是本机已有的命令，不用去 GitHub 下载
    hooks:
      - id: ruff-format
        name: ruff format --check
        entry: ruff format --check # 只检查，不修改
        language: system           # 直接在 PATH 里找 ruff
        types: [python]            # 只把暂存的 .py 文件交给它
      - id: ruff-check
        name: ruff check
        entry: ruff check
        language: system
        types: [python]

讲师的配置跑的是 hatch fmt --check。这里换成直接调用 ruff。

钩子返回非 0 的退出码，git 就拒绝提交。修好之前，提交进不去。这样就能在所有开发者身上，强制同一套质量标准。不然人很容易忘了先跑格式化（41:05）。

学生的总结很到位。pre-commit 钩子就是仓库里的一组检查。每次提交前，它们必须全部通过。确实需要时，可以加一个参数跳过，就是 git commit --no-verify（41:45）。

为什么会在这里踩坑

第一，钩子不随克隆带走。配置文件在仓库里，真正的钩子却装在 .git/hooks/ 下。新同事没跑 pre-commit install，钩子就不存在。第二，--no-verify 一加就绕过去了。本机实测，带着两个 lint 错误也提交成功。所以服务器上还得有 CI 再查一遍。

下面的演示走一遍完整流程。提交被拦，修好格式，再提交成功。最后看 --no-verify 怎么绕过。

CI 在服务器上重跑同一套检查，谁也绕不过 41:45

前面的检查都在本机跑。持续集成服务在远程服务器上跑同样的脚本。每次 push、每个 PR，甚至按时间表，它都会跑一遍。

yaml · 最小例子（示意，省掉了检出代码和装 ruff）
on: [push, pull_request]      # 每次 push、每个 PR 都触发
jobs:
  lint:
    runs-on: ubuntu-latest    # 每个作业一台全新的虚拟机
    steps:
      - run: ruff check .     # 退出码非 0，这个作业就变红

打个比方钩子是自家门口的门禁，CI 是机场安检。自家门禁可以不装，也能绕开。机场安检谁都得过。

持续集成服务通常和代码托管平台搭配，比如 GitHub Actions。它在特定事件发生时运行你的脚本。时间表可以细到每周一上午 9 点（42:22）。

触发能抓住什么（讲义）
每次 push引入主线的错误
每个 pull request贡献者带进来的问题。很多人连格式化器都不跑。结果直接显示在 PR 页面上（46:57）
定时外部依赖的问题。比如依赖悄悄发了破坏性改动。版本号却按语义化版本标成兼容（第 6 讲）
  • 能跑什么：格式检查、lint 和测试。编译型语言确认能编译，静态类型语言跑类型检查。讲师的演示里，类型检查作业失败了（46:26）。
  • 矩阵：远程机器不在乎跑得久。可以在多个系统和多个语言版本的组合上，并行跑测试。比如 Windows、Linux、macOS 各配几个版本。讲师管这叫“笛卡尔积”（42:56）。

  • 状态徽章：README 里常放 CI 状态和覆盖率的徽章（讲义）。
  • 组成：工作流是 .github/workflows/ 下的 YAML 文件。结构是触发事件、若干作业 jobs、每个作业的步骤 steps。可以复用别人写好的 action，比如检出代码、安装 Python。最后一步通常是一条 shell 命令。任何一步退出码非 0，就算失败（45:55）。

正则表达式是描述一组字符串的小语言 50:49

一个正则表达式描述一个字符串集合。某个字符串在这个集合里，就叫匹配上了。

bash · 本机实测（用 grep -E 代替 ag）
$ printf 'import numpy as np\nimport os\nfrom x import y as z\n' > imp.py   # 造 3 行
$ grep -nE 'import .* as .*' imp.py   # 找出所有重命名过的 import
1:import numpy as np
3:from x import y as z

打个比方正则像一张招聘启事。“三年经验，会 Python”。它不点名要谁，只描述一类人。符合条件的都算匹配。

这是加讲的话题。它原本排在第 3 讲，因为时间不够挪到了这里。正则表达式英文叫 regular expression，简称 regex。它是描述字符串集合的语言。也可以说，它描述的是字符串模式（51:22）。它横跨很多领域：

  • 命令行工具的参数：前面用 ag 搜代码就是一例。测试成千上万时，可以只跑名字匹配某个模式的那些。讲义举的是 go test -run [regexp]，视频里是 hatch test 的参数（52:03）。
  • 编辑器的搜索与替换：讲师在 Vim 里搜 \d\+。所有数字都高亮出来，还能整体替换（52:37）。
  • 程序里：几乎每门语言都有正则库。能做模式匹配、校验和轻量解析（讲义）。讲义的例子是 ag "import .* as .*"，找出所有重命名过的 Python import。
为什么会在这里踩坑

.* 很宽。import .* as .* 连注释和字符串里的这句话都会匹配。正则只认字符，不懂代码结构。这正是本讲第 4 节里 grep 输给 semgrep 的原因。

正则只检查字符的形状，不检查意思 53:13

正则一个字符一个字符地比形状。\d{4}-\d{2}-\d{2} 认得出日期的样子，却认不出 99 日根本不存在。

[True, True, False]
$ python -c 'import re; print([bool(re.fullmatch(r".+@.+", s)) for s in ["alyssa@mit.edu", "nonsense@@@email", "@mit.edu"]])'   # 三个 @ 也能过
[True, True, False]
$ grep -nE 'hello [^abc]' h.txt      # h.txt：hello a / hello b / hello d / hello ab / hello f

$ grep -nE '\bdef\b' d.py            # d.py 第 2 行是字符串 "hello, blah blah define"

打个比方正则像只看轮廓的门卫。身高体型对得上就放行，从不查身份证。

正则本来是计算机理论里的概念。各种语言和工具都有自己的实现。于是有了很多方言，英文叫 flavor。核心概念相同，表面语法略有差别。

比如 Vim 里要写 \d\+，加号前面也要反斜杠。ag 里写 \d+ 就行（53:44）。这些小差别要么记住，要么用到时再查。本讲用 Python 的正则语法。

手推（注释是推理步骤）

^^^^^^      # 前 6 个字符是 hello 加空格，逐个对上
      ^     # 第 7 个字符是 a，可 [^abc] 偏偏不收 a，这里失败
            # 换个起点重试，后面再也凑不出 hello 加空格，整行不匹配
hello d     # 第 7 个字符是 d，不在 a、b、c 里，匹配

补充（非视频内容）：贪婪与非贪婪

*、+、?、{m,n} 默认是贪婪的。它们先尽量多吃，后面匹配不上，再一点点退回。在后面加一个 ?，写成 *? 或 +?。这就变成非贪婪的，尽量少吃。练习 6 的提示，正是让你读 Python 文档里这一段。

手推 (.+)@(.+) 匹配 nonsense@@@email 的过程：

手推 + 本机实测
# 第 1 步：第 1 组 .+ 很贪，一口吃到末尾
# 第 2 步：后面要一个 @，可已经没字符了，失败
# 第 3 步：往回吐一个字符 l。下一个字符是 l 不是 @，接着吐
# 第 4 步：一直吐到剩下 @email，下一个正好是 @，对上了
# 第 5 步：第 2 组 .+ 吃掉 email，匹配成功
re.match(r"(.+)@(.+)", "nonsense@@@email")    # groups() 是 ('nonsense@@', 'email')，span(1) 是 (0, 10)
re.match(r"(.+?)@(.+)", "nonsense@@@email")   # 非贪婪：groups() 是 ('nonsense', '@@email')，span(1) 是 (0, 8)

打个比方捕获组像拿荧光笔画重点。画过的几段，回头能单独抄出来，也能原样贴到别处。

regex101 上会把它标成 Capture group。

程序里取子串：从一堆 YYYY-MM-DD 的日期里，取出年份或月份。上面就是讲义的例子（1:03:21）。r"…" 是 Python 的原始字符串，能少写很多转义用的反斜杠。

编辑器里的替换：讲师在 Vim 里演示过。他把每个数字换成重复两遍的自己。15 变成 1515，0 变成 00（1:01:08 到 1:02:15）。命令拆开看：

讲师说，同样的办法能从 Web 服务器日志里抽出访客 IP。写一个带捕获组的正则就行。可以在程序里调正则库，也可以交给 grep（1:03:58）。

为什么会在这里踩坑

各家的引用写法不一样。sed 和 Vim 用 \1，VS Code 用 $1。Python 的 re.sub 也用 \1，但替换串要写成原始字符串。不然 "\1" 会先被 Python 转成一个控制字符：

bash · 本机实测（补充，非视频内容）
$ python -c 'import re; print(repr(re.sub(r"(\d+)", "<\1>", "x = 15")))'    # 替换串没加 r
'x = <\x01>'
$ python -c 'import re; print(repr(re.sub(r"(\d+)", r"<\1>", "x = 15")))'   # 加了 r，\1 才是捕获组
'x = <15>'

正则数不了数，解析 HTML 要用真正的解析器 1:04:46

正则没有计数器。“n 个 a 后面跟 n 个 b”，它就表达不了。层层嵌套的 HTML 更不行。

bash · 本机实测（补充，非视频内容）
$ printf '<b>a<b>b</b>c</b>\n' > h.html   # 两层嵌套的 b 标签
$ grep -oE '<b>.*</b>' h.html    # 贪婪：一口吞到最后一个 </b>
<b>a<b>b</b>c</b>
$ grep -oP '<b>.*?</b>' h.html   # 非贪婪：停在第一个 </b>，外层的开头配上了内层的结尾
<b>a<b>b</b>

打个比方正则像只会看眼前一步的人。数括号得记住前面开了几层，它没这个记性。

正则是描述字符串集合的紧凑语言，但能力有限。讲义说，有些集合不属于正则语言，正则写不出来。比如“若干个 a 后面跟同样多个 b”。写成集合是 {aⁿbⁿ | n ≥ 0}。这一点可以用泵引理证明。

更实际的例子是 HTML，它也不是正则语言。拿正则去“解析” HTML，做不对（1:04:46）。上面的实测就是一个小例子。

现代正则引擎有前瞻（lookahead）和反向引用（backreference）这些扩展。能力超出了理论上的正则语言，很实用。但表达力仍然有限。更复杂的语言要用真正的解析器，比如 pyparsing。它是一种 PEG 解析器。

补充（非视频内容）：为什么正则数不了数

理论上的正则，都能换成一台有限状态机。机器只有有限个状态，比如 k 个。下面用鸽笼原理手推一遍：

手推（注释是推理步骤）
# 假设有台 k 个状态的机器，恰好认得 {aⁿbⁿ}
# 依次喂它 1 个 a、2 个 a……直到 k+1 个 a，记下每次停在哪个状态
# k+1 次读数，只有 k 个状态，必有两次停在同一个状态
# 设这两次分别读了 i 个和 j 个 a，i 不等于 j
# 接下来都喂 i 个 b。两边从同一状态出发，走法一模一样
# 所以 a^i b^i 和 a^j b^i 要么都接受，要么都拒绝
# 可前者该接受，后者该拒绝。矛盾，这样的机器不存在

说白了，机器记不住任意大的 n。HTML 能一层层无限嵌套，道理一样。

讲义：让 LLM 帮你写正则

对话式 AI 很擅长生成正则。讲义给了一句提示词，大意如下。

“写一个 Python 风格的正则。从 Nginx 日志行里，匹配出请求的路径。”

后面再附上一行示例日志：169.254.1.1 - - [09/Jan/2026:21:28:51 +0000] "GET /feed.xml HTTP/2.0" 200 2995 "-" "python-requests/2.32.3"。

不管谁写的正则，都要拿真实数据测一测。下面是笔记作者自己写的一版，没问 LLM。在本机对这行日志真跑：

bash · 本机实测（补充）
$ python -c 'import re; print(re.search(r"\"[A-Z]+ (\S+) HTTP/[\d.]+\"", open("access.log").read()).group(1))'   # 第 1 组就是请求路径
/feed.xml
为什么会在这里踩坑

LLM 写的正则看着很专业，可它没见过你的真实日志。格式和它设想的稍有不同，它就悄悄配错。也可能什么都配不上。所以一定拿几行真日志测过再用。

问答：测外部 API 就用 mock 顶替 1:05:24

课后问答里最实用的一条是 mock。代码里调了外部 API，测试时就拿假的顶替。

python · 最小例子（写法示意）
class FakeClient:                         # 接口和真客户端一样，背后是自己写的
    def get(self, url):
        raise TimeoutError("simulated")   # 想测出错分支，就让它直接报错

def test_timeout():
    assert fetch_title(FakeClient(), "/x") is None   # 注入假客户端，离线也能跑

打个比方mock 像消防演习用的假人。外形和真人一样，想让它怎么倒就怎么倒。也不怕伤到谁。

  • 代码里能用正则吗？当然能，前面在 Python REPL 里演示的就是。Python 的正则库叫 re。有的语言标准库里没有正则。比如 Rust，用的是流行的第三方库。搜索工具也常常借用现成的正则库（1:05:24）。笔记补充：ripgrep 用的是 Rust 的 regex 库。ag 是 C 写的，用的是 PCRE。
  • 现场演示 AI 补测试（1:07:19）。AI 一开始给的测试很有用。可你让它生成得越多，它越会生成没用的。除非你好好引导它。人和 AI 一起协作，能达到很好的效果。这次讲师只给了几句提示。让 AI 一边写测试一边修 bug，直到不再变化。最后覆盖率到了 100%（1:09:03）。测试覆盖了 3、5、15 的倍数，还有异常分支。提示词不需要特殊格式，LLM 很能理解英文指令。技巧只影响最后那几个百分点（1:08:32）。
  • 测试和代码放同一个文件？Rust 习惯把小的单元测试写在同一个文件里。复杂的集成测试另外放。Python 也有 doctest。编译型语言把测试写进源文件，有个代价。改测试也得重编译（1:10:08 到 1:11:11）。
  • 代码里有大量 API 调用，怎么测？（1:11:42）用 mock。实现一个和真实 API 接口相同的版本。背后的逻辑是你自己写的，很简单。比如假的 OpenAI 或 YouTube 客户端。测试时把它注入进去。你能让它返回错误，也能离线跑。另一种做法是对真实 API 跑一次，把网络通信全部录下来。以后测试时直接回放。Python 里有 pytest 的 VCR 插件。也可以直接测真实 API。几种做法各有利弊（1:12:58）。
  • 哪里找好的提示词？没有现成的提示词仓库。OpenAI、Anthropic 这些公司都写了不错的提示词指南。示例提示词多半和具体代码库绑定。录屏的智能体编程过程，可能更值得看（1:13:31）。
为什么会在这里踩坑

测试直接打真实 API，又慢又花钱。网络一抖，测试还会随机失败。CI 一会儿红一会儿绿。没人分得清是代码坏了，还是网络坏了。用 mock 或者录制回放，测试才稳定。

一页带走：本讲结论都在这几行里 1:14:42

把本讲浓缩成几行命令。每行的注释就是结论和考点。

本讲速查（注释即考点）
ruff format --check src     # 只改表面写法，语法树不变，所以能放心自动跑
ruff check --fix src        # 只自动修安全的问题。语义问题写不出安全变换，要人看过再改
semgrep -l python -e "subprocess.Popen(..., shell=True, ...)"   # 按语法树匹配，拆行和别名都认得
coverage report -m          # return "fizzbuzz" 那行一直没覆盖：它是死代码，bug 就在这
pre-commit install          # 每人各装一次，没装的人不受约束
git commit --no-verify      # 钩子还能被绕过，所以要 CI 在服务器上统一查
re.fullmatch(r"\d{4}-\d{2}-\d{2}", "2026-01-99")   # 能匹配：正则只看形状，校验日期要用日期解析
re.match(r"(.+)@(.+)", "nonsense@@@email")        # 贪婪：第 1 组吃到 nonsense@@，停在最后一个 @ 前
sed -E 's/([0-9]+)/\1\1/g'  # \1 引用第 1 个捕获组，15 变成 1515
  • 格式化器只改表面语法，语法树不变。它统一团队风格，分检查和修复两种模式。EditorConfig 统一编辑器设置。
  • linter 做静态分析。规则能配置，也能按行写 # noqa。安全修复交给工具，其余看文档人工改。semgrep 在语法树上匹配，适合写项目自己的规则。
  • 测试分单元、集成、功能三类。TDD、回归测试、性质测试、mock 是常用方法。pytest 自动发现 test_ 开头的函数。
  • 覆盖率 = (语句数 − 未执行) / 语句数。它能指出没测到、甚至永远执行不到的代码。但 100% 覆盖不等于正确。
  • pre-commit 钩子在本地查，CI 在服务器上查，查的是同一套。CI 支持 push、PR、定时触发和矩阵。CD 用同一套设施自动部署。命令运行器把长命令变短。
  • 正则描述字符串集合。基础是字面量、字符类、量词和锚点 ^ $。再加上 \d \w \b、分组捕获和替换里的 \1。各工具方言略有不同。正则表达力有限，复杂语言要用解析器。
