练习 1 · $SHELL 只记登录 shell，不一定是眼前这个

Git Bash 实测Linux 未实测

原题：本课需要 Bash 或 Zsh 这样的 Unix shell。Windows 上别用 cmd.exe 或 PowerShell，可以用 WSL 或 Linux 虚拟机。用 echo $SHELL 检查，输出像 /bin/bash 或 /usr/bin/zsh 就对了。

echo $SHELL 只能看出登录时用的 shell。想确认眼前这个是不是 bash，看 $BASH_VERSION 更准。

▶跑

打个比方$SHELL 像入职登记表上写的部门。你后来借调到别的组，登记表不会跟着改。

?原理

$SHELL 是一个环境变量，记的是你的登录 shell。$BASH_VERSION 只有 bash 自己会设置。所以它能直接说明，正在解释这行命令的就是 bash。

!为什么会在这里踩坑
误解
以为 $SHELL 就是当前正在跑的 shell。
真相
它只是登录 shell 的记录。在 bash 里再敲 zsh 进入 zsh，$SHELL 不会变。想知道当前进程是谁，看 $BASH_VERSION 或 ps -p $$。$$ 是当前 shell 的 PID。
考点（答案写在注释里）
echo $SHELL          # 登录 shell，进了 zsh 也不会变
echo $BASH_VERSION   # 只有 bash 会设置，空的就说明不是 bash
ps -p $$             # $$ 是当前 shell 的 PID，看它到底是谁
# 在 PowerShell 里 echo $SHELL 是空的
# Unix shell 才会从环境里继承 SHELL，所以这正说明你不在 Unix shell 里

练习 3 · glob 由 shell 展开，没匹配上就原样留着

Git Bash 实测

原题：find ~/Downloads -type f -name "*.zip" -mtime +30 里的 *.zip 是 glob。glob 是什么？建一个测试目录，试试 ls *.txt、ls file?.txt 和 ls {a,b,c}.txt。参考 Bash 手册的 Pattern Matching。

* 和 ? 由 shell 按磁盘上已有的文件展开。{a,b,c} 不看磁盘，直接生成三个词。

K先回顾

glob 和正则的区别，见第 1 讲第 9 节。

?原理
写法含义谁展开
*任意长度的任意字符，可以是 0 个shell 展开。按已有的文件匹配，结果按名字排序
?恰好 1 个任意字符同上
{a,b,c}花括号展开，直接生成 a、b、c 三个词shell 展开。不管文件在不在
▶跑

读输出时注意两点。file?.txt 匹配到 file1 和 file2，没有 file10，因为 ? 只匹配一个字符。{a,b,c}.txt 不看磁盘，照样生成 c.txt。于是 ls 报错，整条命令退出码是 2。

打个比方glob 像点名册，只喊到场的人。花括号像摆座位牌，不管人来没来，牌子先摆上。

!为什么会在这里踩坑
错误写法
echo *.md，以为没匹配时什么都不输出
实际
bash 默认把没匹配上的 glob 原样留着。于是输出字面上的 *.md，见上面 ex03-b 的第一行。后面要是接 rm，就会去删一个叫 *.md 的文件。
正确写法
想要“没匹配就为空”，先 shopt -s nullglob。实测输出 []。
考点（答案写在注释里）
ls *.txt               # 不加引号：要的就是 shell 先展开成文件列表

练习 5 · 2>&1 要写在 > file 后面

Git Bash 实测

原题：shell 有三条标准流：stdin(0)、stdout(1) 和 stderr(2)。运行 ls /nonexistent /tmp，把 stdout 和 stderr 分别重定向到两个文件。怎么让两者进同一个文件？参考 Redirections。

> out 2> err 让两路各进各的文件。想进同一个文件，写 > all 2>&1，顺序不能反。

K先回顾

重定向见第 1 讲第 13 节。那里演示的第 2 幕画了接线过程。

实测改动

Git Bash 的 /tmp 是 Windows 临时目录，里面全是不相干的文件。所以实测时把 /tmp 换成沙箱里的 demo 目录，它只有一个文件。命令结构完全不变。

▶跑

两者进同一个文件有两种写法。结果逐字节相同，用 cmp 验证过：

打个比方2>&1 是让 2 号“跟 1 号走”。它只看 1 号此刻在哪。1 号要是还没搬家，2 号就跟着留在终端。

!为什么会在这里踩坑
错误写法
ls /nonexistent demo 2>&1 > wrong.txt
现象
错误信息还是打在终端上，文件里只有正常输出。
原因
重定向从左到右处理。2>&1 的意思是，1 号此刻指向哪，2 号就跟着指向哪。执行它时 1 号还连着终端，于是 2 号也连到终端。之后的 > wrong.txt 只改了 1 号。
正确写法
先改 1 再复制，写成 > file 2>&1。或者用 bash 的 &> file。
考点（答案写在注释里）
cmd 2>/dev/null | wc -l   # 只数 stdout 的行数
# stderr 被扔进 /dev/null，而且管道本来就只接 stdout
cmd > all 2>&1            # 对：先把 1 改到文件，2 再跟过去
cmd 2>&1 > all            # 错：2 先跟了终端，报错还在屏幕上

练习 6 · a && b || c 不等于 if-else

Git Bash 实测

原题：$? 是上一条命令的退出码，0 表示成功。&& 只在前一条成功时运行下一条。|| 只在前一条失败时运行。写一行命令，仅当 /tmp/mydir 不存在时才创建它。参考 Exit Status。

答案是 [ -d /tmp/mydir ] || mkdir /tmp/mydir。目录存在时，左边退出码是 0，右边直接跳过。

?原理

目录存在时，[ -d /tmp/mydir ] 退出 0，|| 右边被跳过。不存在时退出 1，就执行 mkdir。整行的退出码，是最后真正执行的那条命令的退出码。

▶跑

第二次运行时，mkdir 根本没执行，所以不会报 File exists。另一个常见答案是 mkdir -p /tmp/mydir。-p 在目录已存在时也返回成功。实测完，脚本自动删掉了 /tmp/mydir。

打个比方|| 像“不行就找备胎”。前一条办成了，备胎就不用出场。

!为什么会在这里踩坑
误解
以为 a && b || c 就等于 if a; then b; else c; fi。
实际
a 成功但 b 失败时，c 也会执行。实测 true && false || echo … 打印了 “c ran”。if 版本不会进 else：
考点（答案写在注释里）
cd mydir && rm -rf *   # cd 失败，rm 就不跑
cd mydir; rm -rf *     # 危险：cd 失败后，照样在当前目录 rm -rf *
# 所以脚本里推荐 set -e，或者用 && 串起来

练习 7 · cd 必须内建，因为子进程改不了父进程的目录

Git Bash 实测

原题：为什么 cd 必须内建在 shell 里，而不能是一个独立程序？提示：想想子进程能影响父进程什么，不能影响什么。

外部程序跑在子进程里。它只能改自己那份当前目录，退出时那份就没了。

?原理

每个进程都有自己的当前目录。shell 运行外部程序时，会创建一个子进程。子进程拿到的是父进程目录的拷贝。它只能改自己的拷贝，退出时拷贝也跟着消失。所以外部的 cd 程序改不了你 shell 的目录。“fork 加拷贝”这一层是补充的系统知识，不在视频里。

▶跑

打个比方子进程像你复印了一张地图交给跑腿的。他在复印件上画了新路线，你手里的原件一点没变。

下面的演示把这段输出画成两个进程框。看子进程的当前目录怎么被拷贝、修改，然后消失：

练习 8 · [ -f "$1" ] 的引号一个都不能省

Git Bash 实测

原题：写一个脚本，接收文件名参数 $1。用 test -f 或 [ -f … ] 检查文件在不在。存在和不存在时，打印不同的信息。参考 Conditional Expressions。

核心就一行 if [ -f "$1" ]; then。$1 外面的双引号一定要加。不然空参数和带空格的文件名，都会出错。

K先回顾

if 与退出码、test 和 [，见第 1 讲第 14 节。脚本参数是 $1。

{}写
▶跑

打个比方双引号像给文件名套个信封。名字里有空格也好，是空的也好，信封都只算一件。

!为什么会在这里踩坑：$1 没加引号
现象
不传参数时，错误版说文件 '' 存在。文件名带空格时，报 [: my: binary operator expected。正确版两种情况都对。
原因
不加引号的 $1 会先按空白切词。空参数让 [ -f ] 只剩一个参数 -f。test 规定单个非空字符串就算真。带空格时，参数变成 -f my file.txt 三个，语法就错了。

[[ -f $1 ]]   # [[ ]] 是 bash 关键字，里面不切词，所以不出错
# 讲义说 [[ ]] 更安全，就是这个原因。为了习惯和可移植，照样加引号（补充）

练习 9 · ./ 运行要 x 权限，bash 读文件只要 r

Git Bash 实测Linux 未实测

原题：把上一题的脚本存成 check.sh，试试 ./check.sh somefile 会怎样。再 chmod +x check.sh 后重试。为什么需要这一步？提示：对比 chmod 前后的 ls -l check.sh。

./check.sh 是让内核执行这个文件，没有 x 就拒绝。bash check.sh 是让 bash 读它，只要 r 就行。

?原理

在 Linux 上，新建的文件默认是 -rw-r--r--，没有 x。./check.sh 会被拒绝，报 Permission denied，退出码 126。chmod +x 给 u、g、o 都加上 x。之后内核读第一行的 #!，找到解释器去运行。

▶跑

下面是本机 Git Bash 的实测结果。NTFS 不记录 x 位，所以 chmod 前后都是 rwx，也复现不了 Permission denied：

打个比方./check.sh 是让这张纸自己站起来干活，得有许可证。bash check.sh 是你拿着纸照着念，看得见字就行。

考点（答案写在注释里）
bash check.sh       # 运行的是 bash，它本身有 x。check.sh 只是被读进去的数据
./check.sh          # 把 check.sh 本身当程序执行，所以它自己得有 x

考点（答案写在注释里）

练习 17 · awk 里跟数字比，别跟字符串比
