▶跑：两个服务，故意先起 web

输出这样读。缓存没起来时，web 返回 503。Windows 上连不上本机端口，要重试约 2 秒才放弃。所以异常是 TimeoutError，Linux 上通常立即是 ConnectionRefusedError。缓存起来后，计数是 1、2、3。缓存被 kill 后又回到 503，web 始终没崩。这正是 depends_on 要解决的启动顺序问题。它也说明服务本身要容忍依赖暂时不可用。

▶跑：静态检查，以及在装好 Docker 的机器上

有 Docker 时的验收标准如下。docker compose ps 显示 web 和 cache 两个服务都在运行。连续 curl localhost:8080，计数递增。docker compose down 后再 up -d，计数接着上次的值。因为具名卷 redis_data 保存了数据。docker compose down -v 会连卷一起删，计数归零。

打个比方配置分层像穿衣服。默认值是内衣，配置文件是衬衫。环境变量是外套，命令行参数是雨衣。别人看到的，是最外面那一层。

!为什么会在这里踩坑：容器里的 127.0.0.1 和 localhost
错误写法
在容器里还监听 127.0.0.1。比如把 HOST 写死在代码里。
现象
容器日志显示服务已经启动。宿主机 curl localhost:8080 却连不上。这条未实测，是按原理推断的。
原因
容器有自己的网络命名空间，127.0.0.1 指的是容器自己。端口映射的流量，是从容器的网卡进来的。只有监听 0.0.0.0 才收得到，这条是补充。
正确写法
把监听地址做成配置。本机默认 127.0.0.1，容器里用 ENV HOST=0.0.0.0 覆盖。就是本练习 Dockerfile 的第 6 行。
错误写法
把 REDIS_URL=redis://localhost:6379 写进 compose。
原因
在 web 容器里，localhost 是 web 自己，Redis 在另一个容器。要用服务名 cache，由 Compose 的内部 DNS 解析。

原题：按 GitHub Pages 快速入门做一个网站。加分题，不计分：给它配一个自定义域名。

静态网站就是一堆文件。仓库里放好 index.html 推上去，GitHub Pages 原样发布。自定义域名靠一个 CNAME 文件加一条 DNS 记录。

发布与静态站点托管，见第 6 讲第 20 节。Git 的提交与推送在第 5 讲。

{}写
▶跑：推送前，先在本地预览

静态站点就是一堆文件，任何静态文件服务器都能预览。Python 自带的 http.server 就够了。--bind 127.0.0.1 只对本机开放。

CRLF 警告来自 Git for Windows 的系统级 core.autocrlf 设置。提交前把换行符登记成 LF，检出时再换成 CRLF。不影响网站。

▶跑：需要 GitHub 账号和域名的步骤
  1. 在 GitHub 新建一个公开仓库，名字是 你的用户名.github.io。这是快速入门的做法。再把上面的提交推上去。
  2. 进仓库的 Settings，再进 Pages，确认来源是 main 分支的根目录。稍等片刻，页面顶部会显示网址。
  3. 验收：浏览器打开 https://你的用户名.github.io/，看到 “Hello, GitHub Pages!”。curl -sI 返回 200。
  4. 加分：在 Settings 的 Pages 里填入自定义域名。它会提交一个 CNAME 文件，内容就是域名。再到域名服务商那里加一条 CNAME 记录。让这个子域名指向 你的用户名.github.io。生效后，dig +short 子域名 CNAME 能看到它。最后在 Pages 设置里勾选 Enforce HTTPS。具体以 GitHub 文档为准。

打个比方GitHub Pages 像商场给的免费橱窗。你把成品摆进去，路过的人就能看到。CNAME 像在橱窗上挂了自家的招牌。
