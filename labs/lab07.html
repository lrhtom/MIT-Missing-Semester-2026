补充实验 · harness 就是一个循环，50 多行就能写完

Git Bash 实测假模型

harness 把上下文交给模型，再执行模型要的工具。工具结果追加回上下文。循环到模型输出文字为止。

做练习前，先把这个循环跑一遍。mini_harness.py 里工具是真的，能读文件、运行命令。模型是假的，按顺序吐出预先写好的回复。所以每次结果都一样。把 fake_llm 换成一次真正的 API 调用。它就成了一个最小的编码智能体。讲义说，核心概念 200 行代码就能实现。

K先回顾

harness 的循环，见第 7 讲第 5 节。上下文管理和压缩，见第 14 节和第 15 节。

{}读
▶跑：批准所有工具调用

输出怎么读。每一行 [推理 #N]，都是把整个上下文交给模型一次。输入从 25 字节涨到 517、599、676 字节。读过的文件、命令的输出，全都留在上下文里。一个请求，背后是 4 次推理、3 次工具调用。

打个比方harness 像餐厅的传菜员，厨师是模型。厨师喊要什么料，传菜员就去库房取。取来放到灶台上，厨师再喊下一样。直到厨师说“出菜”。

▶跑：拒绝运行命令

读文件被配置成自动批准，运行命令需要确认。不加 --approve 时，harness 不执行命令，只告诉模型“被拒绝”。这对应讲师的配置（4:35）。改文件不问，每条 bash 都要他确认。

▶跑：把“上下文窗口”设成 600 字节

第三次工具调用后，上下文 676 字节，超过了上限。harness 把前缀压缩成一条摘要，变成 2 条、112 字节。最后一次推理只带着摘要。真实的 harness 会再调用一次 LLM 来写这份摘要。第 7 讲有两个演示，用的就是这些输出。一个讲工具调用循环，一个讲压缩。

!为什么会在这里踩坑：没验证也敢下结论
现象
extra-b 里，两条命令都被拒绝了。假模型最后照样说“dl.py 能通过编译”。
原因
这个假模型是写死的，不会因为被拒绝而改口。真实模型也可能在没验证的情况下下结论。
正确做法
看 harness 的原始输出，确认工具真的执行了。结论要能被输出撑住，才算数。
考点（答案写在注释里）
python mini_harness.py --approve "…"               # 4 次推理、3 次工具调用，上下文从 25 涨到 676 字节
python mini_harness.py "…"                         # 不批准：run 的结果是“（用户拒绝了这次工具调用）”，39 字节
python mini_harness.py --approve --limit 600 "…"   # 676 字节超限，压缩成 2 条 / 112 字节
ctx.append({"role": "tool", "content": result})    # 工具结果必须追加进上下文：模型没有记忆，只看得到输入

练习 4 · 三种配置的区别：何时进上下文、进多少

格式与体积 Git Bash 实测在智能体中测试未实测

原题：为你选的编码智能体，创建并测试三样东西。一是 AGENTS.md，或者对应的文件，比如 CLAUDE.md。二是一个技能，比如 Claude Code 的 skill 或 Codex 的 skill。三是一个子智能体，比如 Claude Code 的 subagent。想想什么时候该用哪一个。你的智能体可能不支持其中某些功能。可以跳过，或者换一个支持的智能体。

AGENTS.md 每次启动全文加载。技能和子智能体启动时只加载描述。子智能体还在独立的上下文里跑。

AGENTS.md 与技能，见第 7 讲第 16 节。子智能体见第 17 节。

练习 5 · 让智能体写一条 sed，别让它逐行编辑

命令行做法 Git Bash 实测智能体部分未实测

原题：第 9 讲（代码质量）有一道 Markdown 列表正则练习。用编码智能体完成它。把讲义文件里作为列表标记的 - 换成 *。注意不是所有的 - 都是列表标记。它是不是直接编辑文件完成的？让智能体直接改文件来做这种事，有什么缺点和局限？想办法让它不通过直接编辑文件来完成。提示：让它用第 1 讲里的某个命令行工具。

列表标记只在行首，后面跟空格，而且不在代码块里。让智能体写一条 sed 或 awk 命令。规则一眼看清，换个文件还能再用。

K先回顾

第 1 讲的 sed 和 awk。第 9 讲的正则。本讲的上下文与审查，见第 7 讲第 14 节和第 18 节。

?原理：直接编辑的缺点
  • 耗上下文：要把整个文件读进上下文。每一处修改，还要生成一段 diff。文件越大，越慢、越贵，还可能撑满窗口。
  • 难复现、难审查：28 处修改，分散在一堆编辑操作里。你只能逐处检查。一条 sed 或 awk 命令，规则一眼看懂，换个文件还能再用。
  • 容易漏改或误改：模型是概率性的。长文件里逐行手改，可能漏掉几处。也可能把破折号 --- 也改了。以上是根据讲座内容的推理，你做练习时可以验证。

▶跑：在智能体里比较两种提示（需要账号）

验收标准有三条。① 用提示 A 时，记录它是否直接编辑。还有它调了几次编辑工具。再看 git diff --stat 改了多少行，应为 28 行，多了就是误改。② 用提示 B 时，它应该给出一条 sed 或 awk 命令并运行。git diff --stat 同样是 28 行。③ 用 cmp 把两种方式的结果和本页 bullets.sh 的结果比一比。看谁做对了。

打个比方让智能体逐行改，像请人在书里一处处描改符号。让它写 sed，像请他刻一枚印章。印章对不对，你看一眼就知道，还能反复用。

!为什么会在这里踩坑：awk 里写成了 gsub
bash · 本机实测（输入是第 101 行那段文字）
$ cat line101.txt
- `abc` --- matches the literal "abc".
$ awk '{ sub(/- /, "* ") } 1' line101.txt    # sub 只换第一处
* `abc` --- matches the literal "abc".
$ awk '{ gsub(/- /, "* ") } 1' line101.txt   # gsub 全换，破折号被改坏
* `abc` --* matches the literal "abc".
错误写法
gsub(/- /, "* ")
后果
gsub 会把一行里所有的“- ”都换掉。第 101 行的破折号 --- 后面正好有空格。于是它变成了 --*。
正确写法
用 sub。它只替换一行里的第一处匹配，也就是行首的列表标记。
考点（答案写在注释里）
sed 's/-/*/g' code-quality.md        # 错：68 行被改，第 1 行的 --- 变成 ***，front matter 坏了
awk '!code && /^[[:space:]]*- / { sub(/- /, "* ") }'   # 对：只换行首的“- ”，正好 28 行
/^[[:space:]]*```/ { code = !code; print; next }   # 遇到代码块围栏就翻转标志，块里的行一律不动
diff a.md a.md.new | grep -c '^>'   # 数改动行数，再和智能体的 git diff --stat 对照
