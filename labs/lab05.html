练习 1 · 学一条命令，就说出它动了哪些对象和引用

Git Bash 实测

原题：如果你没用过 Git，先读 Pro Git 的前几章。或者玩一遍 Learn Git Branching。边学边把 Git 命令和数据模型对应起来。

这是开放题。每学一条命令，都要能说出两件事。它新建了哪些对象，挪了哪个引用。

K先回顾

对象与内容寻址，见第 5 讲第 6 节。引用和 HEAD，见第 7 节和第 8 节。

?怎么做
  1. 读 Pro Git 第 1 到 3 章，讲基础和分支。或者在 Learn Git Branching 里，过完 Main 页签的前两组关卡。那个网站会把每条命令画成提交图的变化。正适合这道题。
  2. 每学一条命令，就在空的实验仓库里真跑一次。再用三招看穿它：git cat-file -p 看对象，cat .git/HEAD 看引用，git log --all --graph --oneline 看图。
  3. 判断标准是不看文档也能回答。这条命令执行后，对象库多了什么？哪个引用动了？工作区和暂存区变成什么样？下面 9 组实验就是按这个方法做的。每组都对应第 5 讲的一个演示。

读 Pro Git、玩 Learn Git Branching，要你自己完成。本页不写读后感。

打个比方学 Git 命令像学下棋。背开局口诀，不如看懂每一步棋盘怎么变。每走一步，就看对象库和引用变成了什么样。

▶跑 1-a：blob 与 SHA-1，哈希和讲义一字不差

第 2 行用 sha1sum 手算出了同一个 ID。Git 哈希的是 blob 17\0 加上内容。对象存在 .git/objects/44/48adbf…。前 2 位做目录，后 38 位做文件名。

▶跑 1-b：tree、commit 与引用

根 tree 698281bc… 和 foo tree c68d233a…，都和讲义完全一致。git commit 新建了 5 个对象：2 个 blob、2 个 tree、1 个 commit。它还让 master 指向那个 commit。HEAD 里只有一行 ref: refs/heads/master。

▶跑 1-c：改一个字节，哪些对象会变

bar.txt 变了，foo tree 就变了。foo tree 一变，根 tree 也变，于是有了新 commit。没变的 baz.txt 继续用原来的 blob 4448adbf…。对象数从 5 变成 9，新增 4 个，不是 5 个。

▶跑 1-d：暂存区的三种状态

git add 只把文件此刻的内容复制进暂存区。之后再改，就出现 MM。git commit 提交的是暂存区。git restore 用暂存区覆盖工作区。

▶跑 1-e：分支与合并，复刻视频里的 nato.txt 演示
▶跑 1-f：游离 HEAD 与 reflog
▶跑 1-g：rebase 产生新的提交

feature 上两个提交的哈希，从 19113a7、1fc7223 变成了 8736fc2、88a446a。改动一样，但 parent 变了。

▶跑 1-h：远程仓库，本地裸仓库扮演 GitHub

bob 推送之后，alice 的 git status 仍说一致。git fetch 之后，她才知道自己 behind 1。git pull --ff-only 直接快进。

▶跑 1-i：git bisect run

练习 2 · 谁改了哪行：log 加路径，blame 加 show

Git Bash 实测（联网一次）

原题：克隆课程网站的仓库。（1）把版本历史画成图。（2）最后修改 README.md 的是谁？提示：给 git log 加一个参数。（3）_config.yml 里 collections: 这一行，最后一次修改的提交说明是什么？提示：git blame 和 git show。

答案是两条路子。git log -1 -- README.md 找最后改文件的人。git blame 找到改某行的提交，再用 git show 看它的说明。

K先回顾

git log 的选项和路径限定，见第 5 讲第 10 节。blame 见第 19 节。

▶跑：克隆

一共 861 个提交，最早的在 2019-01-04。克隆完成后，脚本把这份副本留在系统临时目录。后面的实验都复制它，不再联网。

▶跑（1）：历史画成图

图里有很多 Merge branch 和 Merge pull request。贡献者的修改先在各自分支上提交，再合进 master。

▶跑（2）：最后修改 README.md 的人

答案是 git log -1 -- README.md。-- 后面的路径，把历史限定在改过这个文件的提交。-1 只取最新一个。第二行是改过 README.md 的提交总数。答案会随仓库更新而变，这里是生成本页时的结果。

{}写（3）：blame 加 show
▶跑（3）

答案是 “Redo lectures as a collection”，时间是 2020-01-17。collections: 这一行，就是那次把讲义改成 Jekyll collection 时加的。

打个比方git blame 像查监控录像，看是谁最后动了这一行。git show 是调出那次的工单，看他为什么动。

!为什么会在这里踩坑：在 U 盘上的仓库里跑 git
现象
笔记作者第一次在 U 盘上的仓库副本里跑 git log。结果报 fatal: detected dubious ownership in repository at '…'。后面还有一句 is on a file system that does not record ownership。
原因
从 Git 2.35.2 起，为了安全，Git 有一条新规矩。属主不是当前用户的目录，它拒绝在里面运行。FAT32 不记录属主，于是一律被当作可疑。
解决
把仓库放到 NTFS 盘上。或者按提示，把这个目录加进 safe.directory。只对你信任的目录这样做。本页实验都在系统临时目录里跑，所以没这个问题。这是补充，是本机遇到的情况。
考点（答案写在注释里）
git log -1 -- README.md            # -- 后面是路径：只看改过这个文件的提交
git blame -L 19,19 _config.yml     # 这一行最后是哪次提交改的
# 那次提交只是改了缩进，怎么找更早真正写这行的人（补充）
git blame -w _config.yml           # -w 忽略空白改动
git blame <提交>^ -- _config.yml   # 从那次的父提交开始，再 blame 一次
git log -L 19,19:_config.yml       # 看这一行的完整演变

练习 3 · 从历史里删文件，就得重建它之后的每个提交

Git Bash 实测filter-repo 未实测

原题：初学 Git 时，常犯两种错。一是提交了不该管的大文件，二是加进了敏感信息。试着往仓库里加一个文件，提交几次。然后把它从历史里删掉，不只是从最新提交里删。可以参考 GitHub 的文档 Removing sensitive data。

只删最新提交里的文件，旧快照里它还在。要从历史里抹掉，得重建它出现之后的每个提交。这串提交的哈希必然全变。

K先回顾

提交不可变、引用可变，见第 5 讲第 7 节。不可达的对象会被回收，见第 13 节。

▶跑：问题重现

最新提交已经是 remove secret 了。可 git show HEAD~2:secret.txt 照样打印出 key。每个提交都是完整快照，旧快照里的文件永远在。

{}写：改写全部历史
▶跑

输出怎么读：第一个提交 984ec36 本来就没有 secret.txt。它的树不变，哈希也没变。从 config 开始，三个提交都换了新哈希：bc3c8bf、67efda1、b721e90。之后没有任何提交含 secret.txt。那个 blob 也被 gc 删了，git cat-file 找不到它。

打个比方改写历史像重印一套账本。改了第 2 页，后面每页的“上一页编号”都得跟着改。旧账本还在柜子里，得把柜子也清掉。

▶跑：GitHub 文档推荐的工具

filter-repo 更快，也更安全，不用手动清理备份引用。装好以后，一条命令就完成。BFG Repo-Cleaner 是另一个常见选择。

!为什么会在这里踩坑
误区 1
以为 git rm secret.txt && git commit 就删干净了。见 ex03-a，历史里它还在。
误区 2
filter-branch 跑完就以为完事了。refs/original/ 备份和 reflog 还指着旧提交。不清理的话，gc 不会删那个 blob。scrub.sh 第 7 到 9 行就是干这个的。
误区 3
以为改写本地历史，就能撤回推出去的秘密。别人的克隆、GitHub 上的缓存和 fork 都可能还有旧提交。第一步永远是作废那个 key（视频 27:05）。改写历史只是第二步。推送时还要 force push，并通知协作者。
考点（答案写在注释里）
git rm secret.txt && git commit   # 只删了最新快照里的，HEAD~2 的快照里照样有
bash scrub.sh secret.txt           # 去掉第 7 到 9 行再跑：cat-file -t 仍输出 blob
# 原因：refs/original 和 reflog 还指着旧提交，gc 不删可达对象（本机补充实测）
# 大文件同理：进了历史，每个克隆都要下载它。只能改写历史瘦身
# 更好的做法是一开始就用 .gitignore 或 Git LFS（补充）

练习 4 · stash 就是两个临时提交加一个引用

Git Bash 实测

原题：从 GitHub 克隆一个仓库，改一个已有的文件。执行 git stash 会怎样？运行 git log --all --oneline，看到了什么？用 git stash pop 撤销刚才的 stash。什么场景下这会有用？

stash 把改动存成两个提交。一个存暂存区，一个存工作区。refs/stash 指着后者，工作区随即变干净。

K先回顾

暂存区见第 5 讲第 9 节。合并提交可以有两个 parent，见第 12 节。

▶跑：在练习 2 克隆的课程网站仓库里

输出怎么读：stash 之后，工作区干净了。git log --all --graph 顶部多出两个提交。index on master 存暂存区，WIP on master 存工作区，后者有两个 parent。git stash pop 把改动放回工作区，再删掉这条 stash。输出里的 Dropped refs/stash@{0} 说的就是这个。

打个比方stash 像把桌上没写完的作业先塞进抽屉。桌面清空了，可以干别的。回来再把抽屉里的东西摊回桌上。

!为什么会在这里踩坑：stash 提交没出现在顶部
现象
笔记作者第一次跑时，把提交时间固定成了 2026-01-16。结果 stash 的两个提交，没出现在 git log 顶部。
原因
固定时间让 stash 提交比仓库里最新的提交还早。git log 按时间排序时，它们就排不到顶部。
处理
这一条实验不固定提交时间。所以这两个 stash 哈希每次运行都不同。
什么时候有用
  • 写到一半，得马上切去别的分支修紧急 bug。现在的改动还不值得提交。
  • 本地有没提交的修改，git pull 拒绝合并。先 stash，pull 完再 pop。
  • 想试试没有这些改动时，测试过不过。
考点（答案写在注释里）
git stash        # 存成两个提交：index on master 存暂存区，WIP on master 存工作区
git stash list   # refs/stash 指着 WIP 那个提交，它有两个 parent
git stash pop    # 放回工作区，再删掉这条 stash
# pop 时冲突了，stash 会被保留。解决完要手动 git stash drop（补充，见 git help stash）

练习 5 · 别名的值不写 git，整串要加引号

Git Bash 实测

原题：和很多命令行工具一样，Git 有配置文件 ~/.gitconfig。在里面建一个别名，让 git graph 输出 git log --all --graph --decorate --oneline 的结果。可以直接编辑 ~/.gitconfig，也可以用 git config 命令。参考 Git Aliases。

答案是 git config --global alias.graph 'log --all --graph --decorate --oneline'。Git 会自动在别名前补上 git，所以值里不写 git。

▶跑

git config --global 写的就是 ~/.gitconfig。可以看到 [alias] 一节多了 graph = …。前几节是本页实验统一设的示例身份和选项。手动编辑这个文件，加上同样两行，效果完全相同。

打个比方别名像手机里的快捷短语。你打 graph，它替你展开成一长串。展开时，它自动在前面加上 git。

!为什么会在这里踩坑：忘了引号，或者别名里多写了 git
错误写法 1
git config --global alias.graph git log --all --graph，没加引号
真实报错
error: no action specified，退出码 129，配置文件根本没写。不加引号时，shell 把后面拆成好几个参数。git config 就认不出你想做什么。
错误写法 2
alias.graph 'git log --oneline'，值以 git 开头
真实报错
expansion of alias 'graph' failed; 'git' is not a git command。Git 会自动在别名前补上 git，于是变成了 git git log。想执行任意 shell 命令，别名要以 ! 开头。
正确写法
git config --global alias.graph 'log --all --graph --decorate --oneline'
考点（答案写在注释里）
git config --global alias.graph 'log --all --graph --decorate --oneline'   # 对
git config --global alias.graph git log --all --graph   # 错：没引号，报 no action specified
git config --global alias.graph 'git log --oneline'     # 错：展开成 git git log
git config --global alias.st '!git status -s'           # ! 开头，才交给 shell 执行（补充）

练习 6 · 全局 gitignore 管住所有仓库的垃圾文件

Git Bash 实测

原题：运行 git config --global core.excludesfile ~/.gitignore_global。之后就能在 ~/.gitignore_global 里定义全局忽略规则。这条命令只设置了位置，文件要你自己建。设好全局 gitignore，用来忽略系统或编辑器生成的临时文件。比如 .DS_Store。

两步就够了。先用 core.excludesfile 指定全局规则文件的位置，再把规则写进去。之后每个仓库都会照它忽略。

{}写：~/.gitignore_global
▶跑

输出怎么读：?? 是未跟踪。notes.txt 是正常文件，应该被注意到。!! 是被忽略。git check-ignore -v 能查出忽略的来源。哪个文件、第几行的规则，一清二楚。排查“这个文件怎么不见了”时很有用。

打个比方全局 gitignore 像你随身带的垃圾分类表。不管走到哪个仓库，都按这张表把垃圾挑出去。

!为什么会在这里踩坑：规则对已跟踪的文件无效
误区
以为加了忽略规则，提交过的文件就不再被跟踪。
实际
gitignore 只管未跟踪的文件。已经在仓库里的文件，要先 git rm --cached 文件 再提交。之后规则才对它生效。这是补充。
考点（答案写在注释里）
git config --global core.excludesfile '~/.gitignore_global'   # 只设位置，文件要自己建
git status --short --ignored    # ?? 是未跟踪，!! 是被忽略
git check-ignore -v .DS_Store   # 查出是哪个文件第几行的规则忽略了它
git rm --cached file            # 已跟踪的文件先移出暂存区，忽略规则才生效（补充）

练习 8 · 同一行被两边改了才冲突，解决完要 add

Git Bash 实测

原题：模拟协作，练习解决合并冲突。（1）git init 一个新仓库，建 recipe.txt，写几行菜谱。（2）提交，然后建两个分支：git branch salty 和 git branch sweet。（3）在 salty 上把 “1 cup sugar” 改成 “1 cup salt”，提交。（4）在 sweet 上把同一行改成 “2 cups sugar”，提交。（5）回到 master，先 git merge salty，再 git merge sweet。发生了什么？看看 recipe.txt。<<<<<<<、======= 和 >>>>>>> 是什么意思？（6）编辑文件，保留你想要的内容，删掉冲突标记。再用 git add 加 git commit 完成合并，或者用 git merge --continue。也可以试试 git mergetool。（7）用 git log --graph --oneline 看合并历史。

两边改了同一行，Git 不替你拍板，就报冲突。你编辑文件、删掉标记，再 git add 标记已解决，最后提交。

K先回顾

三方合并与冲突，见第 5 讲第 12 节。那里演示的第 2 幕就是这道题。

打个比方冲突像两个同事改了同一份报价单的同一格。一个写 1 杯盐，一个写 2 杯糖。系统不敢替你选，就把两种写法都摆出来，等你定。

!为什么会在这里踩坑：冲突没解决就提交
错误写法
冲突后直接 git commit。
真实报错
error: Committing is not possible because you have unmerged files.
正确做法
编辑文件，再 git add 标记已解决，然后 git commit。不想合了，就 git merge --abort 回到合并之前。上面实测里，文件回到了 salty 的内容。还要小心把冲突标记也提交进去。提交前搜一下 <<<<<<<。

考点（答案写在注释里）
git merge salty      # master 没有新提交：fast-forward，不产生合并提交
git merge sweet      # 同一行两种改法：CONFLICT，状态 UU
git add recipe.txt   # 编辑完、删掉标记，add 才算“已解决”
git merge --abort    # 不想合了，回到合并之前
# 反过来先 merge sweet 再 merge salty：sweet 快进，salty 冲突
# 只是 HEAD 那一侧成了 "2 cups sugar"，另一侧是 "1 cup salt"（本机补充实测）
